# Design

Condensed architecture reference for `gprt`. See `docs/REQUIREMENTS.md` for feature status and `docs/KEYBINDINGS.md` for the key reference.

## Module layout and dependency rules

```
go.mod                         module github.com/hirano00o/gprt (go 1.26)
cmd/gprt/main.go               flags (--debug, --config), config load, wiring, app.Run(); returns immediately after Run
internal/config/               YAML config (strict), defaults, gh-style dir resolution
internal/logging/              slog file logger, ring buffer of recent errors (shown by :messages)
internal/model/                domain types (PullRequest, ReviewThread, ReviewComment, Check, ChangedFile, Section…)
internal/gh/                   GitHub client: auth via go-gh, embedded GraphQL queries, REST files with ETag, mapping, errors
internal/cache/                disk+memory store: Entry{Body, ETag, FetchedAt}; namespaced keys; goroutine-safe
internal/diff/                 hunk parser → Hunk/Line with old/new numbers; anchors; thread location
internal/highlight/            chroma tokenising → per-line []Token{Text, Kind}; no tcell dependency
internal/drafts/               draft store keyed by target; atomic JSON files under the state dir
internal/browser/              URL resolver + cli/browser
internal/store/                UI-goroutine-owned state + service layer: sections, current PR, files, pending review,
                                drafts index, mutation queue, refresh scheduling; talks to gh via its own interface
internal/ui/                   tview composition: root, router, panes, dialogs, status bar
internal/ui/keys/              key normalisation + Sequencer (multi-key/count state machine) + keymap tables (pure)
internal/ui/widget/            ListView, DiffView, Span{Text, Style} + span drawing helpers, popup list
internal/ui/editor/            Vim (modal layer, pure) + Editor primitive (TextArea + status line) + mention popup + $EDITOR bridge
internal/ui/theme/             tview.Styles setup, palette-by-hash colours, token → tcell.Style mapping, icon sets
docs/REQUIREMENTS.md           requirement list with implementation status (updated every milestone)
docs/DESIGN.md                 this file
docs/KEYBINDINGS.md            keymap reference (source for the `?` help)
```

**Dependency direction:** `ui → store → {gh, cache, drafts, diff, highlight} → model`.

- `editor` depends only on tcell/tview and receives a `CandidateFunc func(prefix string) []Candidate`.
- `highlight` returns token kinds; `theme` maps them to `tcell.Style`.
- `widget.Span` is the single span type used across widgets.
- `store` defines `type GitHub interface {…}` (grown per milestone); its tests use a fake in the same package.
- `store` never imports tview: it receives `Dispatch func(func())`, wired to `app.QueueUpdateDraw`.

## Domain types (`internal/model`) — implemented

- `RepoRef{Host, Owner, Name}` with `NameWithOwner()`; `PRRef{Repo, Number}` with `Key()` (`host/owner/repo#n`).
- `PullRequest`: ID, Ref, RepositoryID, Title, Body, Author, State, IsDraft, ReviewDecision, Mergeable (`MergeableState`: MERGEABLE|CONFLICTING|UNKNOWN), MergeStateStatus (`MergeStateStatus`: BEHIND|BLOCKED|CLEAN|DIRTY|DRAFT|HAS_HOOKS|UNKNOWN|UNSTABLE), BaseRefName, HeadRefName, HeadOID, Additions/Deletions/ChangedFiles, Labels, ReviewRequests (`Reviewer{Login, Kind: User|Team|Other, AsCodeOwner}`), LatestReviews (`Review{ID, Author, State, Body, SubmittedAt, ReactionGroups}`), Checks (`Check{Name, Status, Conclusion, URL, Workflow, IsRequired}`), RollupState (`StatusState`: SUCCESS|FAILURE|PENDING|ERROR|EXPECTED, `""` when the head commit has no status-check rollup at all), Timeline (`[]TimelineItem`: IssueComment | Review | Commit | Event), ReviewThreads, PendingReview (`*Review`), ReactionGroups, viewer flags (`ViewerCanUpdate`, `ViewerDidAuthor`, `ViewerCanClose`, `ViewerCanReopen`, `ViewerCanReact`), CreatedAt, UpdatedAt, URL. RollupState is populated by the search/list query and drives the list's check icon before the heavier per-check `Checks` list is available; `Checks`, `Timeline`, `ReviewThreads`, and `PendingReview` are populated by the PR detail query (`gh.Client.PullRequest`, M1b) — see the GitHub client section below.
- `ReviewThread{ID, Path, Line, StartLine, Side, StartSide, SubjectType, IsResolved, IsOutdated, ViewerCanReply, ViewerCanResolve, ViewerCanUnresolve, Comments}`.
- `ReviewComment{ID, ReviewID, Author, Body, CreatedAt, State (PENDING|SUBMITTED), ReactionGroups, ViewerCanUpdate, ViewerCanDelete, URL}`; `IssueComment` similar (no `ReviewID`/`State`).
- `ChangedFile{Path, PreviousPath, Status, Additions, Deletions, Patch, HasPatch, SHA}`; `Status` is a `FileStatus` (`added|removed|modified|renamed|copied|changed|unchanged`, lowercase to match the REST "list pull request files" response).
- `Check` / `ChecksSummary` / `ChecksState`: `Summarize(checks) ChecksSummary` tallies outcomes like `gh pr checks` does — a non-`COMPLETED` status (`QUEUED`, `IN_PROGRESS`, `PENDING`, `WAITING`, `REQUESTED`, `EXPECTED`) is pending; a completed check is success on `SUCCESS`, skipped on `SKIPPED`/`NEUTRAL`, and failure on every other conclusion, including an empty or unrecognised one — a completed check is never dropped from the tally, so an unknown outcome (or one this package does not know about yet) reads as a failure rather than silently as green. `ChecksSummary.State()` derives the rollup icon state (failure beats pending beats success; no checks → `none`).
- `Section{Name, Query, Kind}` (`Kind` ∈ DirectReview, TeamReview, Mine, Involved, Custom), `ListItem{PR *PullRequest, Section}`; `RateLimit{Remaining, ResetAt, Known}` returned with every result — `Known` is false when the server did not report a rate limit at all (GraphQL's `rateLimit` field was null, for example on a GHES instance with rate limiting turned off), distinguishing that from "zero remaining requests".
- `ReactionContent` (8 known values) with `Emoji()`; `ReactionGroup{Content, Count, ViewerHasReacted}`.

All types are pure data: no network or UI dependencies, methods are simple derivations of fields already present.

## GitHub client (`internal/gh`) — auth/viewer/search/PR detail implemented (M1a, M1b); files/mutations below planned for later milestones

- `New(opts Options) (*Client, error)` — implemented: `Options{Host, Token, Timeout, Logger, Debug, Transport}`; host/token resolved via go-gh `auth` (`auth.DefaultHost`/`auth.TokenForHost`) when left empty; an empty resolved token returns the sentinel `ErrNoToken`. Builds one `api.GraphQLClient` via `api.NewGraphQLClient(api.ClientOptions{Host, AuthToken, Timeout (default 30s), Transport, EnableCache: false, LogIgnoreEnv: true, Log/LogVerboseHTTP only when Debug})` (in `clientOptions`, extracted from `New` for testability); `LogIgnoreEnv` is always `true`, regardless of `Debug`, because go-gh's own `NewHTTPClient` otherwise reads the ambient `GH_DEBUG` environment variable independently of gprt's `--debug` flag and, when a user's shell happens to have it set, would write verbose HTTP logs straight to `os.Stderr` — corrupting the TUI, which owns the terminal; gprt's `Debug` flag is the only thing allowed to turn on HTTP logging, and even then only to `Options.Logger`, never to stderr directly. `Options.Logger` (an `*slog.Logger`) is bridged to go-gh's `io.Writer`-shaped `Log` option by a small `slogWriter` adapter (which also redacts the auth token from every chunk before it reaches the logger, even in verbose mode — see `redact`). `Client.Host() string` returns the resolved host. Stateless; safe for concurrent use.
- **Reads implemented:** `Viewer(ctx) (model.User, model.RateLimit, error)`; `SearchPullRequests(ctx, query, cursor string) (SearchResult, error)` where `SearchResult{Items []model.PullRequest, EndCursor, HasNextPage, TotalCount, RateLimit, Warnings []string}`, one page of up to 50 results per call. Nodes with no ID (not a PullRequest, or nulled out by GraphQL error propagation) are skipped rather than surfacing as phantom `#0` rows, and their count is added to `Warnings`. go-gh decodes `data` and then returns a non-nil `*api.GraphQLError` whenever `errors` is non-empty, even when `data` also decoded successfully (GraphQL responses can carry both); discarding the page in that case would throw away otherwise-usable results every refresh whenever a single node hits a permission-scoped error (`INSUFFICIENT_SCOPES` resolving a team reviewer without `read:org`, `FORBIDDEN` on a SAML-enforced org member). So a `*api.GraphQLError` only fails the call when at least one of its items is **not** scoped to a specific node (its `Path` does not start with `"search", "nodes", <index>`); a fully node-scoped error keeps the page and reports every item's message in `Warnings` instead. `BuildSearchQuery(kind model.SectionKind, custom, state string) string` composes gprt's fixed base qualifiers, a state term (`open`→`state:open`, `closed`→`is:closed is:unmerged` so closed and merged are mutually exclusive rather than "closed" also matching every merged PR, `merged`→`is:merged`, `all`→ no term; skipped entirely for a Custom section whose own query already restricts by state — negated forms `-state:`/`-is:open|closed|merged` count as "already restricting" too), and the section's qualifier (custom, verbatim, for Custom).
- **`PullRequest(ctx, ref, viewerLogin) (DetailResult, error)`** (implemented, M1b) — one query (`queries/pull_request.graphql`) fetching a pull request's full metadata, reactions, labels, review requests, latest reviews, head-commit status-check rollup (checks), review threads (with their comments), conversation timeline, and the viewer's own pending review (`reviews(author: viewerLogin, states: [PENDING])`, since GitHub has no dedicated field for it — `viewerLogin` is passed in rather than resolved internally, keeping `Client` stateless). `DetailResult{PR model.PullRequest, Warnings []string, RateLimit model.RateLimit}`. Review threads, timeline items, and status-check contexts are three independently paginated connections within that one query; `PullRequest` follows each one's `hasNextPage` by re-issuing the same query with that connection's cursor advanced (the other, already-decoded fields are simply re-read each call — kept simple rather than clever), capping each at 5 additional pages and noting truncation in `Warnings` rather than fetching without bound. A node-scoped GraphQL error under `repository.pullRequest` is handled like search's node-scoped errors (the result is kept, the message surfaces in `Warnings`, deduplicated across pagination rounds — the non-paginated fields, including whatever a persistent error is scoped to, are re-read every round); a review thread, status-check context, or timeline item nulled out by such an error (decoding with every field, including its ID/`__typename`, at the zero value) is dropped the same way search drops an unresolvable node, with an "N … omitted" warning. A null `pullRequest` is `*gh.Error{Kind: KindNotFound}` only when the response carried no GraphQL error at all; when an error caused the null — even one scoped under `repository.pullRequest`, since a non-null child resolver failing (for example a permission error deep in `timelineItems`) propagates the null up to the nearest nullable ancestor, which is `pullRequest` itself — the real error is classified instead, so a transient failure is never misreported as "this pull request does not exist" (a genuine `NOT_FOUND`-typed item still classifies to `KindNotFound`). A failure outside `repository.pullRequest` (for example the repository itself not resolving) always fails the call. The query has no `EnterpriseTeam` inline fragment, for the same GHES-safety reason as `search.graphql`; a `ReviewRequestedEvent`/`ReviewRequestRemovedEvent`'s `requestedReviewer` is narrowed to `User`/`Team` only (a `Bot`/`Mannequin` reviewer on those two timeline events renders as "(removed)" rather than by name). A `StatusContext` (the legacy commit-status API, as opposed to a `CheckRun`) maps its `StatusState` to `model.Check`'s `(Status, Conclusion)` pair using `CheckStatusExpected`/`CheckConclusionError`, which `internal/model` carries specifically for this: `EXPECTED` is that API's own equivalent of "pending", and `ERROR` has no counterpart in the modern `CheckConclusionState` enum. `model.Event.Type` is the GraphQL `__typename` verbatim (for example `"ReviewRequestedEvent"`); `Detail` is a short rendered string for the timeline events that carry more than an actor/timestamp (a label name, a rename, a base-branch change, …), empty otherwise.
- **Reads planned (later milestones):** `ChangedFiles(ref, page)` (REST + ETag via `cache`), `MentionableUsers(repo, q)`, `Teams(org, q)`, `Branches(repo, q)`, `Labels(repo)`, `PullRequestTemplates(repo)`, `Repository(nameWithOwner)`.
- **Mutations (all planned):** `CreatePendingReview`, `AddReviewThread`, `AddThreadReply`, `SubmitReview`, `AddReviewNow` (`addPullRequestReview` with event+threads), `DeletePendingReview`, `UpdateReviewComment`, `DeleteReviewComment`, `AddIssueComment`, `UpdateIssueComment`, `DeleteIssueComment`, `ResolveThread`, `UnresolveThread`, `AddReaction`, `RemoveReaction`, `UpdatePullRequest`, `RequestReviewers(union)`, `MarkReady`, `ConvertToDraft`, `Merge`, `Close`, `Reopen`, `CreatePullRequest`. Each returns the payload fields needed for optimistic apply.
- Queries live in `internal/gh/queries/*.graphql` (embedded via a single `embed.FS`), loaded once per document (`sync.OnceValue`) and decoded into private response structs (`internal/gh/map.go`) before being mapped into `model`; a query field selected for future use but not yet mapped to a model field (for example `isCrossRepository`) is simply left out of the decoding struct rather than added to `model.PullRequest` early.
- Errors: `*gh.Error{Kind: Auth|RateLimited|NotFound|Validation|Network|Server|Unknown, Message, RetryAfter, Err}` implements `Error()`/`Unwrap()`. `classify(err) error` maps a `*api.HTTPError` by status code (401→Auth; 403 with `X-RateLimit-Remaining: 0` or `Retry-After` present→RateLimited with `RetryAfter` from `Retry-After` seconds or `X-RateLimit-Reset`; 403 otherwise→Auth; 404→NotFound; 422→Validation; 5xx→Server), a `*api.GraphQLError` by its first recognised item `Type` (`NOT_FOUND`→NotFound, `RATE_LIMITED`→RateLimited, `FORBIDDEN`/`INSUFFICIENT_SCOPES`→Auth, else Unknown with every item's message joined), a `net.Error`/`*url.Error`→Network, and passes `context.Canceled`/`context.DeadlineExceeded` through unchanged (wrapping them would add an `Unwrap` hop for no benefit).
- **GraphQL is primary** (search, PR detail with `reviewThreads`/`comments`/`reviews`/`statusCheckRollup`, all mutations). **REST** is used only for `/pulls/{n}/files?per_page=100` (patches, ETag; ≤3000 files; `patch` absent for binary/huge files). GraphQL has no ETag; REST 304s are free. go-gh's built-in cache stays **off** (it is TTL-only and caches 404/422 and GraphQL POSTs, which is wrong for gprt's needs).
- Viewer's pending review: `reviews(first: 1, author: $login, states: [PENDING])`. Only one pending review per user per PR; while it exists, every new comment/reply must attach to it (`pullRequestReviewId`), matching GitHub's own UI, which hides "single comment" in that state.
- `addPullRequestReview` without `event` creates a PENDING review; with `event: COMMENT` + `threads:` publishes immediately. `DraftPullRequestReviewThread` has no `subjectType`, so file-level comments always go through `addPullRequestReviewThread(subjectType: FILE)` on a pending review.
- Comments must target lines inside a hunk; file-level comments omit `line`; multi-line comments use `startLine`/`startSide`.
- `requestReviews(union: false)` replaces the reviewer set. Draft toggle: `markPullRequestReadyForReview` / `convertPullRequestToDraft`. Reactions: `addReaction`/`removeReaction(subjectId, content)`.
- Mention candidates: `repository.mentionableUsers(query:, first: 100)`; teams: `organization.teams(query:)`; templates: `repository.pullRequestTemplates`; branches: `repository.refs(refPrefix: "refs/heads/", query:)`.
- Search: 30 req/min, 1000 results max; qualifiers `type:pr archived:false sort:updated-desc` plus a section qualifier; multiple `repo:` in advanced search must be grouped `(repo:a OR repo:b)`. GraphQL budget is 5000 points/hour; every query selects `rateLimit { remaining resetAt }`.
- Section queries de-overlap with negations: `user-review-requested:@me`; `review-requested:@me -user-review-requested:@me`; `author:@me -review-requested:@me`; `involves:@me -author:@me -review-requested:@me`; dedupe by ID stays as a safety net regardless. Custom sections are appended verbatim (the `(repo:a OR repo:b)` grouping rule is documented for users, not enforced).

## Cache (`internal/cache`) — store implemented, ETag/SWR wiring planned

- Layout: `<cache dir>/v1/<host>/<login>/repos/<owner>/<repo>/pr-<n>/<sha256(rest)>.json` and `v1/<host>/<login>/search/<sha256>.json`. `Entry{Body, ETag, FetchedAt}`; path segments outside `[A-Za-z0-9._-]` (including `""`, `.`, `..`) are replaced with `"=" + hex(segment)` — the `=` prefix is outside the safe character class, so an escaped segment can never collide with a literal one, and an empty segment can never disappear via `filepath.Join` and collide two different keys onto the same path. The fixed `repos` segment keeps the PR tree disjoint from the `search` tree at the same level: without it, a repository literally owned by an account named "search" would land under `.../<login>/search/...`, and `InvalidateSearch`'s `os.RemoveAll` would delete that owner's PR caches along with the search cache.
- `Store` serialises `Get`, `Put`, and `invalidateDir` (used by `InvalidatePR`/`InvalidateSearch`) behind a single mutex held across each call's entire body, including its disk I/O, not just the in-memory map: `Store.Get(k) (Entry, bool, error)` checks memory then falls back to disk, and `Store.Put(k, e) error` — after rejecting `e` if its `Body` is nil or its `FetchedAt` is zero (the same two conditions `readDiskEntry`, below, treats as corruption, so `[]byte{}` is a valid non-nil body but a zero-value `Entry` is not) — marshals `e`, then takes the lock and updates memory and writes to disk together. This closes two races: a `Get` reading a file `invalidateDir` is mid-way through deleting could otherwise write the stale result back into memory, and a `Put` in flight during an invalidation could otherwise write its file after the invalidation's `RemoveAll` and resurrect the directory it just deleted (`writeAtomic`'s temp-file-then-rename means a concurrent `Get` can never observe a half-written file at the destination path, so that is not a separate risk). Coarser than a per-key scheme, an accepted trade-off given gprt is a single-user CLI touching small JSON files.
- A missing file is `(Entry{}, false, nil)`. A corrupt file — invalid JSON, or JSON that decodes but has a nil body or a zero fetch time (as a truncated write might produce) — is also `(Entry{}, false, nil)` and is deleted so it does not keep failing on every lookup; if the deletion itself fails, that error is returned instead. Any other read error (for example a permission error) is returned as-is. Disk writes are atomic (temp file + rename). Directories are created mode `0700`, files mode `0600`; no request headers are persisted.
- `InvalidatePR(host, login, ref) error` removes the PR's on-disk directory and the matching memory entries; `InvalidateSearch(host, login) error` does the same for the search namespace. Neither touches unrelated hosts/logins/PRs. Both return the `os.RemoveAll` error instead of swallowing it, since a failed removal would otherwise let a stale disk entry resurface on a later `Get`. Both delegate to shared `prDir`/`searchDir` helpers so the on-disk layout is defined in one place, alongside `Store.path`.
- `Key` should be built with `PRKey(host, login, ref, rest) (Key, error)` or `SearchKey(host, login, rest) (Key, error)` rather than a struct literal: both validate the fields that become on-disk path segments (non-empty host/login; for `PRKey`, also a non-empty repo owner/name and a positive PR number).
- GraphQL stale-while-revalidate is wired for the list (M1a): `internal/store` caches each section's page-1 result under `SearchKey(host, login, query+"\x00")` (only page 1: nothing ever reads a `LoadMore` page back) and the viewer lookup under `SearchKey(host, "-", "viewer")` (a placeholder login, since the real login is not known until that lookup itself completes — this also lets a later run's cache-first viewer read seed the login synchronously, before the network viewer fetch returns, so per-section cache reads on that same call can use it). `LoadList(false)` shows the cached page-1 entry immediately, marked stale, while a network refetch runs; `LoadList(true)` and `Refresh` (the auto-refresh ticker) skip that cache-first read. `Reload` (the `R` key) additionally calls `cache.InvalidateSearch(host, login)` before refetching, so a later `LoadList(false)`'s cache-first read can never resurrect the data `Reload` was asked to discard; `Refresh` does not invalidate, since a routine background refresh has no reason to believe the cache is wrong, only that it might be a few minutes old. A cache-key or marshal failure during a read or write is swallowed rather than propagated (caching here is a best-effort optimisation, not required for correctness, and a missing login before the viewer resolves is the expected, harmless case that triggers this path on a first-ever run), but a genuine I/O error from `Get`/`Put` is logged once per Store via `Logger.Warn` so a persistently broken cache is at least visible in the debug log file when `--debug` is on — the `:messages` ring buffer keeps only `slog.LevelError` and above, so a `Warn`-level entry never reaches it. Section cache writes are additionally gated on the viewer being network-confirmed (see the Store section below), so a page fetched while a cache-seeded login is still unconfirmed is never written under a login that turns out to be wrong. The current pull request's detail (M1b) follows the identical stale-while-revalidate shape, one level down: `internal/store` caches it under `PRKey(host, login, ref, "detail")`. `OpenPR` shows that cached entry immediately, marked stale, while a network refetch runs (mirroring `LoadList(false)`'s section cache-first read); `RefreshPR` (the auto-refresh ticker) and `ReloadPR` (the `R` key, via `Reload`) both skip that cache-first read, and `ReloadPR` additionally calls `InvalidatePR` first, for the same reasons `Refresh`/`Reload` do for the list. The write is gated on `viewerConfirmed` the same way section pages are.

REST reads (planned, M2): send `If-None-Match`; a `304` keeps the cached body, a `200` replaces it. After any mutation on a PR (planned): `InvalidatePR` then refetch.

**Open items:** the in-memory map and on-disk tree are unbounded (no LRU eviction, no pruning of old entries at startup). Deferred to M2, when REST file patches start entering the cache and unbounded growth becomes worth paying for.

## Store / service (`internal/store`) — PR list and PR detail data implemented (M1a, M1b); files/drafts/mutations below planned

- `type GitHub interface { Viewer(ctx) (model.User, model.RateLimit, error); SearchPullRequests(ctx, query, cursor string) (gh.SearchResult, error); PullRequest(ctx, ref model.PRRef, viewerLogin string) (gh.DetailResult, error) }` — the consumer-side subset of `*gh.Client` the store depends on; tests substitute a fake in the same package. `Deps{GitHub, Cache *cache.Store, Dispatch func(func()), Logger, Config, Host, Now func() time.Time}`; `New(deps) *Store` builds the section list (see below) but starts no network activity until `Start(ctx)`.
- All fields are owned by the UI goroutine; no mutex. Goroutines receive `ctx` plus snapshot arguments (section index, cursor, generation token) and never touch the store directly. Results come back only through `Dispatch`.
- Sections: the four built-ins (`DirectReview` "Review requested", `TeamReview` "Team review requested", `Mine` "My pull requests", `Involved` "Involved") followed by one `Custom` section per `config.List.Sections`, in that fixed order — this order is also the priority order `Rows` uses for cross-section deduplication. Each section's search query is built via `gh.BuildSearchQuery` against the store's current list state (`config.List.State` initially) and rebuilt whenever `SetFilter` changes that state. Each section tracks its own items, cursor, `hasNext`, total, loading flag, stale flag, and last error.
- `Start(ctx)`: applies any cached viewer synchronously (a local cache read, not a network call — see the Cache section above for why this must happen before any section cache read), starts a network refresh of the viewer without waiting for it, then calls `LoadList(false)`. `Stop()` cancels the current list context and the current pull request's in-flight detail fetch, if any (it leaves `current`/`currentPR`/`DetailState` untouched — only `ClosePR` clears those).
- Viewer confirmation: a login applied from cache by `applyCachedViewer` is a guess, not a fact — `viewerConfirmed` stays false until the network resolves it at least once. If the confirmed login differs from a seeded one (for example after `gh auth switch` between runs), every section's items are discarded (`discardAllSectionItems`, which also emits `EventListChanged` immediately so the UI drops the wrong rows without waiting for an unrelated event) and a full, cache-skipping `LoadList(true)` runs, so nothing from the wrong account lingers on screen or survives into the reload; the currently open pull request's detail (M1b), if any, is discarded the same way (its viewer-scoped fields — `PendingReview`, `ViewerCanUpdate`/`Close`/`Reopen`/`React` — could otherwise belong to the wrong account) and `ReloadPR` (invalidate + refetch) runs for it. When the viewer resolves *without* a mismatch (the common case: the login was simply unknown until now, for example because `OpenPR` was called before `Start`'s own viewer fetch resolved) and a pull request is open, its detail fetch is unconditionally restarted (`startDetailFetch`, not `RefreshPR`, is called directly: `RefreshPR` itself no-ops while a fetch is already in flight, by design, for the auto-refresh ticker's sake, but an in-flight fetch at exactly this moment is very likely the pull request's own first fetch — started under the stale/empty login, the one that most needs restarting) so its pending-review lookup and viewer-scoped flags reflect the now-known login rather than whatever they were fetched with (possibly an empty `$viewer`); the superseded fetch's eventual result is dropped by the generation check like any other. `cacheSectionPage` refuses to write until `viewerConfirmed` is true, so a section fetched during the unconfirmed window is never cached under a login that turns out to be wrong. If the login is still unknown ("") when `startList` runs and no viewer fetch is currently in flight (`viewerFetchInFlight`), it starts another one, using `baseCtx` (not this generation's list context) so a later generation cancelling the list context does not also cancel — and falsely error-report — an otherwise-healthy viewer retry; a transient viewer failure would otherwise leave every section's cache reads/writes silently disabled (both log at Debug when skipped) for the rest of the session.
- Fetch pattern: `fetchSection(ctx, gen, i, cursor)` registers an in-flight key `{section, cursor}` (a duplicate call for the same key is a no-op) → a goroutine calls `GitHub.SearchPullRequests(...)` and, via a single deferred closure that recovers a panic into the result's `err` (so a panic still reaches the same apply path instead of leaking the in-flight registration and `loading` flag forever) and computes `cancelled := ctx.Err() != nil`, dispatches: check `gen == current` **first**, and only then unregister the in-flight key and apply the result — checking the generation before unregistering means a late, dropped result from a superseded generation can never erase the *current* generation's own in-flight entry for the same key (which would otherwise open a window for a duplicate fetch to slip past the dedup check). `fetchViewer` follows the identical single-deferred-closure shape for the same reason. `cancelled` (not `errors.Is(err, context.Canceled/DeadlineExceeded)`) is what `applyFetchResult`/`applyViewerResult` use to decide whether a failure was *our own* cancellation (Stop, or a superseded generation) and therefore silent: go-gh's underlying `http.Client{Timeout: ...}` produces an error that also satisfies `errors.Is(err, context.DeadlineExceeded)` on a plain request timeout unrelated to `ctx` ever being cancelled, so only `ctx.Err()` — asking whether *we* gave up — tells the two apart; a real timeout on an otherwise-healthy `ctx` is reported like any other error. `LoadList(force bool)` (`!force` shows a cached page-1 first, marked stale), `Refresh` (background re-fetch, never re-shows a cached page since sections already hold live items, and never invalidates the on-disk cache), and `Reload` (invalidates the on-disk search cache for the current login and marks every section stale before behaving like `LoadList(true)`, so its incoming page 1 replaces outright rather than chaining — see below; used by the `R` key) all start a new generation, cancel the previous list context, and clear the in-flight map — clearing it (rather than leaving a superseded generation's entries to expire on their own) lets the new generation's fetches start immediately instead of being dedup-blocked by an old, still-running fetch for the same (section, cursor); `LoadMore(sectionIndex)` fetches the next page under the current generation/context when `hasNext` and not already loading.
- A failed fetch keeps the section's previous items, records the error on both the section and the store (via `recomputeLastErr`, see below), and emits `EventError` — **except** when the failure is our own cancellation (`cancelled`, see the fetch-pattern bullet above), which is silent: no `lastErr`, no `EventError`, just the usual `loading`/in-flight cleanup (this also resets `refreshTargetPages` to 0, stopping any in-progress refresh-chain). The same silence applies to `fetchViewer`/`applyViewerResult`: a cancelled viewer fetch sets neither `viewerLastErr` nor emits `EventError` either. A successful page-1 fetch (`cursor == ""`) always replaces the section's items outright — a PR no longer present in the new page 1 must actually disappear from the list, not linger from a previous fetch — except that when the section was **not** just confirming a stale cache-shown preview for the first time (see `applyCachedFirstPage`) and it previously had more than one page loaded (`sectionState.loadedPages`) and the new page 1 still `HasNextPage`, the store sets `refreshTargetPages` to that previous depth and automatically chains fetches for pages 2..N (each appended with ID-deduplication against what is already held, and its own warnings appended rather than replacing page 1's — see below) to restore the section to its previous depth against fresh data, stopping early on an error or once `HasNextPage` goes false. If a *new* generation starts (another `Refresh`/`Reload`/`LoadList`) while a chain is still mid-flight, `startList` restores `loadedPages` from the abandoned `refreshTargetPages` first (when it is larger) before resetting `refreshTargetPages` to 0 and starting the new generation's own page-1 fetch: without this, the new generation would compute its chain target from the interrupted chain's partial page count instead of the section's true previous depth, permanently shrinking it. `discardAllSectionItems` also zeroes both fields, so a login-mismatch reset does not inherit the wrong account's page depth. A later page (`cursor != ""`, whether from `LoadMore` or an automatic chain) is appended with the same ID-deduplication and is intentionally never cached, since only the page-1 cache key is ever read back; page 1 is cached (subject to the viewer-confirmation gate above) after every page-1 apply. Every apply then updates cursor/hasNext/total and clears stale.
- `lastErr` (`LastError()`) is never assigned directly: `recomputeLastErr` derives it from persistent per-source state, in priority order — a dedicated `panicErr` if set (from `recoverGoroutine`, cleared only when the next list generation starts via `startList`, not by an unrelated fetch succeeding in the meantime), else `viewerLastErr` if set, else `detailErr` (the open pull request's own standing detail error, ranked above section errors because the open pull request is what the user is looking at), else the first section (in priority order) with a standing `lastErr`, else nil — and is called after every viewer fetch, section fetch, detail fetch, or recovered-panic outcome, and directly from `OpenPR`/`ClosePR`, which clear `detailErr` themselves. This was originally a plain "last write wins" field set inline at each call site (including directly inside `recoverGoroutine`), which raced: the viewer fetch, each section's fetch, and a recovered goroutine panic are independent, uncoordinated sources dispatching onto the same channel with no ordering guarantee, so (caught only by `go test -count=3`, not a single run) an unrelated success could dispatch after, and silently clear, a genuine standing error from a different source.
- `sectionState.warnings` (surfaced via `SectionStates`, see below) follows the same "page 1 is authoritative, later pages only add to it" rule as items: a page-1 apply replaces `warnings` outright with that page's `Warnings`, while a later page (`LoadMore` or a chain page) appends its own `Warnings` with string-deduplication instead of overwriting — otherwise a clean chained page 2 would silently erase whatever page 1 had warned about.
- `LastRefresh()` updates only once every section's page-1 fetch within one generation has *succeeded*: `pendingPageOne` starts at `len(sections)` in `startList` and counts down as each page-1 result (not `LoadMore`, not an automatic refresh-chain page) resolves via `notePageOneOutcome`; `generationHadError` latches true on any page-1 failure in that generation, suppressing the update even though `pendingPageOne` still reaches zero.
- Cache I/O failures: a `Get`/`Put` error (as opposed to a normal cache miss) is logged via `Logger.Warn("cache read/write failed", "err", err)` at most once per Store (`cacheWarned`), so a persistently broken cache does not spam the log on every fetch; this reaches the debug log file when `--debug` is on, not `:messages` (its ring buffer keeps only `slog.LevelError` and above — see `internal/logging.Recorder`).
- `gh.SearchResult.Warnings` (data that could not be fully resolved on a page, but did not fail it — see the GitHub client section above) is kept per section and surfaced via `SectionStates() []SectionState{Section, Loading, Stale, HasNext, Total, Err, Warnings}`; each distinct (section, warning message) pair is also logged once via `Logger.Warn` (same `:messages` caveat as cache failures above), so a warning that persists across refreshes is not re-logged every time.
- Refresh: `StartAutoRefresh(ctx, interval)` runs a `time.Ticker` goroutine whose only action is `Dispatch(func(){ store.Refresh(); store.RefreshPR() })`; it stops when `ctx` is done. `RefreshPR` is a no-op when no pull request is open. Wiring the ticker to a real `refresh_interval` in `cmd/gprt`, and the UI to `OpenPR` when a pull request is selected, are the M1b UI slice's work.
- `Rows() []Row` (`Row{Kind Header|Item, Section, Item model.ListItem, Stale}`): items are deduplicated across sections by PR ID, keeping the section that appears first in priority order; the current filter (see below) is applied to each section's claimed items; remaining items are sorted by `UpdatedAt` descending; a section left with no items after filtering is omitted entirely, including its heading.
- Filter (`filter.go`, pure and independently tested): `SetFilter(text)` parses `repo:`/`author:`/`reviewer:`/`label:`/`state:` qualifiers (case-insensitive value matching except free text tokens, which must all match) plus free text matched against title, `#number`, `owner/name`, and author login. Omitting `state:` reverts the search state to `Config.List.State` rather than leaving it at whatever a previous `SetFilter` call last set — `"state:closed"` followed later by `"author:alice"` shows open PRs filtered by author, not closed ones. An unrecognised state value is ignored for search-triggering purposes (the raw text is still stored, so `Filter()` and every other qualifier in the same string still take effect) and reported via `EventError`. When the resolved state does change, every section's query is rebuilt, every section is marked stale (so `Rows` shows the old data as stale immediately rather than looking frozen until the new fetch lands), and a full `Reload` runs.
- Events (`Subscribe(fn func(Event))`, emitted synchronously from `apply`, never from a goroutine): `EventViewerLoaded`, `EventListChanged`, `EventLoadingChanged`, `EventRateLimitChanged`, `EventError` (`Section` set when scoped to one section), `EventPRChanged` (M1b — `CurrentRef`/`CurrentPR` changed), `EventPRLoadingChanged` (M1b — `DetailState().Loading` changed). `EventLoadingChanged` and `EventPRLoadingChanged` are always emitted together, from a single `emitLoadingChanged` helper, whenever detail loading starts or stops — `Loading()` folds in `detailLoading`, so anything driving the spinner off `EventLoadingChanged` alone still needs telling. Accessors: `Viewer()`, `RateLimit()`, `LastRefresh()`, `Loading()` (any section, or the current PR's detail, loading), `LastError()`, `CurrentRef()`, `CurrentPR()`, `DetailState()` (M1b — see below).
- `StartAutoRefresh`'s ticker goroutine (which has no fetch result of its own to apply on a panic) defers `recoverGoroutine(op)` directly (never wrapped in a closure, so `recover` inside it is "called directly by a deferred function" as the language requires); a recovered panic is logged and dispatched as `EventError` instead of crashing the process. `fetchSection`/`fetchViewer` recover inline instead, as described above, since they must always dispatch their (possibly panic-derived) result through one path.
- **Current PR / detail state (implemented, M1b, data side only — no UI yet):** `current *model.PRRef` (the pull request `OpenPR` last opened, or nil) and `currentPR *model.PullRequest` (its most recently applied detail, from cache or the network) are Store fields alongside the list's `sections`. `CurrentRef() (model.PRRef, bool)`, `CurrentPR() *model.PullRequest`, and `DetailState() DetailState{Loading, Stale bool; Err error; Warnings []string; FetchedAt time.Time}` are the read-only accessors the UI slice renders against.
  - `OpenPR(ref)`: sets `current`, discards any previously held `currentPR` (a stale detail for a *different* pull request must never linger under the new ref), applies a cached detail immediately if one exists (`cache.PRKey(host, login, ref, "detail")`, marked `Stale`), then starts a network fetch under a new generation (`detailGen`, incremented; the previous generation's context is cancelled). A successful fetch replaces `currentPR`, clears `Stale`, records `Warnings`/`FetchedAt`, and writes the cache (gated on `viewerConfirmed`, like section pages); a failed fetch keeps the previous `currentPR`, sets `DetailState().Err`, and emits `EventError` — except our own cancellation (a later `OpenPR`/`ReloadPR`/`ClosePR` superseding this generation, or `Stop`), which is silent, exactly like a superseded section fetch.
  - `RefreshPR()`: like `Refresh`, skips the cache-first read (the store already holds live data, if any); also a no-op when nothing is open or a detail fetch is already in flight.
  - `ReloadPR()`: invalidates the pull request's on-disk cache entry (`cache.InvalidatePR`) before re-fetching, and marks the existing detail `Stale` first so the UI does not look frozen while the fetch is in flight; a no-op when nothing is open. `Reload()` (the `R` key) now calls `ReloadPR()` in addition to reloading the list.
  - `ClosePR()`: cancels any in-flight detail fetch (bumping `detailGen` so a late result is dropped, silently) and clears `current`/`currentPR`/`DetailState()` back to their zero values.
  - Fetch pattern: a single-slot in-flight flag (`detailFetchInFlight`) — not a map keyed like the list's `inFlight`, since there is only ever one "current" pull request — registered/cleared on the UI goroutine; the goroutine itself follows the same single-deferred-closure shape as `fetchSection`/`fetchViewer` (`go func(){ res, err = GitHub.PullRequest(ctx, ref, login); defer recover-into-err; dispatch(func(){ if gen != detailGen { return }; clear in-flight; apply(res, err, cancelled) }) }()`), checking the generation before clearing the flag for the identical reason `fetchSection` does.
- Files (planned): REST pages fetched sequentially (page count derived from `changedFiles`); each page is parsed, published as rows, and its lines enqueued as highlight jobs on a pool of 2 workers, cancelled by context on PR switch. All pages are refetched when `HeadOID` changes.
- Pending review (planned): discovered on PR load; `EnsurePendingReview` creates one lazily. Pending comments come from `reviewThreads.comments` with `State == PENDING` (to verify against the first real PR in M3b); the review query supplies the review's ID and body.
- Mutations (planned): a single-flight FIFO queue; the composer's send action is disabled while one is in flight. Optimistic apply of the payload, then `InvalidatePR` and refetch; state-changing mutations (merge/close/reopen/draft/title/labels/reviewers/submit) also refetch the list. If `addPullRequestReview` fails with "already has a pending review", the store rediscovers the pending review and retries as add-to-review.
- Drafts (planned): keyed by `drafts.Key(prKey, kind, anchor)`. An editor change triggers `drafts.Save` synchronously (atomic temp+rename, no debounce); drafts are cleared on send/discard. Anchor sets are precomputed for gutter markers; drafts that no longer resolve to a line (for example after a force-push) surface in the `p` list to open or discard.

## Vim editor (`internal/ui/editor`) — planned (M3a)

- `editor.Vim` (pure): a modal state machine over `Text interface { Text() string; Cursor() int; SetCursor(int); Replace(start, end int, s string); Select(start, end int) }`. Tests use a string-backed fake that panics on an offset not aligned to a grapheme-cluster boundary; production wraps `*tview.TextArea` (`Cursor()` = the start of `GetSelection()` when nothing is selected; the adapter works before the first `Draw`, so it is unit-testable). Modes: Normal / Insert / Visual / VisualLine / Command; state: count, pending operator, unnamed register (with a linewise flag), visual anchor. `Handle(key) Action` returns `Consumed` | `ForwardToTextArea` | `Command(":w"…)` | `MentionQuery(prefix)`.
- **Undo/redo live in the layer, not in `TextArea`** — `TextArea` groups insert-mode keystrokes per word and does not export its own undo. Every command maps to one `Replace(start, end, new)`; the layer records `{start, old, new}`; `u` = `Replace(start, start+len(new), old)`, `Ctrl-r` is the inverse. Commands that enter insert mode (`i a I A o O cc cw c$ C s`) snapshot `Text()` on entry and, on `Esc`, push a single entry built from the common prefix/suffix diff, so one insert session is one undo unit, matching vim. `SetText` (`:e` return, draft restore) pushes one entry so `u` returns to the previous text. `Ctrl-z`/`y`/`l`/`d`/`k`/`q`/`x`/`v` are never forwarded to `TextArea`.
- Motions compute byte offsets from `Text()` (called once per keystroke) using `uniseg` grapheme boundaries (`Select` rounds up to a cluster boundary, so implementing `h` as "-1 byte" would not move on CJK text); operate on logical lines; keep the desired column in display cells; `j`/`k` skip whole wrapped paragraphs like vim (`gj`/`gk` is out of scope); word classes are unicode-aware. After `Replace` the cursor sits at the end of the replacement, so every command sets the cursor explicitly (`dd` → next line start, `O` → new line start, `p` → last pasted character, `x` → same column). Leaving insert mode moves the cursor left one column, matching vim.
- Insert mode forwards a whitelist to `TextArea`: runes, Enter, Tab (when the popup is closed), Backspace, Delete, arrows, Home/End, Ctrl-w, Ctrl-u. `Esc`/`Ctrl-s`/popup keys are intercepted first; everything else is dropped. Forwarding is a single path: the router calls `textArea.InputHandler()(ev, app.SetFocus)` and returns `nil`. Paste (`PasteHandler`) is accepted in any mode and recorded as one undo entry.
- `Editor` primitive (`Flex`: `TextArea` + status line): `Focus` delegates to `TextArea`; `Draw` runs `Flex.Draw` then the mention popup (`*tview.List`), placed at the cursor's screen position from `GetCursor`/`GetOffset`/`GetInnerRect` (opens upward when it does not fit, like `InputField`); cursor style is set via `screen.SetCursorStyle` (steady block in normal/visual, steady bar in insert; reset on blur/exit). Mention detection runs in the `changed` handler (`@[\w-]*` before the cursor); accepting a candidate is one `Replace(atPos, cursor, "@login ")`; candidates come from the injected `CandidateFunc` (fuzzy match; `MatchedIndexes` are byte offsets, converted to cells with `uniseg` for highlighting).
- The composer is removed from the `Flex` (`RemoveItem`) when hidden, never resized to 0 — a `TextArea` drawn at width 0 stops extending its lines.
- External editor: `:e` runs `app.Suspend(func(){ temp file; exec config editor > $EDITOR > vim })`, then `SetText` (plus an undo entry), then `app.Sync()`.

## Configuration (`internal/config`) — implemented

Config file: `~/.config/gprt/config.yaml` (or the resolved `ConfigDir()`), strict YAML, every key optional.

```yaml
host: github.com          # default: gh's default host
refresh_interval: 5m
icons: unicode            # unicode | nerd
editor: ""                # overrides $EDITOR for :e
browser: ""               # overrides $BROWSER
highlight_style: github-dark
tab_width: 4
list:
  state: open             # open | closed (not merged) | merged | all
  sections:
    - name: Backend
      query: "org:acme label:backend"
keys:                     # action ID → key sequence (vim notation); unspecified actions keep defaults
  global.toggle_list: "<C-w>o"
  diff.comment: "c"
  pr.submit: "S"
```

- `ConfigDir()`, `CacheDir()`, `StateDir()` follow gh's own precedence rather than `os.UserConfigDir`/`adrg/xdg`, which resolve to `~/Library/…` on macOS and would diverge from `~/.config/gh`, which gprt piggybacks on for authentication:
  - Config: `GPRT_CONFIG_DIR` > `$XDG_CONFIG_HOME/gprt` > `~/.config/gprt`
  - Cache: `$XDG_CACHE_HOME/gprt` > `~/.cache/gprt`
  - State: `$XDG_STATE_HOME/gprt` > `~/.local/state/gprt`
  - A non-absolute `$XDG_CONFIG_HOME`/`$XDG_CACHE_HOME`/`$XDG_STATE_HOME` is invalid per the XDG Base Directory specification and is silently treated as unset. `$GPRT_CONFIG_DIR` is gprt's own variable, not an XDG one: if it is set but not absolute, `ConfigDir()` (and therefore `DefaultPath()`) returns an error naming the variable and its value instead of silently falling back to `$XDG_CONFIG_HOME`.
- `Load(path)` returns `Default()` unchanged if the file does not exist; a path that exists as a symlink whose target does not (a broken symlink) is instead reported as an error, since treating it as "no config" would silently hide the misconfiguration. An empty document (zero bytes, blank lines, comments only, or just a `---` marker) also returns `Default()` unchanged: goccy/go-yaml's `Decoder.Decode` overwrites its destination with a zero value before reporting `io.EOF` for an empty document, so `Load` uses `yaml.NewDecoder(...).Decode` specifically to detect that `io.EOF` and discards the now-zeroed struct in favour of a fresh `Default()`, rather than the naive `yaml.UnmarshalWithOptions` (which would silently return the zeroed config with no error at all). A file with more than one YAML document (separated by `---`) is rejected as `*config.ParseError`: without this check the decoder would silently parse only the first document and ignore the rest. A lone trailing `---` with nothing meaningful after it is not a second document (decoding it also reports `io.EOF`, same as an empty file) and is accepted. Otherwise `Load` unmarshals starting from `Default()` (so omitted keys keep their default) with `yaml.Strict()` (unknown keys are a config error), then calls `Validate()`. A parse/strict-decode failure, or a rejected extra document, is returned as `*config.ParseError{Path, Err, Formatted}`: `Error()` returns `yaml.FormatError`'s human-readable text (what a user sees) or the plain "multiple YAML documents" message, `Unwrap()` returns the underlying yaml error (so callers can still `errors.Is`/`errors.As` against the cause).
- `Validate()` collects every problem via `errors.Join` instead of stopping at the first one: `icons` ∈ {unicode, nerd}; `list.state` ∈ {open, closed, merged, all}; `refresh_interval` ≥ 30s; `tab_width` ∈ [1, 16]; each `list.sections[i]` needs a non-empty `name` and `query`; each `keys[action]` needs a non-empty sequence. A non-integral `tab_width` (`2.5`) is silently truncated by the YAML decoder before `Validate` ever sees it (`tab_width: 2.5` becomes `2`, no error) — a YAML-decoder quirk, not a validation gap.

## Mutation sequences

PR = pull request node ID, PRV = viewer's pending review ID, T = thread ID, C = comment ID. After every mutation: apply the payload → `InvalidatePR` → refetch the PR (state-changing mutations also refetch the list).

|--------|-------------------|-----------------------|
| Line comment, single | `addPullRequestReview(PR, event: COMMENT, threads: [{path, line, side, body}])` | not offered → add to review |
| Line comment, add to review | `addPullRequestReview(PR)` → PRV → `addPullRequestReviewThread(pullRequestReviewId: PRV, path, line, side, body)` | `addPullRequestReviewThread(PRV, …)` |
| Range comment (single side) | as above + `startLine`, `startSide` | same |
| File comment, single | `addPullRequestReview(PR)` → `addPullRequestReviewThread(PRV, path, subjectType: FILE)` → `submitPullRequestReview(PRV, event: COMMENT)`; a failure mid-way leaves a pending review that shows up in `p` for discard | `addPullRequestReviewThread(PRV, subjectType: FILE)` |
| File comment, add to review | `addPullRequestReview(PR)` → `addPullRequestReviewThread(PRV, subjectType: FILE)` | same as right column above |
| Reply, single | `addPullRequestReviewThreadReply(T, body)` | not offered → `addPullRequestReviewThreadReply(T, body, pullRequestReviewId: PRV)` |
| Reply, add to review | ensure pending → `addPullRequestReviewThreadReply(T, body, PRV)` | same |
| General PR comment | `addComment(subjectId: PR, body)` (always immediate) | same |
| Edit own review comment | `updatePullRequestReviewComment(pullRequestReviewCommentId: C, body)` | same |
| Delete own review comment | `deletePullRequestReviewComment(id: C)`; deleting the last pending comment prompts "discard review?" | same |

| Resolve / unresolve | `resolveReviewThread(threadId: T)` / `unresolveReviewThread(threadId: T)` (disabled on pending threads) | same |

## Concurrency rules

Binding for every implementer; violating one of these is a defect regardless of test coverage.

1. `store` fields are UI-goroutine only; no mutex. Goroutines get ctx + snapshot values, never the store itself.
2. `dispatch` is called only from goroutines the store started; never from key handlers or dispatch callbacks. Synchronous results return by value. Tests drive `Dispatch` through a channel-based fake event loop (a fake that calls `f()` synchronously is forbidden because it would hide deadlocks).
3. Every async result carries a generation token; `apply` drops results whose token != current (ctx cancel alone is not enough).
4. Timer callbacks (`AfterFunc` debounce, refresh ticker) only `dispatch(func(){ store.X() })`.
5. In-flight dedup map is registered/unregistered on the UI goroutine.
6. `cache.Store` (mutex) and `gh.Client` (stateless) are goroutine-safe; rate-limit info travels with results.
7. Mutations run through a single-flight FIFO queue; no re-send while in flight.
8. Highlight pool (2 workers) is ctx-cancelled on PR switch; check chroma lexer concurrency in M2 (else one lexer per worker).
9. Every goroutine has `defer recover` → log + toast. Never wait for goroutines after `app.Stop()` (tview #1163); `main` returns as soon as `Run()` returns.
10. `app.Suspend`/`app.Sync` may be called from key handlers; never `app.Draw()` from the event loop; use `QueueUpdateDraw` everywhere. SimulationScreen tests run `Run()` in a goroutine and synchronise assertions through `app.QueueUpdate`.

Both the launcher's stderr and the fallback's stderr are captured through a small bounded writer (`boundedWriter`, 4 KiB) rather than an unbounded `bytes.Buffer`, since a long-lived or chatty process could otherwise grow gprt's memory for as long as it keeps writing. `cli/browser.Stdout`/`Stderr` are process-global variables, not per-call options: `New` points them at `io.Discard` and a private bounded buffer so the fallback launcher never writes to gprt's own stdout/stderr (which would corrupt the TUI) and a fallback failure's captured stderr is included in the returned error; constructing a second `Opener` repoints these globals at its own buffer, so an older `Opener`'s `Fallback` (if it still runs afterward) silently captures nothing rather than "interleaving" with the newer one — gprt only ever constructs one `Opener`, so this is accepted. |

If the wrapped handler's `Handle` returns an error (for example the log file becomes unwritable), that error is always propagated, and — once per `Recorder`, via `sync.Once` — a `"debug log write failed: …"` entry is pushed into the ring so the failure is visible even though it could not reach the file. |
| Tests | `net/http/httptest`, `tcell.NewSimulationScreen("")` | Standard library plus tcell's simulation screen for UI smoke tests. |
