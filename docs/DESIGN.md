# Design

Condensed architecture reference for `gprt`. See `docs/REQUIREMENTS.md` for feature status and `docs/KEYBINDINGS.md` for the key reference.

## Module layout and dependency rules

```
go.mod                         module github.com/hirano00o/gprt (go 1.26)
cmd/gprt/main.go               flags (--debug, --config), config load, wiring, app.Run(); returns immediately after Run
internal/config/               YAML config (strict), defaults, gh-style dir resolution
internal/logging/              slog file logger, ring buffer of recent errors (shown by :messages)
internal/model/                domain types (PullRequest, ReviewThread, ReviewComment, Check, ChangedFile, Section…)
internal/gh/                   GitHub client: auth via go-gh, embedded GraphQL queries, REST files with ETag, mapping, errors
internal/cache/                disk+memory store: Entry{Body, ETag, FetchedAt}; namespaced keys; goroutine-safe
internal/diff/                 hunk parser → Hunk/Line with old/new numbers; anchors; thread location
internal/highlight/            chroma tokenising → per-line []Token{Text, Kind}; no tcell dependency
internal/drafts/               draft store keyed by target; atomic JSON files under the state dir
internal/browser/              URL resolver + cli/browser
internal/store/                UI-goroutine-owned state + service layer: sections, current PR, files, pending review,
                                drafts index, mutation queue, refresh scheduling; talks to gh via its own interface
internal/ui/                   tview composition: root, router, panes, dialogs, status bar
internal/ui/keys/              key normalisation + Sequencer (multi-key/count state machine) + keymap tables (pure)
internal/ui/widget/            ListView, DiffView, Span{Text, Style} + span drawing helpers, popup list
internal/ui/editor/            Vim (modal layer, pure) + Editor primitive (TextArea + status line) + mention popup + $EDITOR bridge
internal/ui/theme/             tview.Styles setup, palette-by-hash colours, token → tcell.Style mapping, icon sets
docs/REQUIREMENTS.md           requirement list with implementation status (updated every milestone)
docs/DESIGN.md                 this file
docs/KEYBINDINGS.md            keymap reference (source for the `?` help)
```

**Dependency direction:** `ui → store → {gh, cache, drafts, diff, highlight} → model`.

- `editor` depends only on tcell/tview and receives a `CandidateFunc func(prefix string) []Candidate`.
- `highlight` returns token kinds; `theme` maps them to `tcell.Style`.
- `widget.Span` is the single span type used across widgets.
- `store` defines `type GitHub interface {…}` (grown per milestone); its tests use a fake in the same package.
- `store` never imports tview: it receives `Dispatch func(func())`, wired to `app.QueueUpdateDraw`.

## Domain types (`internal/model`) — implemented

- `RepoRef{Host, Owner, Name}` with `NameWithOwner()`; `PRRef{Repo, Number}` with `Key()` (`host/owner/repo#n`).
- `PullRequest`: ID, Ref, RepositoryID, Title, Body, Author, State, Merged, MergedAt (populated by `MergePullRequest`'s payload, M5; `Merged` is GitHub's own explicit boolean, redundant with but more direct to check than `State == PRStateMerged`), IsDraft, ReviewDecision, Mergeable (`MergeableState`: MERGEABLE|CONFLICTING|UNKNOWN), MergeStateStatus (`MergeStateStatus`: BEHIND|BLOCKED|CLEAN|DIRTY|DRAFT|HAS_HOOKS|UNKNOWN|UNSTABLE), BaseRefName, HeadRefName, HeadOID, Additions/Deletions/ChangedFiles, Labels (`Label{ID, Name, Color}` — `ID` added M5, selected only by the detail query's `labels` connection, empty for a label mapped from search), ReviewRequests (`Reviewer{ID, Login, Kind: User|Team|Other, AsCodeOwner}` — `ID` added M5, selected only by the detail query's `reviewRequests` connection, empty for a Bot/Mannequin/EnterpriseTeam/removed reviewer or one mapped from search), LatestReviews (`Review{ID, Author, State, Body, SubmittedAt, ReactionGroups}`), Checks (`Check{Name, Status, Conclusion, URL, Workflow, IsRequired}`), RollupState (`StatusState`: SUCCESS|FAILURE|PENDING|ERROR|EXPECTED, `""` when the head commit has no status-check rollup at all), Timeline (`[]TimelineItem`: IssueComment | Review | Commit | Event), ReviewThreads, PendingReview (`*Review`), ReactionGroups, viewer flags (`ViewerCanUpdate`, `ViewerDidAuthor`, `ViewerCanClose`, `ViewerCanReopen`, `ViewerCanReact`), CreatedAt, UpdatedAt, URL. RollupState is populated by the search/list query and drives the list's check icon before the heavier per-check `Checks` list is available; `Checks`, `Timeline`, `ReviewThreads`, and `PendingReview` are populated by the PR detail query (`gh.Client.PullRequest`, M1b) — see the GitHub client section below.
- (M5) `RepositoryInfo{ID, Ref, DefaultBranch, MergeCommitAllowed, SquashMergeAllowed, RebaseMergeAllowed, DeleteBranchOnMerge, ViewerPermission}`; `Branch{Name, HeadOID}`; `Team{ID, Slug, Name}`; `PullRequestTemplate{Filename, Body}` (`Filename` empty for GitHub's single root-level `PULL_REQUEST_TEMPLATE.md` template); `MergeMethod` (`MERGE`|`SQUASH`|`REBASE`, matching GraphQL's `PullRequestMergeMethod` enum exactly); `RepositorySummary{Ref, ID, DefaultBranch, IsArchived}` (the create-PR repository picker's candidate shape — `model.User` was not reusable here, since a picker candidate needs a repository identity, not an account one).
- `ReviewThread{ID, Path, Line, StartLine, Side, StartSide, SubjectType, IsResolved, IsOutdated, ViewerCanReply, ViewerCanResolve, ViewerCanUnresolve, Comments}`.
- `ReviewComment{ID, ReviewID, Author, Body, CreatedAt, State (PENDING|SUBMITTED), ReactionGroups, ViewerCanUpdate, ViewerCanDelete, URL}`; `IssueComment` similar (no `ReviewID`/`State`).
- `ChangedFile{Path, PreviousPath, Status, Additions, Deletions, Patch, HasPatch, SHA}`; `Status` is a `FileStatus` (`added|removed|modified|renamed|copied|changed|unchanged`, lowercase to match the REST "list pull request files" response).
- `Check` / `ChecksSummary` / `ChecksState`: `Summarize(checks) ChecksSummary` tallies outcomes like `gh pr checks` does — a non-`COMPLETED` status (`QUEUED`, `IN_PROGRESS`, `PENDING`, `WAITING`, `REQUESTED`, `EXPECTED`) is pending; a completed check is success on `SUCCESS`, skipped on `SKIPPED`/`NEUTRAL`, and failure on every other conclusion, including an empty or unrecognised one — a completed check is never dropped from the tally, so an unknown outcome (or one this package does not know about yet) reads as a failure rather than silently as green. `ChecksSummary.State()` derives the rollup icon state (failure beats pending beats success; no checks → `none`).
- `Section{Name, Query, Kind}` (`Kind` ∈ DirectReview, TeamReview, Mine, Involved, Custom), `ListItem{PR *PullRequest, Section}`; `RateLimit{Remaining, ResetAt, Known}` returned with every result — `Known` is false when the server did not report a rate limit at all (GraphQL's `rateLimit` field was null, for example on a GHES instance with rate limiting turned off), distinguishing that from "zero remaining requests". The store records rate limits only through `setRateLimit`, which ignores an unknown value, so no fetch or mutation path can replace a known figure with "unknown".
- `ReactionContent` (8 known values) with `Emoji()`; `ReactionGroup{Content, Count, ViewerHasReacted}`.

All types are pure data: no network or UI dependencies, methods are simple derivations of fields already present.

## GitHub client (`internal/gh`) — auth/viewer/search/PR detail/files implemented (M1a, M1b, M2); issue-comment mutations implemented (M3a); review mutations implemented (M3b); reaction mutations and mentionable-users read implemented (M4 data slice); repository metadata/branches/labels/templates/teams/viewer-repositories reads and PR edit/merge/create mutations implemented (M5 data slice)

- `New(opts Options) (*Client, error)` — implemented: `Options{Host, Token, Timeout, Logger, Debug, Transport}`; host/token resolved via go-gh `auth` (`auth.DefaultHost`/`auth.TokenForHost`) when left empty; an empty resolved token returns the sentinel `ErrNoToken`. Builds one `api.GraphQLClient` via `api.NewGraphQLClient(api.ClientOptions{Host, AuthToken, Timeout (default 30s), Transport, EnableCache: false, LogIgnoreEnv: true, Log/LogVerboseHTTP only when Debug})` (in `clientOptions`, extracted from `New` for testability); `LogIgnoreEnv` is always `true`, regardless of `Debug`, because go-gh's own `NewHTTPClient` otherwise reads the ambient `GH_DEBUG` environment variable independently of gprt's `--debug` flag and, when a user's shell happens to have it set, would write verbose HTTP logs straight to `os.Stderr` — corrupting the TUI, which owns the terminal; gprt's `Debug` flag is the only thing allowed to turn on HTTP logging, and even then only to `Options.Logger`, never to stderr directly. `Options.Logger` (an `*slog.Logger`) is bridged to go-gh's `io.Writer`-shaped `Log` option by a small `slogWriter` adapter (which also redacts the auth token from every chunk before it reaches the logger, even in verbose mode — see `redact`). `Client.Host() string` returns the resolved host. Stateless; safe for concurrent use.
- **Reads implemented:** `Viewer(ctx) (model.User, model.RateLimit, error)`; `SearchPullRequests(ctx, query, cursor string) (SearchResult, error)` where `SearchResult{Items []model.PullRequest, EndCursor, HasNextPage, TotalCount, RateLimit, Warnings []string}`, one page of up to 50 results per call. Nodes with no ID (not a PullRequest, or nulled out by GraphQL error propagation) are skipped rather than surfacing as phantom `#0` rows, and their count is added to `Warnings`. go-gh decodes `data` and then returns a non-nil `*api.GraphQLError` whenever `errors` is non-empty, even when `data` also decoded successfully (GraphQL responses can carry both); discarding the page in that case would throw away otherwise-usable results every refresh whenever a single node hits a permission-scoped error (`INSUFFICIENT_SCOPES` resolving a team reviewer without `read:org`, `FORBIDDEN` on a SAML-enforced org member). So a `*api.GraphQLError` only fails the call when at least one of its items is **not** scoped to a specific node (its `Path` does not start with `"search", "nodes", <index>`); a fully node-scoped error keeps the page and reports every item's message in `Warnings` instead. `BuildSearchQuery(kind model.SectionKind, custom, state string) string` composes gprt's fixed base qualifiers, a state term (`open`→`state:open`, `closed`→`is:closed is:unmerged` so closed and merged are mutually exclusive rather than "closed" also matching every merged PR, `merged`→`is:merged`, `all`→ no term; skipped entirely for a Custom section whose own query already restricts by state — negated forms `-state:`/`-is:open|closed|merged` count as "already restricting" too), and the section's qualifier (custom, verbatim, for Custom).
- **`PullRequest(ctx, ref, viewerLogin) (DetailResult, error)`** (implemented, M1b) — one query (`queries/pull_request.graphql`) fetching a pull request's full metadata, reactions, labels, review requests, latest reviews, head-commit status-check rollup (checks), review threads (with their comments), conversation timeline, and the viewer's own pending review (`reviews(author: viewerLogin, states: [PENDING])`, since GitHub has no dedicated field for it — `viewerLogin` is passed in rather than resolved internally, keeping `Client` stateless). `DetailResult{PR model.PullRequest, Warnings []string, RateLimit model.RateLimit}`. Review threads, timeline items, and status-check contexts are three independently paginated connections within that one query; `PullRequest` follows each one's `hasNextPage` by re-issuing the same query with that connection's cursor advanced (the other, already-decoded fields are simply re-read each call — kept simple rather than clever), capping each at 5 additional pages and noting truncation in `Warnings` rather than fetching without bound. A node-scoped GraphQL error under `repository.pullRequest` is handled like search's node-scoped errors (the result is kept, the message surfaces in `Warnings`, deduplicated across pagination rounds — the non-paginated fields, including whatever a persistent error is scoped to, are re-read every round); a review thread, status-check context, or timeline item nulled out by such an error (decoding with every field, including its ID/`__typename`, at the zero value) is dropped the same way search drops an unresolvable node, with an "N … omitted" warning. A null `pullRequest` is `*gh.Error{Kind: KindNotFound}` only when the response carried no GraphQL error at all; when an error caused the null — even one scoped under `repository.pullRequest`, since a non-null child resolver failing (for example a permission error deep in `timelineItems`) propagates the null up to the nearest nullable ancestor, which is `pullRequest` itself — the real error is classified instead, so a transient failure is never misreported as "this pull request does not exist" (a genuine `NOT_FOUND`-typed item still classifies to `KindNotFound`). A failure outside `repository.pullRequest` (for example the repository itself not resolving) always fails the call. The query has no `EnterpriseTeam` inline fragment, for the same GHES-safety reason as `search.graphql`; a `ReviewRequestedEvent`/`ReviewRequestRemovedEvent`'s `requestedReviewer` is narrowed to `User`/`Team` only (a `Bot`/`Mannequin` reviewer on those two timeline events renders as "(removed)" rather than by name). A `StatusContext` (the legacy commit-status API, as opposed to a `CheckRun`) maps its `StatusState` to `model.Check`'s `(Status, Conclusion)` pair using `CheckStatusExpected`/`CheckConclusionError`, which `internal/model` carries specifically for this: `EXPECTED` is that API's own equivalent of "pending", and `ERROR` has no counterpart in the modern `CheckConclusionState` enum. `model.Event.Type` is the GraphQL `__typename` verbatim (for example `"ReviewRequestedEvent"`); `Detail` is a short rendered string for the timeline events that carry more than an actor/timestamp (a label name, a rename, a base-branch change, …), empty otherwise.
- **`ChangedFiles(ctx, ref, page, etag) (FilesResult, error)`** (implemented, M2) — one REST call to `GET /repos/{owner}/{name}/pulls/{number}/files?per_page=100&page={page}`, built against a raw `*http.Client` (`Client.rest`, from `api.NewHTTPClient`, not `api.RESTClient`: the latter's own `Do` helpers turn a 304 into an error, which gprt needs to observe directly) with an `Accept: application/vnd.github+json` header and, when `etag` is non-empty, `If-None-Match: etag`. The REST base URL (`Client.restBase`) reimplements go-gh's own unexported `restPrefix` rule (`https://api.<host>` for github.com-style hosts, `https://<host>/api/v3` for a GHES host, via the exported `auth.NormalizeHostname`/`auth.IsEnterprise`) since `api.NewHTTPClient` has no REST path helper of its own; it deliberately does not special-case go-gh's own `garage.github.com`/`github.localhost` test hosts, and — an accepted limitation, since gprt's own `Options` has no such field today — does not honour a hypothetical `api.ClientOptions.APIHost` override either, deriving the REST endpoint purely from `host`. `FilesResult{Files []model.ChangedFile, ETag string, NotModified bool, HasNext bool, RateLimit model.RateLimit}`: a `304` response is `NotModified: true` with no `Files` (`etag` is still valid) — *unless* `etag` was empty (no `If-None-Match` was ever sent), in which case the `304` is a protocol violation, not a routine "nothing changed", and is reported as a classified error (`KindUnknown`) instead of a silently empty success; a `200` decodes the JSON array (`filename`/`previous_filename`/`status`/`additions`/`deletions`/`sha` mapped directly, `patch` a `*string` so an *absent* key — GitHub omits it for binary/too-large files — is distinguishable from an explicit empty string, the only two conditions that set `HasPatch`); `HasNext` comes from the response's `Link` header (`rel="next"` present in any of its comma-separated segments); `RateLimit` from `X-RateLimit-Remaining`/`X-RateLimit-Reset` (`Known` false when `X-RateLimit-Remaining` is absent). Errors go through the same `classify`, extended with `api.HandleHTTPError(resp)` to turn a non-2xx REST response into the `*api.HTTPError` `classify` already knows how to map.
- **`MentionableUsers(ctx, repo, query, first) ([]model.User, model.RateLimit, error)`** (implemented, M4 data slice; `id` selection added M5) — one query (`queries/mentionable_users.graphql`, GraphQL's `repository(owner, name) { mentionableUsers(query:, first:) { nodes { id login name } } }` — `id` was added in M5 alongside `model.User`'s own new `ID` field, needed by the edit-PR form's reviewers picker to add a brand-new individual reviewer via `RequestReviewers`); `query` is sent as an explicit `null` variable (via `stringVariable`, the same convention `AddThreadReply`'s optional `pendingReviewID` uses) when empty, matching an unfiltered request rather than a literal empty-string search; a null `repository`/`mentionableUsers` (no GraphQL error) is `*gh.Error{Kind: KindUnknown}` — there is no dedicated `KindNotFound` handling here, unlike `PullRequest`'s, since a pull request's own repository not resolving is an unexpected condition this call has no more specific story for. `Store.startMentionableUsersFetch` (see the Store section below) is the only caller; it never paginates beyond the first page.
- **Repository/branch/label/template/team/viewer-repositories reads (implemented, M5 data slice):** `Repository(ctx, repo) (model.RepositoryInfo, RateLimit, error)` (`queries/repository.graphql`, `repository(owner, name){ id defaultBranchRef{name} mergeCommitAllowed squashMergeAllowed rebaseMergeAllowed deleteBranchOnMerge viewerPermission }`; a null `repository` with no GraphQL error at all is `*gh.Error{Kind: KindNotFound}`, mirroring `PullRequest`'s own null-vs-error distinction — `Ref` in the returned `model.RepositoryInfo` is the caller's own input `repo`, not re-derived from the response, since the query has no host to give back). `Branches(ctx, repo, query string, first int) ([]model.Branch, RateLimit, error)` (`queries/branches.graphql`, `repository.refs(refPrefix: "refs/heads/", query:, first:)`; `query` sent as an explicit `null` via `stringVariable` when empty, matching `MentionableUsers`'/`Teams`' own convention; `target { oid }` needs no inline fragment since GraphQL's `GitObject` interface exposes `oid` directly). `Labels(ctx, repo) ([]model.Label, RateLimit, error)` (`queries/labels.graphql`, `repository.labels(first: 100, after:)`, paginated with `after` while `hasNextPage` holds — a repository can have more than 100 labels; the final page's rate limit is returned, and any page's failure discards everything fetched so far, matching `MentionableUsers`' fail-fast behaviour for a simple read). `PullRequestTemplates(ctx, repo) ([]model.PullRequestTemplate, RateLimit, error)` (`queries/pull_request_templates.graphql`, `repository.pullRequestTemplates { filename body }`; `filename` is nullable — GitHub's own root-level `PULL_REQUEST_TEMPLATE.md` template has none — decoding to `""`). `Teams(ctx, org, query string, first int) ([]model.Team, RateLimit, error)` (`queries/teams.graphql`, `organization(login:).teams(query:, first:){ nodes{ id slug name } }`); a user-owned repository's org login has no organization, which GitHub reports as `organization` resolving to null accompanied by a `NOT_FOUND`-typed GraphQL error scoped to the top-level `"organization"` path — confirmed expected, not a failure, so it returns an empty list with no error instead of propagating it (any other GraphQL/HTTP error still fails the call via `classify`, exactly like every other method). `ViewerRepositories(ctx, first int) ([]model.RepositorySummary, RateLimit, error)` (`queries/viewer_repositories.graphql`, `viewer.repositories(first:, affiliations: [OWNER, COLLABORATOR, ORGANIZATION_MEMBER], orderBy: {field: PUSHED_AT, direction: DESC})`; `Query.viewer` itself takes no arguments — `repositories` lives on the `User` type it resolves to) — the create-pull-request repository picker's candidate list, filtered locally by the UI. Every input/payload field name here was confirmed against the live schema via `gh api graphql` introspection, not assumed, and all five read documents were additionally exercised once against this repository (hirano00o/gprt) itself to confirm they parse.
- **Issue-comment mutations (implemented, M3a):** `AddIssueComment(ctx, subjectID, body) (model.IssueComment, model.RateLimit, error)` (`queries/add_comment.graphql`, GitHub's `addComment(input:{subjectId, body})`, reading back `commentEdge.node`); `UpdateIssueComment(ctx, id, body) (model.IssueComment, model.RateLimit, error)` (`queries/update_issue_comment.graphql`, `updateIssueComment(input:{id, body})`, reading back `issueComment`); `DeleteIssueComment(ctx, id) (model.RateLimit, error)` (`queries/delete_issue_comment.graphql`, `deleteIssueComment(input:{id})`, no payload fields besides `clientMutationId`, which gprt never sets). All three input shapes were confirmed against the live schema via `gh api graphql` introspection (`__type(name:"AddCommentInput")` etc.) rather than assumed. `issueCommentNode` mirrors `pull_request.graphql`'s own `IssueComment` timeline fragment field-for-field, mapped by the same `toModel`/`normalizeNewlines`/`toReactionGroups` helpers `pull_request_map.go` uses, so the mutation payload and the detail query decode to identical `model.IssueComment` shapes. Errors go through the same `classify` as every other call — no mutation-specific error mapping exists, since a non-2xx GraphQL response is already a `*api.HTTPError` by the time `classify` sees it (confirmed against `api.GraphQLClient.DoWithContext`'s source: a non-2xx status short-circuits through `HandleHTTPError` before any GraphQL-body decoding happens).
- **Review mutations (implemented, M3b, `internal/gh/review.go`):** `CreatePendingReview(ctx, prID) (model.Review, model.RateLimit, error)` (`queries/create_pending_review.graphql`, `addPullRequestReview(input:{pullRequestId})` with no `event`, which GitHub always creates PENDING); `AddReviewNow(ctx, prID, threads []DraftThread, body) (model.Review, model.RateLimit, error)` and `AddReviewNowWithEvent(ctx, prID, event model.ReviewEvent, body) (model.Review, model.RateLimit, error)` both wrap the same `addPullRequestReview` document (`queries/add_review_now.graphql`) — the former hardcodes `event: COMMENT` with a `threads:` list (single line/range/file comment published immediately), the latter sends an arbitrary `event` with `threads: null` (used by `Store.SubmitReview` when no pending review exists yet, since `addPullRequestReview` both creates and submits in one call whenever `event` is set); `DraftThread{Path, Line, Side, StartLine, StartSide, Body}` maps to `DraftPullRequestReviewThread`, omitting `startLine`/`startSide` when `StartLine == 0` (a single-line comment). `AddReviewThread(ctx, ThreadInput) (model.ReviewThread, model.RateLimit, error)` (`queries/add_review_thread.graphql`, `addPullRequestReviewThread`) — `ThreadInput{PullRequestReviewID, Path, Line, Side, StartLine, StartSide, SubjectType, Body}`, `Line`/`Side`/`StartLine`/`StartSide` sent as GraphQL `null` (via `intVariable`/`sideVariable`) rather than their Go zero value whenever unset, matching a `FILE`-subject thread's omitted line numbers or a single-line thread's omitted range fields; the payload's `thread { … }` selection matches `pull_request.graphql`'s own `reviewThreads` node field-for-field, so it decodes directly into the same private `reviewThreadNode` type and reuses `pull_request_map.go`'s `mapReviewThread`. `AddThreadReply(ctx, threadID, body, pendingReviewID) (model.ReviewComment, model.RateLimit, error)` (`queries/add_thread_reply.graphql`, `addPullRequestReviewThreadReply`; `pendingReviewID` sent as `null` when `""`, for a reply with no pending review) similarly reuses `reviewCommentNode`/`mapReviewComment`. `SubmitReview(ctx, reviewID, event model.ReviewEvent, body) (model.Review, model.RateLimit, error)` (`queries/submit_review.graphql`, `submitPullRequestReview`) submits an *existing* pending review — distinct from `AddReviewNowWithEvent`, which creates one. `DeletePendingReview(ctx, reviewID) (model.RateLimit, error)` (`deletePullRequestReview`), `UpdateReviewComment`/`DeleteReviewComment(ctx, id, …) (…)` (`updatePullRequestReviewComment`/`deletePullRequestReviewComment`, mirroring the issue-comment mutations' shape), and `ResolveThread`/`UnresolveThread(ctx, threadID) (model.ReviewThread, model.RateLimit, error)` (`resolveReviewThread`/`unresolveReviewThread`, payload `thread { id isResolved viewerCanResolve viewerCanUnresolve }` — a dedicated, smaller `threadResolutionNode` than the full shape `AddReviewThread` returns, but including both viewer-can-* flags alongside `isResolved` deliberately: GitHub flips both together with a thread's resolved state (a resolved thread reports `viewerCanUnresolve`, not `viewerCanResolve`, and vice versa), and the store overwrites all three from this payload rather than only `IsResolved` — see the store bullet's `SetThreadResolved`/`applyThreadResolution` entry for why leaving the other two stale caused a real bug) round out the set. `model.ReviewEvent` (`APPROVE`/`REQUEST_CHANGES`/`COMMENT`; GitHub's schema also defines `DISMISS`, which gprt never sends) was added to `internal/model/review.go` for this. Every input/payload field name here was confirmed against the live schema via `gh api graphql` introspection (`__type(name:"AddPullRequestReviewInput")` etc.), not assumed from the plan.
- **Reaction mutations (implemented, M4 data slice, `internal/gh/reaction.go`):** `AddReaction(ctx, subjectID, content model.ReactionContent) ([]model.ReactionGroup, model.RateLimit, error)` (`queries/add_reaction.graphql`, `addReaction(input:{subjectId, content})`) and `RemoveReaction(ctx, subjectID, content) ([]model.ReactionGroup, model.RateLimit, error)` (`queries/remove_reaction.graphql`, `removeReaction(input:{subjectId, content})`) both select the mutation payload's own top-level `reactionGroups` field directly, rather than nesting through `subject { reactionGroups }` (`AddReactionPayload`/`RemoveReactionPayload` expose both, confirmed identical via `gh api graphql` introspection — the top-level field needs one fewer selection level) and reuse `pull_request.go`'s `reactionGroupFragment`/`toReactionGroups`, so the returned groups have the exact shape `PullRequest`'s own `reactionGroups` selection produces. `model.ReactionContent`'s eight values match GitHub's `ReactionContent` enum exactly (confirmed via introspection). `subjectId`/`content` were confirmed against the live schema's `AddReactionInput`/`RemoveReactionInput`, not assumed.
- **PR edit/merge/create mutations (implemented, M5 data slice, `internal/gh/pr_edit.go`, `pr_merge.go`, `pr_create.go`):** `UpdatePullRequest(ctx, id string, in UpdatePullRequestInput{Title, Body, BaseRefName *string; LabelIDs *[]string}) (model.PullRequest subset: Title, Body, BaseRefName, Labels, UpdatedAt, RateLimit, error)` (`queries/update_pull_request.graphql`, `updatePullRequest(input:{pullRequestId, title, body, baseRefName, labelIds})`) — a nil pointer field is sent as an explicit GraphQL `null`, meaning "leave unchanged" (`stringPtrVariable`), matching the optional-variable convention `review.go`'s `intVariable`/`stringVariable` established; `LabelIDs` is `*[]string` specifically so a non-nil, empty slice ("clear every label") is distinguishable from nil ("don't touch labels"). `RequestReviewers(ctx, id string, userIDs, teamIDs []string, union bool) ([]model.Reviewer, RateLimit, error)` (`queries/request_reviewers.graphql`, `requestReviews(input:{pullRequestId, userIds, teamIds, union})`; its `pullRequest { reviewRequests(first: 20) {...} }` payload selection matches `pull_request.graphql`'s own field-for-field, so it decodes directly into the shared `reviewRequestNode` type and reuses `mapReviewer`). `MarkReadyForReview(ctx, id) (isDraft bool, RateLimit, error)` / `ConvertToDraft(ctx, id) (isDraft bool, RateLimit, error)` (`queries/mark_ready_for_review.graphql`/`convert_to_draft.graphql`, `markPullRequestReadyForReview`/`convertPullRequestToDraft`, each taking only `pullRequestId` — confirmed via introspection that neither input has any other field — and returning the server's own post-toggle `isDraft` rather than assuming success). `MergePullRequest(ctx, id string, method model.MergeMethod, commitHeadline, commitBody *string, expectedHeadOID string) (model.PullRequest subset: State, Merged, MergedAt, RateLimit, error)` (`queries/merge_pull_request.graphql`, `mergePullRequest(input:{pullRequestId, mergeMethod, commitHeadline, commitBody, expectedHeadOid})`; `commitHeadline`/`commitBody` sent as explicit `null` when nil, letting GitHub fill in its own default commit message; `model.MergeMethod` (`MERGE`|`SQUASH`|`REBASE`) matches GraphQL's `PullRequestMergeMethod` enum exactly, confirmed via introspection). `ClosePullRequest(ctx, id) (model.PRState, RateLimit, error)` / `ReopenPullRequest(ctx, id) (model.PRState, RateLimit, error)` (`queries/close_pull_request.graphql`/`reopen_pull_request.graphql`, `closePullRequest`/`reopenPullRequest`, each `pullRequestId`-only, returning the server's post-toggle `state`). `CreatePullRequest(ctx, in CreatePullRequestInput{RepositoryID, BaseRefName, HeadRefName, Title, Body, Draft}) (model.PullRequest subset: ID, Ref, URL, RateLimit, error)` (`queries/create_pull_request.graphql`, `createPullRequest(input:{repositoryId, baseRefName, headRefName, title, body, draft})`; the returned `Ref`'s host comes from `Client.Host()`, not the payload, which only carries `repository.nameWithOwner`). Every mutation payload here exposes only `{clientMutationId, pullRequest}` (confirmed via introspection — no richer per-mutation shape exists), and every input/payload field name was confirmed against the live schema, not assumed.
- Queries live in `internal/gh/queries/*.graphql` (embedded via a single `embed.FS`), loaded once per document (`sync.OnceValue`) and decoded into private response structs (`internal/gh/map.go`) before being mapped into `model`; a query field selected for future use but not yet mapped to a model field (for example `isCrossRepository`) is simply left out of the decoding struct rather than added to `model.PullRequest` early.
- Errors: `*gh.Error{Kind: Auth|RateLimited|NotFound|Validation|Network|Server|Unknown, Message, RetryAfter, Err}` implements `Error()`/`Unwrap()`. `classify(err) error` maps a `*api.HTTPError` by status code (401→Auth; 403 with `X-RateLimit-Remaining: 0` or `Retry-After` present→RateLimited with `RetryAfter` from `Retry-After` seconds or `X-RateLimit-Reset`; 403 otherwise→Auth; 404→NotFound; 422→Validation; 5xx→Server), a `*api.GraphQLError` by its first recognised item `Type` (`NOT_FOUND`→NotFound, `RATE_LIMITED`→RateLimited, `FORBIDDEN`/`INSUFFICIENT_SCOPES`→Auth, `UNPROCESSABLE`→Validation — the GraphQL-level shape of a validation failure, an HTTP 200 whose `errors` array carries this type, as opposed to a plain HTTP 422 with a `message`-only body — else Unknown with every item's message joined), a `net.Error`/`*url.Error`→Network, and passes `context.Canceled`/`context.DeadlineExceeded` through unchanged (wrapping them would add an `Unwrap` hop for no benefit).
- **GraphQL is primary** (search, PR detail with `reviewThreads`/`comments`/`reviews`/`statusCheckRollup`, all mutations). **REST** is used only for `/pulls/{n}/files?per_page=100` (patches, ETag; ≤3000 files; `patch` absent for binary/huge files). GraphQL has no ETag; REST 304s are free. go-gh's built-in cache stays **off** (it is TTL-only and caches 404/422 and GraphQL POSTs, which is wrong for gprt's needs).
- Viewer's pending review: `reviews(first: 1, author: $login, states: [PENDING])`. Only one pending review per user per PR; while it exists, every new comment/reply must attach to it (`pullRequestReviewId`), matching GitHub's own UI, which hides "single comment" in that state.
- `addPullRequestReview` without `event` creates a PENDING review; with `event: COMMENT` + `threads:` publishes immediately. `DraftPullRequestReviewThread` has no `subjectType`, so file-level comments always go through `addPullRequestReviewThread(subjectType: FILE)` on a pending review.
- Comments must target lines inside a hunk; file-level comments omit `line`; multi-line comments use `startLine`/`startSide`.
- `requestReviews(union: false)` replaces the reviewer set. Draft toggle: `markPullRequestReadyForReview` / `convertPullRequestToDraft`. Reactions: `addReaction`/`removeReaction(subjectId, content)` (implemented, M4 data slice).
- Mention candidates: `repository.mentionableUsers(query:, first: 100)` (implemented, M4 data slice); teams: `organization.teams(query:)`; templates: `repository.pullRequestTemplates`; branches: `repository.refs(refPrefix: "refs/heads/", query:)`.
- Search: 30 req/min, 1000 results max; qualifiers `type:pr archived:false sort:updated-desc` plus a section qualifier; multiple `repo:` in advanced search must be grouped `(repo:a OR repo:b)`. GraphQL budget is 5000 points/hour; every query selects `rateLimit { remaining resetAt }`.
- Section queries de-overlap with negations: `user-review-requested:@me`; `review-requested:@me -user-review-requested:@me`; `author:@me -review-requested:@me`; `involves:@me -author:@me -review-requested:@me`; dedupe by ID stays as a safety net regardless. Custom sections are appended verbatim (the `(repo:a OR repo:b)` grouping rule is documented for users, not enforced).

## Cache (`internal/cache`) — store implemented, ETag/SWR wiring planned

- Layout: `<cache dir>/v1/<host>/<login>/repos/<owner>/<repo>/pr-<n>/<sha256(rest)>.json`, `v1/<host>/<login>/repos/<owner>/<repo>/<sha256(rest)>.json` (repository-scoped, not tied to one pull request — implemented M4 for mentionable users; see `RepoKey`/`repoDir` below), and `v1/<host>/<login>/search/<sha256>.json`. `Entry{Body, ETag, FetchedAt}`; path segments outside `[A-Za-z0-9._-]` (including `""`, `.`, `..`) are replaced with `"=" + hex(segment)` — the `=` prefix is outside the safe character class, so an escaped segment can never collide with a literal one, and an empty segment can never disappear via `filepath.Join` and collide two different keys onto the same path. The fixed `repos` segment keeps the PR tree disjoint from the `search` tree at the same level: without it, a repository literally owned by an account named "search" would land under `.../<login>/search/...`, and `InvalidateSearch`'s `os.RemoveAll` would delete that owner's PR caches along with the search cache. A repository-scoped entry is a deliberate sibling of that same repository's `pr-<n>` subdirectories, not a conflict: its SHA-256-hashed filename never collides with a `pr-<n>` directory name, and there is no `InvalidateRepo` today (nothing yet needs to purge a repository-scoped entry independently of the whole cache directory).
- `Store` serialises `Get`, `Put`, and `invalidateDir` (used by `InvalidatePR`/`InvalidateSearch`) behind a single mutex held across each call's entire body, including its disk I/O, not just the in-memory map: `Store.Get(k) (Entry, bool, error)` checks memory then falls back to disk, and `Store.Put(k, e) error` — after rejecting `e` if its `Body` is nil or its `FetchedAt` is zero (the same two conditions `readDiskEntry`, below, treats as corruption, so `[]byte{}` is a valid non-nil body but a zero-value `Entry` is not) — marshals `e`, then takes the lock and updates memory and writes to disk together. This closes two races: a `Get` reading a file `invalidateDir` is mid-way through deleting could otherwise write the stale result back into memory, and a `Put` in flight during an invalidation could otherwise write its file after the invalidation's `RemoveAll` and resurrect the directory it just deleted (`writeAtomic`'s temp-file-then-rename means a concurrent `Get` can never observe a half-written file at the destination path, so that is not a separate risk). Coarser than a per-key scheme, an accepted trade-off given gprt is a single-user CLI touching small JSON files.
- A missing file is `(Entry{}, false, nil)`. A corrupt file — invalid JSON, or JSON that decodes but has a nil body or a zero fetch time (as a truncated write might produce) — is also `(Entry{}, false, nil)` and is deleted so it does not keep failing on every lookup; if the deletion itself fails, that error is returned instead. Any other read error (for example a permission error) is returned as-is. Disk writes are atomic (temp file + rename). Directories are created mode `0700`, files mode `0600`; no request headers are persisted.
- `InvalidatePR(host, login, ref) error` removes the PR's on-disk directory and the matching memory entries; `InvalidateSearch(host, login) error` does the same for the search namespace. Neither touches unrelated hosts/logins/PRs. Both return the `os.RemoveAll` error instead of swallowing it, since a failed removal would otherwise let a stale disk entry resurface on a later `Get`. Both delegate to shared `prDir`/`searchDir` helpers so the on-disk layout is defined in one place, alongside `Store.path`.
- `Key` should be built with `PRKey(host, login, ref, rest) (Key, error)`, `RepoKey(host, login, repo, rest) (Key, error)` (implemented M4), or `SearchKey(host, login, rest) (Key, error)` rather than a struct literal: all three validate the fields that become on-disk path segments (non-empty host/login; for `PRKey`, also a non-empty repo owner/name and a positive PR number; for `RepoKey`, a non-empty repo owner/name, with no PR number at all). At most one of `Key.PR`/`Key.Repo` is ever set.
- GraphQL stale-while-revalidate is wired for the list (M1a): `internal/store` caches each section's page-1 result under `SearchKey(host, login, query+"\x00")` (only page 1: nothing ever reads a `LoadMore` page back) and the viewer lookup under `SearchKey(host, "-", "viewer")` (a placeholder login, since the real login is not known until that lookup itself completes — this also lets a later run's cache-first viewer read seed the login synchronously, before the network viewer fetch returns, so per-section cache reads on that same call can use it). `LoadList(false)` shows the cached page-1 entry immediately, marked stale, while a network refetch runs; `LoadList(true)` and `Refresh` (the auto-refresh ticker) skip that cache-first read. `Reload` (the `R` key) additionally calls `cache.InvalidateSearch(host, login)` before refetching, so a later `LoadList(false)`'s cache-first read can never resurrect the data `Reload` was asked to discard; `Refresh` does not invalidate, since a routine background refresh has no reason to believe the cache is wrong, only that it might be a few minutes old. A cache-key or marshal failure during a read or write is swallowed rather than propagated (caching here is a best-effort optimisation, not required for correctness, and a missing login before the viewer resolves is the expected, harmless case that triggers this path on a first-ever run), but a genuine I/O error from `Get`/`Put` is logged once per Store via `Logger.Warn` so a persistently broken cache is at least visible in the debug log file when `--debug` is on — the `:messages` ring buffer keeps only `slog.LevelError` and above, so a `Warn`-level entry never reaches it. Section cache writes are additionally gated on the viewer being network-confirmed (see the Store section below), so a page fetched while a cache-seeded login is still unconfirmed is never written under a login that turns out to be wrong. The current pull request's detail (M1b) follows the identical stale-while-revalidate shape, one level down: `internal/store` caches it under `PRKey(host, login, ref, "detail")`. `OpenPR` shows that cached entry immediately, marked stale, while a network refetch runs (mirroring `LoadList(false)`'s section cache-first read); `RefreshPR` (the auto-refresh ticker) and `ReloadPR` (the `R` key, via `Reload`) both skip that cache-first read, and `ReloadPR` additionally calls `InvalidatePR` first, for the same reasons `Refresh`/`Reload` do for the list. The write is gated on `viewerConfirmed` the same way section pages are. A repository's mentionable users (M4) follow the same stale-while-revalidate shape one level up, keyed by repository rather than by pull request: `internal/store` caches the list under `RepoKey(host, login, repo, "mentionable-users-v2")` (bumped from `"mentionable-users"` when `model.User` gained an `ID` field, M5 — an old, still-cached entry decodes fine but every user in it would silently have an empty `ID` until the next network refetch, so the rest segment name itself changed rather than adding a staleness check to every read path) with a 1-hour freshness rule (`mentionableUsersFreshFor`) applied to *both* the in-memory result and the disk entry — a fresh one of either (`Now().Sub(FetchedAt) < 1h`) is applied (or kept) with no network call at all; a stale one is applied immediately and a background refetch starts right away. Unlike every other cached entry, a fresh in-memory result also skips the disk read entirely (checked first, see the Store section below), and the read itself is skipped whenever a fetch for that repository is already in flight (`loading`) — but it is *not* a one-shot "read once, never again" cache: a repository a previous fetch failed for is retried the next time `OpenPR` opens a pull request in it, and `ReloadPR` (the `R` key) forces a fresh read/fetch regardless of any freshness at all. A repository's metadata (M5: `RepositoryInfo`/`Labels`/`PullRequestTemplates`, loaded together) reuses `RepoKey` the identical way, under a sibling `"metadata"` rest segment (`RepoKey(host, login, repo, "metadata")`) rather than a new cache-layout concept; the viewer's own repositories (M5, the create-PR repo picker) instead reuse `SearchKey(host, login, "viewer-repositories")`, since that result is scoped to the viewer's login alone, matching a search/list result rather than a repository- or PR-scoped one — no new `internal/cache` helper was needed for either.

REST reads (implemented, M2, for changed files — see `internal/store`'s "Files" bullet below): send `If-None-Match`; a `304` keeps the cached body, a `200` replaces it. After any mutation on a PR (planned): `InvalidatePR` then refetch.

**Open items:** the in-memory map and on-disk tree are unbounded (no LRU eviction, no pruning of old entries at startup). Deferred to M2, when REST file patches start entering the cache and unbounded growth becomes worth paying for.

## Store / service (`internal/store`) — PR list, PR detail, and changed-files data implemented (M1a, M1b, M2 data slice); comment mutation queue implemented (M3a data slice); pending review + review-thread mutations implemented (M3b data slice); reactions and mentionable users implemented (M4 data slice); repository metadata, viewer repositories, on-demand branch/team search, and PR edit/merge/create mutations implemented (M5 data slice); UI-facing drafts wiring remains the UI's own concern

- `type GitHub interface { Viewer(ctx) (model.User, model.RateLimit, error); SearchPullRequests(ctx, query, cursor string) (gh.SearchResult, error); PullRequest(ctx, ref model.PRRef, viewerLogin string) (gh.DetailResult, error); … (grown per milestone: files, issue-comment and review mutations, AddReaction/RemoveReaction, MentionableUsers, and — M5 — Repository/Branches/Labels/PullRequestTemplates/Teams/ViewerRepositories reads plus UpdatePullRequest/RequestReviewers/MarkReadyForReview/ConvertToDraft/MergePullRequest/ClosePullRequest/ReopenPullRequest/CreatePullRequest mutations) }` — the consumer-side subset of `*gh.Client` the store depends on; tests substitute a fake in the same package. `Deps{GitHub, Cache *cache.Store, Dispatch func(func()), Logger, Config, Host, Now func() time.Time}`; `New(deps) *Store` builds the section list (see below) but starts no network activity until `Start(ctx)`.
- All fields are owned by the UI goroutine; no mutex. Goroutines receive `ctx` plus snapshot arguments (section index, cursor, generation token) and never touch the store directly. Results come back only through `Dispatch`.
- Sections: the four built-ins (`DirectReview` "Review requested", `TeamReview` "Team review requested", `Mine` "My pull requests", `Involved` "Involved") followed by one `Custom` section per `config.List.Sections`, in that fixed order — this order is also the priority order `Rows` uses for cross-section deduplication. Each section's search query is built via `gh.BuildSearchQuery` against the store's current list state (`config.List.State` initially) and rebuilt whenever `SetFilter` changes that state. Each section tracks its own items, cursor, `hasNext`, total, loading flag, stale flag, and last error.
- `Start(ctx)`: applies any cached viewer synchronously (a local cache read, not a network call — see the Cache section above for why this must happen before any section cache read), starts a network refresh of the viewer without waiting for it, then calls `LoadList(false)`. `Stop()` cancels the current list context and the current pull request's in-flight detail fetch, if any (it leaves `current`/`currentPR`/`DetailState` untouched — only `ClosePR` clears those).
- Viewer confirmation: a login applied from cache by `applyCachedViewer` is a guess, not a fact — `viewerConfirmed` stays false until the network resolves it at least once. If the confirmed login differs from a seeded one (for example after `gh auth switch` between runs), every section's items are discarded (`discardAllSectionItems`, which also emits `EventListChanged` immediately so the UI drops the wrong rows without waiting for an unrelated event) and a full, cache-skipping `LoadList(true)` runs, so nothing from the wrong account lingers on screen or survives into the reload; the currently open pull request's detail (M1b), if any, is discarded the same way (its viewer-scoped fields — `PendingReview`, `ViewerCanUpdate`/`Close`/`Reopen`/`React` — could otherwise belong to the wrong account) and `ReloadPR` (invalidate + refetch) runs for it. When the viewer resolves *without* a mismatch (the common case: the login was simply unknown until now, for example because `OpenPR` was called before `Start`'s own viewer fetch resolved) and a pull request is open, its detail fetch is unconditionally restarted (`startDetailFetch`, not `RefreshPR`, is called directly: `RefreshPR` itself no-ops while a fetch is already in flight, by design, for the auto-refresh ticker's sake, but an in-flight fetch at exactly this moment is very likely the pull request's own first fetch — started under the stale/empty login, the one that most needs restarting) so its pending-review lookup and viewer-scoped flags reflect the now-known login rather than whatever they were fetched with (possibly an empty `$viewer`); the superseded fetch's eventual result is dropped by the generation check like any other. `cacheSectionPage` refuses to write until `viewerConfirmed` is true, so a section fetched during the unconfirmed window is never cached under a login that turns out to be wrong. If the login is still unknown ("") when `startList` runs and no viewer fetch is currently in flight (`viewerFetchInFlight`), it starts another one, using `baseCtx` (not this generation's list context) so a later generation cancelling the list context does not also cancel — and falsely error-report — an otherwise-healthy viewer retry; a transient viewer failure would otherwise leave every section's cache reads/writes silently disabled (both log at Debug when skipped) for the rest of the session.
- Fetch pattern: `fetchSection(ctx, gen, i, cursor)` registers an in-flight key `{section, cursor}` (a duplicate call for the same key is a no-op) → a goroutine calls `GitHub.SearchPullRequests(...)` and, via a single deferred closure that recovers a panic into the result's `err` (so a panic still reaches the same apply path instead of leaking the in-flight registration and `loading` flag forever) and computes `cancelled := ctx.Err() != nil`, dispatches: check `gen == current` **first**, and only then unregister the in-flight key and apply the result — checking the generation before unregistering means a late, dropped result from a superseded generation can never erase the *current* generation's own in-flight entry for the same key (which would otherwise open a window for a duplicate fetch to slip past the dedup check). `fetchViewer` follows the identical single-deferred-closure shape for the same reason. `cancelled` (not `errors.Is(err, context.Canceled/DeadlineExceeded)`) is what `applyFetchResult`/`applyViewerResult` use to decide whether a failure was *our own* cancellation (Stop, or a superseded generation) and therefore silent: go-gh's underlying `http.Client{Timeout: ...}` produces an error that also satisfies `errors.Is(err, context.DeadlineExceeded)` on a plain request timeout unrelated to `ctx` ever being cancelled, so only `ctx.Err()` — asking whether *we* gave up — tells the two apart; a real timeout on an otherwise-healthy `ctx` is reported like any other error. `LoadList(force bool)` (`!force` shows a cached page-1 first, marked stale), `Refresh` (background re-fetch, never re-shows a cached page since sections already hold live items, and never invalidates the on-disk cache), and `Reload` (invalidates the on-disk search cache for the current login and marks every section stale before behaving like `LoadList(true)`, so its incoming page 1 replaces outright rather than chaining — see below; used by the `R` key) all start a new generation, cancel the previous list context, and clear the in-flight map — clearing it (rather than leaving a superseded generation's entries to expire on their own) lets the new generation's fetches start immediately instead of being dedup-blocked by an old, still-running fetch for the same (section, cursor); `LoadMore(sectionIndex)` fetches the next page under the current generation/context when `hasNext` and not already loading.
- A failed fetch keeps the section's previous items, records the error on both the section and the store (via `recomputeLastErr`, see below), and emits `EventError` — **except** when the failure is our own cancellation (`cancelled`, see the fetch-pattern bullet above), which is silent: no `lastErr`, no `EventError`, just the usual `loading`/in-flight cleanup (this also resets `refreshTargetPages` to 0, stopping any in-progress refresh-chain). The same silence applies to `fetchViewer`/`applyViewerResult`: a cancelled viewer fetch sets neither `viewerLastErr` nor emits `EventError` either. A successful page-1 fetch (`cursor == ""`) always replaces the section's items outright — a PR no longer present in the new page 1 must actually disappear from the list, not linger from a previous fetch — except that when the section was **not** just confirming a stale cache-shown preview for the first time (see `applyCachedFirstPage`) and it previously had more than one page loaded (`sectionState.loadedPages`) and the new page 1 still `HasNextPage`, the store sets `refreshTargetPages` to that previous depth and automatically chains fetches for pages 2..N (each appended with ID-deduplication against what is already held, and its own warnings appended rather than replacing page 1's — see below) to restore the section to its previous depth against fresh data, stopping early on an error or once `HasNextPage` goes false. If a *new* generation starts (another `Refresh`/`Reload`/`LoadList`) while a chain is still mid-flight, `startList` restores `loadedPages` from the abandoned `refreshTargetPages` first (when it is larger) before resetting `refreshTargetPages` to 0 and starting the new generation's own page-1 fetch: without this, the new generation would compute its chain target from the interrupted chain's partial page count instead of the section's true previous depth, permanently shrinking it. `discardAllSectionItems` also zeroes both fields, so a login-mismatch reset does not inherit the wrong account's page depth. A later page (`cursor != ""`, whether from `LoadMore` or an automatic chain) is appended with the same ID-deduplication and is intentionally never cached, since only the page-1 cache key is ever read back; page 1 is cached (subject to the viewer-confirmation gate above) after every page-1 apply. Every apply then updates cursor/hasNext/total and clears stale.
- `lastErr` (`LastError()`) is never assigned directly: `recomputeLastErr` derives it from persistent per-source state, in priority order — a dedicated `panicErr` if set (from `recoverGoroutine`, cleared only when the next list generation starts via `startList`, not by an unrelated fetch succeeding in the meantime), else `viewerLastErr` if set, else `detailErr` (the open pull request's own standing detail error, ranked above section errors because the open pull request is what the user is looking at), else the first section (in priority order) with a standing `lastErr`, else nil — and is called after every viewer fetch, section fetch, detail fetch, or recovered-panic outcome, and directly from `OpenPR`/`ClosePR`, which clear `detailErr` themselves. This was originally a plain "last write wins" field set inline at each call site (including directly inside `recoverGoroutine`), which raced: the viewer fetch, each section's fetch, and a recovered goroutine panic are independent, uncoordinated sources dispatching onto the same channel with no ordering guarantee, so (caught only by `go test -count=3`, not a single run) an unrelated success could dispatch after, and silently clear, a genuine standing error from a different source.
- `sectionState.warnings` (surfaced via `SectionStates`, see below) follows the same "page 1 is authoritative, later pages only add to it" rule as items: a page-1 apply replaces `warnings` outright with that page's `Warnings`, while a later page (`LoadMore` or a chain page) appends its own `Warnings` with string-deduplication instead of overwriting — otherwise a clean chained page 2 would silently erase whatever page 1 had warned about.
- `LastRefresh()` updates only once every section's page-1 fetch within one generation has *succeeded*: `pendingPageOne` starts at `len(sections)` in `startList` and counts down as each page-1 result (not `LoadMore`, not an automatic refresh-chain page) resolves via `notePageOneOutcome`; `generationHadError` latches true on any page-1 failure in that generation, suppressing the update even though `pendingPageOne` still reaches zero.
- Cache I/O failures: a `Get`/`Put` error (as opposed to a normal cache miss) is logged via `Logger.Warn("cache read/write failed", "err", err)` at most once per Store (`cacheWarned`), so a persistently broken cache does not spam the log on every fetch; this reaches the debug log file when `--debug` is on, not `:messages` (its ring buffer keeps only `slog.LevelError` and above — see `internal/logging.Recorder`).
- `gh.SearchResult.Warnings` (data that could not be fully resolved on a page, but did not fail it — see the GitHub client section above) is kept per section and surfaced via `SectionStates() []SectionState{Section, Loading, Stale, HasNext, Total, Err, Warnings}`; each distinct (section, warning message) pair is also logged once via `Logger.Warn` (same `:messages` caveat as cache failures above), so a warning that persists across refreshes is not re-logged every time.
- Refresh: `StartAutoRefresh(ctx, interval)` runs a `time.Ticker` goroutine whose only action is `Dispatch(func(){ store.Refresh(); store.RefreshPR() })`; it stops when `ctx` is done. `RefreshPR` is a no-op when no pull request is open. Wiring the ticker to a real `refresh_interval` in `cmd/gprt`, and the UI to `OpenPR` when a pull request is selected, are the M1b UI slice's work.
- `Rows() []Row` (`Row{Kind Header|Item, Section, Item model.ListItem, Stale}`): items are deduplicated across sections by PR ID, keeping the section that appears first in priority order; the current filter (see below) is applied to each section's claimed items; remaining items are sorted by `UpdatedAt` descending; a section left with no items after filtering is omitted entirely, including its heading.
- Filter (`filter.go`, pure and independently tested): `SetFilter(text)` parses `repo:`/`author:`/`reviewer:`/`label:`/`state:` qualifiers (case-insensitive value matching except free text tokens, which must all match) plus free text matched against title, `#number`, `owner/name`, and author login. Omitting `state:` reverts the search state to `Config.List.State` rather than leaving it at whatever a previous `SetFilter` call last set — `"state:closed"` followed later by `"author:alice"` shows open PRs filtered by author, not closed ones. An unrecognised state value is ignored for search-triggering purposes (the raw text is still stored, so `Filter()` and every other qualifier in the same string still take effect) and reported via `EventError`. When the resolved state does change, every section's query is rebuilt, every section is marked stale (so `Rows` shows the old data as stale immediately rather than looking frozen until the new fetch lands), and a full `Reload` runs.

- `StartAutoRefresh`'s ticker goroutine (which has no fetch result of its own to apply on a panic) defers `recoverGoroutine(op)` directly (never wrapped in a closure, so `recover` inside it is "called directly by a deferred function" as the language requires); a recovered panic is logged and dispatched as `EventError` instead of crashing the process. `fetchSection`/`fetchViewer` recover inline instead, as described above, since they must always dispatch their (possibly panic-derived) result through one path.
- **Current PR / detail state (implemented, M1b, data side only — no UI yet):** `current *model.PRRef` (the pull request `OpenPR` last opened, or nil) and `currentPR *model.PullRequest` (its most recently applied detail, from cache or the network) are Store fields alongside the list's `sections`. `CurrentRef() (model.PRRef, bool)`, `CurrentPR() *model.PullRequest`, and `DetailState() DetailState{Loading, Stale bool; Err error; Warnings []string; FetchedAt time.Time}` are the read-only accessors the UI slice renders against.
  - `OpenPR(ref)`: sets `current`, discards any previously held `currentPR` (a stale detail for a *different* pull request must never linger under the new ref), applies a cached detail immediately if one exists (`cache.PRKey(host, login, ref, "detail")`, marked `Stale`), then starts a network fetch under a new generation (`detailGen`, incremented; the previous generation's context is cancelled). A successful fetch replaces `currentPR`, clears `Stale`, records `Warnings`/`FetchedAt`, and writes the cache (gated on `viewerConfirmed`, like section pages); a failed fetch keeps the previous `currentPR`, sets `DetailState().Err`, and emits `EventError` — except our own cancellation (a later `OpenPR`/`ReloadPR`/`ClosePR` superseding this generation, or `Stop`), which is silent, exactly like a superseded section fetch.
  - `RefreshPR()`: like `Refresh`, skips the cache-first read (the store already holds live data, if any); also a no-op when nothing is open or a detail fetch is already in flight.
  - `ReloadPR()`: invalidates the pull request's on-disk cache entry (`cache.InvalidatePR`) before re-fetching, and marks the existing detail `Stale` first so the UI does not look frozen while the fetch is in flight; a no-op when nothing is open. `Reload()` (the `R` key) now calls `ReloadPR()` in addition to reloading the list.
  - `ClosePR()`: cancels any in-flight detail fetch (bumping `detailGen` so a late result is dropped, silently) and clears `current`/`currentPR`/`DetailState()` back to their zero values.
  - Fetch pattern: a single-slot in-flight flag (`detailFetchInFlight`) — not a map keyed like the list's `inFlight`, since there is only ever one "current" pull request — registered/cleared on the UI goroutine; the goroutine itself follows the same single-deferred-closure shape as `fetchSection`/`fetchViewer` (`go func(){ res, err = GitHub.PullRequest(ctx, ref, login); defer recover-into-err; dispatch(func(){ if gen != detailGen { return }; clear in-flight; apply(res, err, cancelled) }) }()`), checking the generation before clearing the flag for the identical reason `fetchSection` does.
- **Changed files (implemented, M2, data side only — no UI yet):** `files []FileEntry` (`FileEntry{id int, File model.ChangedFile, Hunks []diff.Hunk, ParseErr error, Tokens [][][]highlight.Token, Highlighted bool}`, hunk → line → tokens, `nil` until a hunk's highlight job applies) holds every page fetched so far for the current pull request, in page order; `filesPageLens` records each page's length within it so a later network result for an already cache-shown page can replace exactly that slice (`replaceFilesPage`) without disturbing the others. Each `FileEntry` gets a store-unique `id` (`assignFileEntryIDs`, a monotonic counter) the moment it is appended or replaces a page: highlight jobs and results carry this `id`, not `File.Path`, specifically so a job still in flight for an entry `replaceFilesPage` has since replaced (same path, fresh network content) can never be misapplied to its replacement — `applyHighlightResult` looks up by `id` and silently discards a miss, while `replaceFilesPage` itself proactively subtracts a replaced entry's own remaining pending count from both `filesHighlightPending` and `filesPendingByID` (keyed by `id`), so `FilesState().Highlighting` never permanently overstates outstanding work for an entry that no longer exists.
  `LoadFiles(force bool)` behaves in three ways depending on the pull request's own load state. If its detail has not resolved yet (`CurrentPR()` still nil, so there is no `HeadOID` to key a generation on), the call is remembered (`filesWanted`) rather than dropped: `applyDetailResult`'s success path starts the deferred load once a `HeadOID` becomes known. Otherwise, with `force == false`, a call is a no-op once a load for that `HeadOID` has started (`filesStarted && filesHeadOID == headOID`) — *unless* a standing error exists and nothing is currently loading, in which case it resumes the sequence from the next unfetched page (`resumeFilesFetch`, `filesPagesLoaded+1`) under the *same* generation, rather than either silently no-op'ing forever or discarding the pages already loaded. Otherwise it starts a new files generation (`filesGen`, cancelling the previous one's context and highlight pool) that fetches pages sequentially from 1 while `HasNext` holds; it also records the pull request's `ChangedFiles` count at that moment (`filesChangedFilesAt`), used by the reload coupling below.
  `force` (`!force` is `LoadFiles`'s own `showCache`) also gates each page's cache read, exactly like `LoadList`'s: a cached page (`cache.PRKey(host, login, ref, "files/page-<n>")`, body = JSON `{files, has_next}`, `Entry.ETag` round-tripped as `If-None-Match`) is applied immediately as stale, then that same page's own network fetch confirms it (`304`, keeping the cached content) or replaces it (`200`, caching the fresh page under the viewer-confirmation gate other caches use); parsing (`diff.Parse` + `diff.ExpandTabs` with `Config.TabWidth`) happens in the fetch goroutine (pure), and its result is dispatched and applied under the generation like every other fetch here — every emit along the way (`EventFilesChanged`/`EventRateLimitChanged`/`EventFilesLoadingChanged`, including the 304 and error paths, both of which now also emit `EventFilesChanged`) is followed by a fresh `gen == filesGen` check before the function continues mutating generation-scoped state or fetching the next page, since a synchronous subscriber may call `OpenPR`/`ClosePR` from inside it. `ref`/`Config.TabWidth` are snapshotted *before* that emit, not after, for the same reason. `res.RateLimit` only overwrites the store's standing rate limit when `Known`. `FilesState().Stale` is a single store-wide flag rather than per-page, which is sound only because pages are fetched strictly sequentially (page *n*+1 is never requested before page *n*'s own fetch has resolved): it goes true the moment any page is shown from cache and false the moment that same page's fetch resolves, so at most one page is ever "shown but unconfirmed" at a time - including when that resolution is a failure: a cache-shown page whose own confirmation fails is discarded outright (`discardCachedPage`, restoring `filesPagesLoaded`/`Stale` as if that page had never been applied), so `resumeFilesFetch`'s next attempt re-fetches that exact page rather than skipping to the one after it and later marking the never-confirmed content as settled once that next page happens to succeed. `startFilesFetch` calls `recomputeLastErr` immediately after `resetFiles` clears `filesErr`, so `LastError()` reflects a vanished files error right away rather than waiting for page 1's own outcome. A parse error is kept per file (`FileEntry.ParseErr`, logged at Warn with its path — GitHub returning a patch `internal/diff` cannot parse is most likely gprt's own bug) without affecting any other file on the same page. Once `HasNext` goes false, `checkFilesTruncation` compares the number of files actually loaded against the pull request's own `ChangedFiles` count and records a `FilesState().Warnings` entry on a mismatch (GitHub's REST files endpoint caps at 3000; a base-branch advance between page fetches can also shift the count without changing `HeadOID`).
  Highlighting: `startHighlightPool` starts one feeder goroutine plus a pool of 2 worker goroutines per files generation, sharing a `*highlight.Highlighter` (safe for concurrent use across the pool — see `internal/highlight`). The UI goroutine never sends directly on the workers' own channel: `enqueueHighlightJobs` only ever pushes onto a mutex-protected, unbounded `highlightQueue` and sends a non-blocking, coalescing wake signal, so it can never block regardless of how backed up the pool is. `highlightFeeder` is the only goroutine that drains `highlightQueue` and forwards jobs (one per hunk, `highlightJob{fileID, path, hunkIndex, lines}`) onto the bounded worker channel, blocking *itself* (never the UI goroutine) when that channel is full. This indirection exists because the UI goroutine blocking on a full worker channel while every worker is itself blocked in `Dispatch` waiting for the UI goroutine (`Dispatch` is `app.QueueUpdateDraw` in production, which blocks until the UI goroutine runs the queued function) would deadlock the whole application. Each highlight result is dispatched as `(gen, fileID, hunkIndex, tokens)` — a `highlight.Lines` error is logged at Debug, not silently discarded, and reported as "no highlighting" either way — and applied (`applyHighlightResult`) only if `gen == filesGen` still holds, decrementing a per-`id` pending count (`filesPendingByID`) that flips `FileEntry.Highlighted` true once it reaches zero. A file with no patch, a parse error, or zero hunks has nothing to highlight and is marked `Highlighted` immediately, with no job ever enqueued for it. `Stop`, `PR switch (OpenPR)`, and `close (ClosePR)` all cancel `filesCancel`'s context — shared by the page-fetch chain and the highlight pool for one generation, so one cancellation stops both — and `OpenPR`/`ClosePR` additionally call `resetFiles`, which bumps `filesGen`; a highlight job whose ctx is already done when it finishes never dispatches at all, rather than dispatching a result the generation check would merely drop, so a cancelled pool queues nothing further.
  A detail refresh (`applyDetailResult`, from `OpenPR`/`RefreshPR`/`ReloadPR` alike) landing with a `HeadOID` different from `filesHeadOID` — a force-push — or with a changed `ChangedFiles` count even when `HeadOID` is unchanged (a base-branch advance) calls `LoadFiles(true)` (guarded on `filesStarted`, so this never fires before files have been loaded at all — that case is `filesWanted`'s, above): `force` is always `true` here because a cached files page is keyed only by page number, not by `HeadOID`, so showing it first would risk briefly displaying the *previous* commit's diff. `ReloadPR` also calls `LoadFiles(true)` unconditionally (no separate cache invalidation needed: `cache.InvalidatePR`, which `ReloadPR` already calls for the detail cache, removes the whole PR's on-disk directory, files pages included), so `Reload` (the `R` key) reloads files too, transitively. `recomputeLastErr` ranks `filesErr` below `detailErr` and above section errors, so `LastError()` surfaces a standing files error too. Accessors: `Files() []FileEntry` (a shallow copy of the slice — safe to range over — but each `FileEntry`'s own `Hunks`/`Tokens` slices are shared with the store's internal state and must be treated as read-only), `FilesState() FilesState{Loading, Stale bool, PagesLoaded int, HasNext bool, Err error, Warnings []string, Highlighting int}` (`Highlighting` = hunk jobs still enqueued or in flight), `FileByPath(path) (FileEntry, bool)`. Events: `EventFilesChanged` (list/pages/parse/stale-flip/error), `EventFileHighlighted` (`Event.Path` names the file), `EventFilesLoadingChanged` paired with `EventLoadingChanged` via `emitFilesLoadingChanged`, mirroring `emitLoadingChanged`'s pairing for detail. `internal/store`'s `highlighter` field is typed as an unexported `lineHighlighter` interface (`Lines(path string, lines []string) ([][]highlight.Token, error)`), which `*highlight.Highlighter` satisfies, purely so a test can substitute a fake returning a controlled error to exercise the Debug-logging path deterministically — production code always builds the real one (`highlight.New(highlight.Options{})`); `internal/diff`/`internal/highlight` themselves are pure and deterministic, so most store tests exercise the real `*highlight.Highlighter` directly rather than needing a fake at all.
- **Pending review state (implemented, M3b data slice, `internal/store/review.go`):** discovered on PR load as `currentPR.PendingReview` (from `pull_request.graphql`'s `reviews(states: [PENDING])`, already implemented in M1b/M2). `PendingReview() *model.Review`, `HasPendingReview() bool`, `PendingComments() []model.ReviewComment` (every comment across `ReviewThreads` whose `State == PENDING` — `pull_request.graphql`'s `reviewThreads.comments` selection already includes `state`, so this assumes it also carries the viewer's own `PENDING` comments directly, matching the plan's own assumption; **this specific behaviour is not yet confirmed against a real pending review** — see "Open items" in `docs/REQUIREMENTS.md`, unchanged by this milestone since no mutation was actually sent to the live API. If it turns out `reviewThreads` omits PENDING threads, `PendingComments`/`CommentOnLines`'s "add to review" apply path would need to merge in the `reviews(states:[PENDING])` connection's own nested `comments` instead). The pending review's own top-level body text is deliberately not folded into `PendingComments`, since it has no per-comment shape of its own — read `PendingReview().Body` separately. `CanSendSingle() bool` (`= !HasPendingReview()`). "Ensure a pending review" (create one lazily if `PendingReview() == nil`, otherwise reuse its ID) is not a separate store method: it is decided inside `ensurePendingReviewID`, called from a mutation's `run` closure using `prID`/`pendingID` values a `prepare` closure wrote immediately before `run` started (not back at enqueue time — a mutation queued behind another cannot trust a pending-review-ID snapshot taken before the one ahead of it had a chance to create, submit, or discard one; see the review-operations bullet below and `enqueuePreparedMutation` in `mutations.go`).
- `SendMode` (implemented, M3b, `internal/store/review.go`): `SendSingle` (publish immediately, `addPullRequestReview(..., event: COMMENT, ...)`) or `SendToReview` (accumulate on the pending review, creating one first if needed). Every send operation (`CommentOnLines`/`CommentOnFile`/`ReplyToThread`) coerces `SendSingle` to `SendToReview` once a pending review exists by the time the mutation actually runs (`sendModeFor`, called from `prepare`, not at enqueue time — see the review-operations bullet below), matching GitHub's own UI, which stops offering a single-comment button in that state; the UI is expected to never even present `SendSingle` then, but the store enforces it regardless. Since a coercion decided this late cannot be reported through the `bool` `CommentOnLines`/`CommentOnFile`/`ReplyToThread` already returned by the time it happens, a coerced send instead emits `EventNotice` (`Event.Message`, a new, generic informational-notice kind alongside `EventError`) from its `apply` closure.
- **Mutations (`internal/store/mutations.go`, implemented for comments, M3a; `prepare` and unconditional refetch-on-failure added M3b):** a single-flight FIFO queue owned entirely by the UI goroutine: `mutation{name string, ref model.PRRef, prepare func() error, run func(ctx) (apply func(), err error)}`, where `ref` is the pull request that was open when the mutation was enqueued and `prepare` is optional (nil for `AddComment`/`EditComment`/`DeleteComment`, set for the review operations below). `Mutating() bool` and `PendingMutations() int` (the running one, if any, plus every one still queued) let the UI disable the composer's send action while one is in flight; `EventMutationChanged` fires on both start and finish. `AddComment(body) bool`, `EditComment(id, body) bool`, `DeleteComment(id)` are all no-ops (besides an `EventError` "no pull request open"/"detail not loaded yet") when `current`/`currentPR` is nil; `AddComment`/`EditComment` additionally report this via their own `bool` return (`false` when nothing was enqueued) so a caller holding a caller-owned buffer on the strength of the call (the composer) knows not to discard it — otherwise each enqueues (`enqueueMutation`) a `mutation` whose `run` calls the matching `gh.Client` method with values already snapshotted by the enqueuing call (never the `Store` itself, matching every other fetch's concurrency discipline) and, on success, returns an `apply` closure that updates `currentPR.Timeline` optimistically (append/replace/remove by comment ID, copy-on-write so an earlier `CurrentPR()` pointer never mutates underneath its holder) before emitting `EventPRChanged`. `startNextMutation` starts the queue's head only when nothing is already running: it calls `m.prepare()` first, if set, synchronously on the UI goroutine — a non-nil error routes straight to `finishMutation(m, nil, err, cancelled: false, sent: false)` without ever starting `run`'s goroutine or calling GitHub, so a mutation whose target moved out from under it while queued is reported as a plain failure rather than silently misbehaving (see `enqueuePreparedMutation`/`errMutationTargetChanged` below). Once `prepare` (if any) succeeds, `run`'s goroutine starts; its single deferred closure (matching `fetchDetail`/`fetchSection`'s own discipline) recovers a panic into the mutation's own error and always dispatches `finishMutation(m, apply, err, cancelled, sent: true)` — `sent` is `true` here unconditionally, since reaching this dispatch at all means `run`'s goroutine actually started and attempted to reach GitHub, regardless of whether it then succeeded or failed. `finishMutation`: on failure, sets `mutationErr` and emits `EventError` (unless the failure is this Store's own cancellation, which is silent, exactly like every other fetch's cancellation), then, only for a non-cancelled failure whose `sent` is `true`, calls `invalidateAndRefetch` exactly like the success path does (see below) — a failed *network call* may have partially taken effect server-side (a multi-call `run` failing partway, or a request that timed out after the server already applied it), so there is no "known safe to leave alone" failure mode worth special-casing for it, and converging on GitHub's own state unconditionally is simpler and safer than guessing; a `sent: false` prepare failure skips this entirely, since nothing was ever sent for there to be anything server-side to converge on, and invalidating/refetching anyway would waste work on a pull request that may not even be the one open anymore (found in the second final review pass: the original code called `invalidateAndRefetch` for every failure regardless of `sent`, so discarding N pending reviews in a row — each failing prepare because the one ahead of it already discarded it — triggered N+1 detail refetches, and an `errMutationTargetChanged` failure invalidated the cache of a pull request that had already been closed). On success, `finishMutation` applies the payload via `apply()` only if the pull request that was current when the mutation was enqueued (`mutation.ref`) is *still* current, then always calls `invalidateAndRefetch(mutation.ref)` (success is only ever reached via a real `run`, so `sent` is implicitly true and not re-checked there): `cache.InvalidatePR` runs regardless of whether `ref` is still current (so a later re-open of that pull request never shows data the mutation has since made stale), and `startDetailFetch(false)` (always a fresh network fetch, never a cache read, since the mutation just changed the pull request server-side and re-showing a cached snapshot over the optimistic apply would be a visible regression) runs only while `ref` is still current. Either way, `startNextMutation` is called again afterwards. `mutationCtx`/`mutationCancel` are created lazily, once, from `baseCtx`: unlike the list's or detail's per-attempt generations, one mutation has no generation of its own to supersede a previous one with — every mutation for the Store's lifetime shares one context, cancelled (and the queue cleared) only by `Stop`. `mutationErr` folds into `recomputeLastErr` ranked above `detailErr`/`filesErr` (a failed mutation is a direct result of something the user just did, so more immediately relevant than a routine background fetch's standing error) but below `panicErr`/`viewerLastErr`; it clears on the next successful mutation. `MutationError() error` returns `mutationErr` directly, bypassing `recomputeLastErr`'s ranking entirely — the accessor a caller that needs to know specifically "did *my* mutation fail" (rather than "is anything at all standing as an error") should use instead of `LastError()`, which would otherwise misreport a successful mutation as failed whenever an unrelated, lower-priority error (a section's, say) happens to still stand. Since M5, `mutation` also carries `unscoped bool` (see the `CreatePullRequest` bullet below — the mutation queue's only entry with no "currently open pull request" to target) and `refreshList bool`: `finishMutation`'s success path calls `Refresh()` (the same non-forced entry point the auto-refresh ticker uses) whenever `refreshList` is set, after `invalidateAndRefetch` — merge/close/reopen/draft/title/labels/reviewers/create all set it, and so, since M5, does `SubmitReview` (moved out of the UI layer: `internal/ui/composer.go`'s own post-send `Store.Refresh()` call was removed, since it duplicated `finishMutation`'s own — both ran synchronously inside the same `EventMutationChanged` emission, so the UI's call started a second, redundant list generation on top of the store's). `enqueueMutation`/`enqueuePreparedMutation` (M3a/M3b) were generalised into a shared `enqueueMutationEntry(mutation)` tail so `enqueueMutationWithListRefresh`/`enqueuePreparedMutationWithListRefresh`/`enqueueUnscopedMutation` could be added alongside them without duplicating either.
- `enqueuePreparedMutation(name, prepare, run)` (implemented, M3b) is `enqueueMutation`'s counterpart for an operation whose actual GitHub call depends on Store state another still-queued mutation might change first — used by `CommentOnLines`/`CommentOnFile`/`ReplyToThread`/`SubmitReview`/`DiscardPendingReview` (see the review-operations bullet below) for exactly that reason: the mutation queue is single-flight only in the sense that at most one mutation's `run` ever talks to GitHub at once, not in the sense that enqueueing is serialized against running, so a second review mutation enqueued while an earlier one is still queued or in flight must not decide "which send mode" / "which pending review ID" from a snapshot taken back at its own enqueue time — that snapshot can no longer be trusted by the time this mutation's turn actually comes. `prepare`'s write to the shared closure variables `run` later reads happens-before `run`'s goroutine is even started, so this crosses goroutines with no lock and no race. `errMutationTargetChanged` ("pull request changed before the mutation started; nothing was sent") is `prepare`'s own sentinel for "the target pull request is no longer the one open" (or its detail is no longer loaded), checked by comparing against `ref` (the pull request open back at enqueue time) the same way `finishMutation`'s generation guard does for `apply`.
- **Review operations (implemented, M3b data slice, `internal/store/review.go`):** all route through the same mutation queue and `finishMutation` apply/refetch discipline as the bullet above, so this bullet only covers what is specific to reviews. `CommentOnLines(path, anchor diff.Range, body, mode SendMode) bool`, `CommentOnFile(path, body, mode) bool`, `ReplyToThread(threadID, body, mode) bool`, `SubmitReview(event, body) bool`, and `DiscardPendingReview() bool` all use `enqueuePreparedMutation` (see the mutations bullet above), since each depends on Store state (which send mode applies, which pending review ID to reuse) that can change while queued behind another mutation; their `prepare` closures re-validate the target pull request (returning `errMutationTargetChanged` otherwise) and re-read that state fresh, writing it into variables their `run` closures read once started. `CommentOnLines`/`CommentOnFile`/`ReplyToThread` build their `gh.DraftThread`/`gh.ThreadInput` from the caller's `diff.Range`/path (`draftThreadFromRange`/`threadInputFromRange` treat `StartLine == 0` or `StartLine == Line` as a single-line comment, omitting the range fields, matching `gh.DraftThread`'s own `StartLine == 0` convention) and return `bool` like `AddComment` (`false`, plus an `EventError`, when nothing was enqueued); their mutation names are mode-independent (`"comment_on_lines"`, not `"comment_on_lines_single"`/`"_review"`), since which path a queued mutation actually takes is only known once `prepare` runs — the path actually taken is logged at Debug from inside `run` instead. A send coerced from `SendSingle` to `SendToReview` (see `SendMode`'s own bullet) emits `EventNotice` from `apply`. `CommentOnFile`'s `SendSingle` path runs `CreatePendingReview` → `AddReviewThread(FILE)` → `SubmitReview(COMMENT)` inside one mutation `run`, applying the thread `AddReviewThread` returned (with its comment(s) marked `SUBMITTED` via `markThreadCommentsSubmitted`, since the review that owns it was just submitted) rather than discarding it; a failure partway leaves a real pending review on GitHub, surfaced locally by the refetch that now always follows a finished mutation (successful or not — see the mutations bullet above), offered for discard via `DiscardPendingReview`. `EditReviewComment(id, body) bool` / `DeleteReviewComment(id) bool` (`gh.Client.UpdateReviewComment`/`DeleteReviewComment`, plain `enqueueMutation` — neither depends on send-mode/pending-review state) mirror `EditComment`/`DeleteComment`'s shape but operate on `ReviewThreads[*].Comments` instead of `Timeline`; deleting a thread's last comment drops the now-commentless thread locally (`removeReviewComment`) but leaves the pending review itself untouched. `SetThreadResolved(threadID, resolved bool) bool` (plain `enqueueMutation`) refuses locally (an `EventError` — `errThreadNotResolvable`/`errThreadNotUnresolvable`, one sentinel per direction so the surfaced message names the action actually requested — no mutation enqueued) when the thread is found and either the viewer cannot perform that specific action (`thread.ViewerCanResolve`/`ViewerCanUnresolve`, GitHub's own authoritative per-thread permission — checked first, since it also covers "already resolved"/"already unresolved" and ownership restrictions) or it still has a `PENDING` comment (`errThreadHasPendingComments`, from `threadHasPendingComments`), since GitHub itself rejects resolving a thread still part of an unpublished review; a thread not found locally is not refused, left to GitHub's own validation. `ResolveThread`/`UnresolveThread`'s payload reports the server's own post-toggle `IsResolved`/`ViewerCanResolve`/`ViewerCanUnresolve` together (see the `gh` bullet above), and `applyThreadResolution` overwrites all three on the local thread from that payload rather than flipping `IsResolved` alone: toggling a thread again right after a successful resolve/unresolve, before the refetch that follows has landed, is judged against those fresh, server-reported flags — using only the pre-toggle flags here (a real bug found in the second final review pass) would refuse a toggle GitHub would actually have accepted, since a just-resolved thread's `ViewerCanUnresolve` only becomes `true` in this payload, never by locally inverting the old value. `DiscardPendingReview() bool` (`gh.Client.DeletePendingReview`) clears `PendingReview` and drops every `PENDING` comment/emptied thread optimistically (`applyDiscardPendingReview`); refused (an `EventError`, no mutation enqueued) when there is no pending review right now, both at the initial call (a fast, synchronous check) and again in `prepare` (in case an earlier queued mutation submitted or discarded it first). `SubmitReview(event model.ReviewEvent, body string) bool` calls `gh.Client.SubmitReview` when a pending review exists, or `AddReviewNowWithEvent` (create-and-submit in one call) otherwise, then clears `PendingReview` and marks every `PENDING` comment `SUBMITTED` (kept, not removed) — the richer fields a real submitted review carries (`SubmittedAt`, its place in `LatestReviews`, …) are left to the refetch `finishMutation` always triggers immediately after, not reconstructed locally. Every apply helper here (`appendReviewThread`, `appendThreadReply`, `replaceReviewComment`, `removeReviewComment`, `applyThreadResolution`, `applyCreatedPendingReview`, `applyDiscardPendingReview`, `applySubmitReview`) is copy-on-write, matching `appendTimelineComment`'s own pattern, so an earlier `CurrentPR()` pointer never mutates underneath its holder. The UI trigger for all of these is done: the `p` pending-list and diff-view `c`/`C`/`r`/`x`/`e`/`d` (M3b's UI slice), plus `SubmitReview`'s own `S` dialog (M4, `internal/ui/submitreview.go` — see the UI section below).
- **Reaction operations (implemented, M4 data slice, `internal/store/reaction.go`):** `ToggleReaction(subjectID string, content model.ReactionContent) bool` adds or removes `content` on `subjectID` — the current pull request itself, a `Timeline` issue comment, a `Timeline`/`LatestReviews` review, or a `ReviewThreads[*].Comments` review comment — via `gh.Client.AddReaction`/`RemoveReaction`, chosen from `subjectID`'s current `ReactionGroups[content].ViewerHasReacted`. Like the review operations above, that decision is made by `enqueuePreparedMutation`'s `prepare` closure immediately before the mutation runs, not at enqueue time (`reactionGroupsFor` locates the subject and reads its groups fresh): two toggles on the same subject enqueued back to back must not both decide "add" from the same stale enqueue-time snapshot — the first one's own `apply` must be visible to the second's `prepare`. If `subjectID` cannot be found on the current pull request at that point, `prepare` fails with `errReactionSubjectNotFound` (an `EventError`, no GitHub call), mirroring `errMutationTargetChanged`. On success, `applyReactionGroups` replaces `subjectID`'s `ReactionGroups` everywhere it appears, copy-on-write: a submitted review can be present in both `Timeline` and `LatestReviews` at once, and both copies are updated together so neither one goes stale. Returns `false` (plus an `EventError`) when no pull request is open or its detail has not resolved yet, matching `mutationTarget()`; a mutation that reached GitHub but failed still triggers the same refetch every other finished mutation does.
- **Mentionable users (implemented, M4 data slice, `internal/store/mentionable.go`):** a repository's `mentionableUsers` (`gh.Client.MentionableUsers`, unfiltered, `first: 100`) is loaded lazily by `OpenPR` the first time a pull request in it is opened. State is per repository (`mentionableEntry{users, fetchedAt, loading, persisted}`, keyed by `model.RepoRef`), not a one-shot "already tried" flag: `startMentionableUsersFetch(repo, force bool)` no-ops while `loading` is already true (in-flight dedup — a second `OpenPR` for a pull request in the same repository while its first fetch is still running never duplicates it), and, unless `force`, also no-ops when the in-memory result is still fresh (`mentionableEntry.fresh`, `mentionableUsersFreshFor` = 1 hour) — skipping the disk cache read entirely in that case. Otherwise (or always, when `force`) a cached disk entry (`cache.RepoKey(host, login, repo, "mentionable-users-v2")`) is applied immediately if fresh enough to skip the network call, or applied anyway (stale, shown right away) before a network fetch starts. Critically, `fetchedAt` is left untouched by a failed fetch (zero if the repository has never once succeeded): a repository a previous attempt failed for always reads as "not fresh" and is naturally retried the next time `OpenPR` opens a pull request in it, without any separate retry bookkeeping. `MentionableUsers() []model.User` returns the current pull request's repository's list (nil while no pull request is open or the list has never resolved). `ReloadPR` (the `R` key) calls `startMentionableUsersFetch(repo, true)` for the current pull request's repository, forcing a refetch even when the in-memory result is still fresh — matching `R`'s "ignore the cache" meaning for the pull request's own detail and files. `EventMentionableChanged` fires whenever the applied list changes (a cache or network result landing) and, synchronously from `OpenPR` itself (not only from a later async apply), whenever the newly opened pull request's repository differs from the previously open one's — `MentionableUsers()` can jump between two repositories' independent lists at that exact instant, which a UI driven purely by the async-apply event would otherwise miss. The fetch goroutine follows the same ctx+snapshot/`Dispatch`/`defer recover` discipline as every other fetch in this package, but uses `s.baseCtx` directly rather than a dedicated, `Stop`-cancellable context: `loading` already dedups a repository's own concurrent fetches, and there is no per-attempt "generation" to supersede the way list/detail/files fetches have; app shutdown cancelling `baseCtx` itself (see `internal/ui/app.go`'s `Run`) is enough. A failed fetch leaves the previous `users`/`fetchedAt` in place (a stale result stays visible rather than being cleared) and is logged and surfaced via `EventError`, never blocking anything else (mention completion simply has fewer, possibly stale, candidates until the next retry succeeds); there is no standing error folded into `LastError()` for it, since a missing/stale candidate list needs no more than the toast/`:messages`/next-retry this already gives it. `cacheMentionableUsers` (persisting a successful fetch to disk) refuses to write until `viewerConfirmed` is true, for the same login-scoped-key reason `cacheDetail`/`cacheSectionPage` do; `mentionableEntry.persisted` tracks whether that write actually happened, and `persistMentionableUsersIfPending` — called from `applyViewerResult`'s non-mismatch confirmation branch — retries it for the current pull request's repository once confirmation resolves, so a fetch that succeeded before `Start`'s own viewer lookup completed is not left un-cached for the rest of the session. The mismatch branch needs no equivalent call: its own `ReloadPR()` (see above) already force-refetches and persists the current repository's mentionable users fresh, under the now-confirmed login (a repository visited earlier in the same session, under a since-corrected login guess, is not similarly re-persisted — its on-disk entry simply stays filed under the old login's cache namespace, a storage-organization nuance rather than a correctness issue, since a repository's mentionable users are not viewer-scoped content).
- **Repository metadata (implemented, M5 data slice, `internal/store/repository.go`):** a repository's `RepositoryInfo`/`Labels`/`PullRequestTemplates` (`gh.Client.Repository`/`Labels`/`PullRequestTemplates`) are loaded together — three separate GitHub calls made sequentially in one goroutine, the first to fail aborting the rest, then applied as a single combined result (`repositoryMetadata{Info, Labels, Templates}`) — reusing mentionable.go's freshness+in-flight state pattern exactly: `repoMetadataEntry{metadata, fetchedAt, loading, persisted}` keyed by `model.RepoRef`, `repositoryMetadataFreshFor` = 1 hour, a failed fetch leaves `fetchedAt` at zero so the repository is naturally retried, cached on disk under `cache.RepoKey(host, login, repo, "metadata")` gated on `viewerConfirmed`. Unlike mentionable users, this is loaded only by an explicit `EnsureRepositoryMetadata(repo)` call, never automatically by `OpenPR` — three extra queries on every pull request switch would be wasteful when most switches never open an edit/merge/create form; the UI calls it when one does. `RepositoryInfo(repo) (model.RepositoryInfo, bool)`, `Labels(repo) ([]model.Label, bool)`, `Templates(repo) ([]model.PullRequestTemplate, bool)` return the second value `false` until the first successful apply (from cache or the network); `EventRepositoryMetadataChanged{Repo}` fires on each one. Unlike mentionable's own `persistMentionableUsersIfPending`, there is no dedicated retry-on-viewer-confirmation hook for a metadata fetch that succeeded before confirmation — an accepted, narrower gap (a form opened during that brief startup window simply isn't cached that one time; the next `EnsureRepositoryMetadata` call for it, cache miss or not, still succeeds and applies the result to memory, only not to disk).
- **Viewer repositories (implemented, M5 data slice, `internal/store/viewer_repositories.go`):** the viewer's own repositories (`gh.Client.ViewerRepositories`, `first: 100`) — the create-pull-request repository picker's candidate list, filtered locally by the UI — follow the identical freshness+in-flight pattern as repository metadata, but as a single, non-keyed entry (there is only one viewer): `EnsureViewerRepositories()`, `ViewerRepositories() []model.RepositorySummary`, cached under `cache.SearchKey(host, login, "viewer-repositories")` (the search/list namespace, since the result is scoped to the viewer's login, not to any one repository or pull request).
- **On-demand branch/team search (implemented, M5 data slice, `internal/store/search.go`):** `SearchBranches(repo, query, fn)` / `SearchTeams(org, query, fn)` back a query-filtered picker (base/head branch, review-request team) with no caching at all — each keystroke is its own, generally distinct query, so a cache would mostly accumulate one-shot entries with no reuse value — and no per-repository/per-organization keying, only a single generation-tokened slot per kind (`branchSearchGen`/`teamSearchGen`), since only one such picker is open, and being typed into, at a time. Each call bumps its generation and returns the new token. Delivery is to `fn` only (invoked on the UI goroutine, from inside the `Dispatch` callback that resolves the search) — there is no `EventBranchesSearched`/`EventTeamsSearched` or `BranchSearchResult()`/`TeamSearchResult()` accessor: an earlier revision of this bullet had both, but a search here has exactly one consumer (the form it backs), so a second, event-based delivery path would only have meant every result travelling twice for no reader of the second copy. `fn` fires only if this call is still the most recent one for its kind: a later call for the same or a different repo/org, made before an earlier one resolved, supersedes it, and `fn` never fires for the superseded call at all, so a stale answer for an abandoned keystroke's query is never applied over a newer one. Both use `s.baseCtx` directly (there is no per-search cancellable context — a superseded search is dropped by the generation check, not cancelled) and follow the same recover→log+`EventError`→`setRateLimit` discipline as every other fetch in this package — a failed search still calls `fn` (with a nil result and the error) alongside the usual `EventError`.
- **Pull request edit/merge/create mutations (implemented, M5 data slice, `internal/store/pr_edit.go`, `pr_create.go`):** `UpdatePullRequestMeta(in gh.UpdatePullRequestInput) bool`, `SetReviewers(userIDs, teamIDs []string) bool` (`union: false`, replacing the requested-reviewer set outright), and `SetDraft(draft bool) bool` (`ConvertToDraft`/`MarkReadyForReview`) all route through the mutation queue like every comment/review/reaction mutation before them, applying each mutation's returned fields optimistically (copy-on-write, matching `appendTimelineComment`'s pattern) before the usual invalidate-and-refetch. `Merge(method model.MergeMethod, headline, body *string) bool` uses `enqueuePreparedMutationWithListRefresh`: its `prepare` hook (run immediately before the mutation's GitHub call, not back at enqueue time) captures the pull request's own `ID` and current `HeadOID` as `expectedHeadOid`, and refuses locally — nothing sent to GitHub — with `errPullRequestNotOpen` when the pull request is no longer `OPEN` by then (a stale `Mergeable`/`MergeStateStatus` is deliberately left for the server to accept or reject on its own, current terms — only the lifecycle state is checked locally). `Close() bool` / `Reopen() bool` mirror the simpler mutations above. `CreatePullRequest(in gh.CreatePullRequestInput, reviewerUserIDs, reviewerTeamIDs []string) bool` is the mutation queue's only *unscoped* entry (`mutation.unscoped`): unlike every other mutation, it does not target "the currently open pull request" — there may be none open at all — so `finishMutation` always invokes its `apply` on success (there is no "still current" ref to gate it on) and never calls `invalidateAndRefetch` for it (nothing server-side existed before this call to invalidate). Its `run` calls `CreatePullRequest` then, if reviewers were given, `RequestReviewers(newID, union: true)`; a failure in that follow-up call does not fail the whole mutation — the pull request itself was still created server-side, and losing its ref over an unrelated second failure would be worse than surfacing both — instead `run` returns a success `apply` that unconditionally emits `EventPullRequestCreated{Ref}` (the UI is expected to open it) and additionally emits `EventError` for the reviewer failure, if any. Every mutation in this bullet, plus the pre-existing `SubmitReview` (M3b/M4), sets `mutation.refreshList`: `finishMutation` calls `Refresh()` (the same non-forced entry point the auto-refresh ticker uses) after a successful state-changing mutation, since a title/label/reviewer/draft/merge/close/reopen/create/submitted-review change is state the list itself displays and would otherwise look stale until the next scheduled refresh. This required generalising `enqueueMutation`/`enqueuePreparedMutation` (M3a/M3b) into a shared `enqueueMutationEntry(mutation)` tail, with `enqueueMutationWithListRefresh`/`enqueuePreparedMutationWithListRefresh`/`enqueueUnscopedMutation` as the new callers' entry points alongside the two originals.
- **Drafts (`internal/drafts`, done — the composer, `internal/ui/composer.go`, calls it directly; the `p` discard/open list and the diff gutter's own `✎` marker are done, M3b):** `internal/store` itself holds no drafts state of its own, since a draft's lifetime (save-on-every-keystroke, no debounce) is driven by the composer, not by any store-owned fetch/generation machinery — `App.Deps.Drafts *drafts.Store` is a separate dependency of `internal/ui` entirely, keyed by `drafts.Key{PR: ref.Key(), Kind, Anchor}` (`KindComment`/`"issue"` for a general PR comment, `KindEdit`/comment ID for an edit).

## Diff (`internal/diff`) — implemented (M2)

Pure: no network, no UI, no dependency on `store`/`ui`.

- `Parse(patch string) ([]Hunk, error)`: parses GitHub's header-less per-file patch — `@@ -a[,b] +c[,d] @@[ section]` hunk headers (a comma-less count defaults to 1, matching `@@ -1 +1 @@`) and body lines prefixed ` `/`+`/`-`. `\ No newline at end of file` is not itself a `Line`: it sets `NoNewline` on the `Line` immediately before it (an error if there isn't one). An empty patch is `(nil, nil)`; any other line shape (before any hunk header, an empty line inside a hunk, an unrecognised prefix, a malformed header) is a parse error naming its 1-based line number within `patch`.
- `Hunk{OldStart, OldLines, NewStart, NewLines int, Section string, Lines []Line}`; `Line{Kind Context|Add|Del, OldNo, NewNo int, Text string, NoNewline bool}` (`OldNo`/`NewNo` are 0 when absent on that side — an `Add` line has no `OldNo`, a `Del` line has no `NewNo`).
- `ExpandTabs(s string, width int) string`: replaces each tab with spaces up to the next `width`-column stop, tracking display column via `uniseg.FirstGraphemeClusterInString` (not byte/rune count) so a wide rune (for example a CJK character) advances the column correctly; `width <= 0` is treated as 1.
- `Anchor(line) (model.DiffSide, int)`: `Del` → `LEFT`/`OldNo`, otherwise (`Add`/`Context`) → `RIGHT`/`NewNo` — this is GitHub's own single-line review-comment placement rule.
- `RangeAnchor(lines) (Range, error)` (`Range{StartSide, Side model.DiffSide, StartLine, Line int}`): the caller guarantees `lines` are contiguous within one hunk. Requires at least 2 lines and a **single side**: only `Del` lines → `LEFT`/`OldNo`; no `Del` lines → `RIGHT`/`NewNo`; a mix is `ErrMixedSides` (a sentinel `error`, not a fixed message — check with `errors.Is`). Mixed-side ranges are recorded as unsupported in v1; M3b runs one exploratory API call and lifts the restriction if the API accepts it (see "Open items" in `docs/REQUIREMENTS.md`).
- `LocateThread(hunks, thread)`: a file-level thread (`SubjectType == FILE`, rendered at the file header instead) or an `IsOutdated` thread never locates. Otherwise delegates to `LocateLine(hunks, thread.Side, thread.Line)`.
- `LocateLine(hunks, side, lineNo) (hunk, line int, ok bool)` (M3b): the shared side/line lookup behind `LocateThread` — `LEFT` → the line with `OldNo == lineNo` (`Del`|`Context`); `RIGHT` → `NewNo == lineNo` (`Add`|`Context`); no match → `ok == false`. Also used by `internal/ui`'s draft gutter marker (parsing a saved line/range-comment draft's anchor back into a location) and the "p" pending-list dialog's `widget.DiffView.JumpToLine`.

## Highlight (`internal/highlight`) — implemented (M2)

Chroma-based tokenising; no tcell/tview dependency (returns token *kinds* only — `internal/ui/theme`, in a later milestone, maps them to `tcell.Style`).

- `Token{Text string, Type chroma.TokenType}`; `Highlighter` (`New(Options{MaxLineBytes, MaxTotalBytes int})`, defaulting to 4096 bytes/line and 1 MiB total when left at zero) caches the resolved lexer per file extension (or, for an extensionless file like `Dockerfile`/`Makefile`, per lowercased base name, so two different extensionless files never share a cache slot).
- `Lines(path string, lines []string) ([][]Token, error)`: callers pass a file's hunk lines with the diff `+`/`-`/` ` prefix already stripped and tabs already expanded (`diff.ExpandTabs`). Lexer resolution is `lexers.Match(path)` (glob-based, fast); a nil result means "render as plain text, unhighlighted" — `lexers.Analyse` (content sniffing) is deliberately never used as a fallback, since it is too slow to run on every hunk. The whole of `lines` is tokenised as **one** text (`strings.Join(lines, "\n")`, wrapped in `chroma.Coalesce`) so a token spanning multiple source lines (a block comment, a multi-line string) is classified correctly on every line it touches, then re-split per line with `chroma.SplitTokensIntoLines`; the trailing `"\n"` that split leaves on all but the last line's tokens is stripped (dropping the token entirely if that empties it), and the result is defensively reshaped to exactly `len(lines)` groups (padding short, folding any surplus onto the last line) so a caller can always index it by line position. Returns `(nil, nil)` — not an error — for: no lexer found, any line over `MaxLineBytes`, or the combined size over `MaxTotalBytes`; these are routine outcomes (binary-ish, generated, or pathological files), not failures.
- **Concurrency:** a `Highlighter` is safe for concurrent `Lines` calls, including for the same path from multiple goroutines at once. A resolved `*chroma.RegexLexer` compiles its rules exactly once, guarded by an internal `sync.Once` plus a mutex-checked "compiled" flag; each `Tokenise` call then allocates a fresh, call-local `LexerState` (text, state stack, mutator context) never shared between calls, and the compiled `*regexp2.Regexp` values it reads are documented by `dlclark/regexp2/v2` as safe for concurrent use once compiled. This is why `internal/store`'s highlight worker pool shares **one** lexer per extension across its 2 workers rather than allocating one lexer per worker (`docs/DESIGN.md`'s concurrency rule 8's stated fallback if this had not held).

## Drafts (`internal/drafts`) — implemented, wired into the composer (M3a); the `✎` diff gutter marker and `p` list implemented (M3b)

Pure package: no dependency on `gh`, `store`, or tview. A `Store` persists in-progress comment/review/PR-body text as small JSON files under a caller-supplied directory (`internal/config.StateDir()` in production), keyed by `Key{PR, Kind, Anchor}`.

- `Key{PR string, Kind Kind, Anchor string}`: `PR` is `model.PRRef.Key()` ("host/owner/repo#number"); `Kind` is one of `KindComment` (a general PR comment or a new line/range review comment), `KindReply` (anchored by thread ID), `KindFile` (anchored by file path), `KindReview` (a pending review's own body), `KindPRBody`, or `KindEdit` (anchored by the comment ID being edited — an issue comment or a review comment; `internal/ui`'s "p" list resolves which by checking the pull request's own timeline/threads for a matching ID). `Anchor` disambiguates drafts of the same `Kind` on the same PR: `"issue"` for a general comment; `"path:SIDE:line"` or `"path:SIDE:start-line"` for a line/range review comment (M3b, `internal/ui`'s `formatLineAnchor`/`parseLineAnchor`, matching `diff.Anchor`/`diff.RangeAnchor`'s own side/line(s)); `"file:path"` for a file comment. `Key.String()` renders `"pr|kind|anchor"`.
- On disk: `<dir>/<sanitised pr>/<sha256(Key.String())>.json`, body `{"key": {"pr", "kind", "anchor"}, "text", "updated_at"}`. `sanitisePR` replaces every byte outside `[A-Za-z0-9.-]` with `_` and appends a short content hash of the full, unsanitised `pr` string — the hash, not the sanitised text alone, is what actually prevents two different `pr` values from colliding on the same directory (a GitHub owner/repo name may itself contain `_`, so two distinct `"host/owner/name#number"` strings could otherwise sanitise identically).
- `New(dir) (*Store, error)` creates `dir` (mode 0700) if missing. `Save(k, text) error` writes atomically (temp file in the same directory + rename, mirroring `internal/cache`'s own `writeAtomic` — the approach is reused, not the package, to keep `internal/drafts` free of a `cache` dependency), file mode 0600; an empty `text` deletes the draft instead, so gprt never keeps an on-disk file for a cleared composer. `Load(k) (Draft, bool, error)` and `Delete(k) error` (a missing draft is not an error). `List(pr) ([]Draft, error)` returns every draft for `pr` sorted by `UpdatedAt` descending; a draft file that fails to read or decode is skipped rather than failing the whole call, with every such failure joined (`errors.Join`) into the returned error so a caller logs it once. `Count(pr) (int, error)` is `len(List(pr))`. A `sync.Mutex` inside `Store` makes every method safe for concurrent use.

## UI (`internal/ui`) — PR list (M1a), PR tab (M1b), Files tab (M2), the composer/vim editor/drafts (M3a), review comments on the diff (M3b), and the submit-review dialog/reaction picker/real mention candidates (M4) implemented

- **Router** (`App.handleKey`, the only `app.SetInputCapture`) — implemented for every context: `keys.Normalize` → Ctrl-C quits immediately, unless `Store.Mutating()` (a comment being sent, edited, or deleted), in which case a confirm dialog (`App.showConfirm`, see the Dialogs bullet below) asks first — checked ahead of everything else, so it applies no matter what has focus, including the composer → while the filter or command-line `InputField` has focus, only `Esc`/`Enter` (plus `Up`/`Down` for the command line's history) are intercepted, everything else is forwarded to the field unchanged → while the composer's editor has focus (`Editor.HasFocus()`, **not** `app.GetFocus() == a.composerEditor` — see the pitfall two paragraphs down), every key goes straight to `Editor.HandleKey` (never `Editor.Handle`: `normalized` — this router's own already-normalized keys — must be fed one key at a time to the per-key method, or a multi-key-normalizing event, such as Alt+rune expanding to `[Esc, rune]`, would have `Handle`'s own internal `keys.Normalize` re-expand and reprocess it again for every one of those keys, corrupting the sequence — see the second pitfall below) except a `Ctrl-w` chord outside insert mode (`App.routeComposerKey`; tracked with its own single-pending-key field, `composerCtrlWPending`, not the Sequencer, precisely so the composer's own keys — including ones that are `ContextGlobal` bindings elsewhere, like `q`, `R`, `?`, `:` — are never intercepted by anything but that one chord): `Ctrl-w h`/`l` call the ordinary `focusPrevPane`/`focusNextPane`, `Ctrl-w j`/`k` call `App.toggleComposerFocus`; in insert mode, `Ctrl-w` is instead vim's own "delete word before cursor", already in `Vim`'s insert whitelist and forwarded straight to `TextArea`'s native implementation — intercepting it as the chord's first key unconditionally, regardless of mode, made it unreachable while typing. The loop also stops as soon as `a.composerEditor` goes nil (a `HandleKey` call that closed the composer, mid-sequence, via `:q`/Ctrl-s/...), since there would be nothing left to feed the remaining keys to. → while a `?`/`:messages` overlay is open, `q`/`Esc` close it (`?` also closes the help overlay specifically, toggling it like the key that opened it) and every other key is returned unchanged so the overlay's own scrollable `TextView` handles it (`j`/`k`/`gg`/`G`/`PgUp`/`PgDn`, ...); a confirm dialog (`a.overlay == "confirm"`) instead returns the event completely unchanged, letting `tview.Modal`'s own `InputHandler` (arrows/Enter/Escape) handle it — `routeOverlayKey`'s q/Esc-only handling would otherwise swallow every key the Modal itself needs → while the diff has focus and a visual selection is active, `Esc` ends it (checked here, ahead of the Sequencer, since Esc is never a dispatchable Action — `keys.Sequencer.Feed` always consumes it itself to reset any pending prefix) → otherwise `keys.Sequencer.Feed` resolves the pressed key(s) against the focused pane's context (falling back to `ContextGlobal`; the PR tab's `widget.DetailView` resolves through `ContextPR` first, since M3a, then `ContextDetail`) and `App.dispatch` runs the resolved `Action`; an action not yet implemented (`list.new_pr`, `pr.edit`) is silently ignored; since M4, `comment.react`/`pr.submit` dispatch to the reaction picker/submit-review dialog (see the Dialogs bullet below). `ContextThread`'s `r`/`x` and `ContextComment`'s `e`/`d` are otherwise unreached by `ContextDiff` (which binds none of them), so they resolve regardless of cursor position and each handler itself toasts "not on a comment thread" when it is not. `p` (`pr.pending`) is bound in `ContextPR`/`ContextFiles`/`ContextDiff`. `list.down`/`up`/`top`/`bottom`/`half_down`/`half_up` are bound in every movable context including `ContextFiles` (M2 review round 2, item 14: `gt`/`gT`, also bound in `ContextFiles`, make a bare "g" always match at least a `Prefix` there, so it can never fall through to the tree's own native handling unconsumed — binding `list.top` to "gg" resolves that the same way `ContextList`/`ContextDiff`/`ContextDetail` already do). `App.dispatch` resolves them against `focusedListPane()`, whichever movable pane (the PR list, the PR tab's `widget.DetailView`, the Files tab's tree, or its `widget.DiffView`) currently has focus, or a no-op `noopMovablePane` when none does; for the tree, `focusedListPane` returns a `treeMovablePane` adapter that synthesises `tview.TreeView`'s own native `j`/`k`/PgUp/PgDn keys through its `InputHandler` (repeating `k`/`j` for top/bottom, since native `g`/`G` only move `tview.TreeView`'s scroll offset, never its `currentNode` — confirmed by reading `treeview.go`: `process`'s selection switch has no case for `treeHome`/`treeEnd` at all, only `Draw` does, and only for `offsetY`), rather than reimplementing tree traversal by hand. `K`/`J` (parent/child) remain unmapped by gprt's keymap, left to the tree's own native handling. If no context bound (or was mid-sequence toward) the pressed key at all, the router returns the original event instead of swallowing it, so the tree's own native handling of a genuinely unbound key (arrows, Home/End, ...) still gets it (as does either overlay `TextView`).
  - **Pitfall (M3a):** `internal/ui/editor.Editor` embeds `*tview.Flex` (its `TextArea` + a status line) and does not override `Focus`, so `tview.Flex.Focus` (inherited, like `tview.Form`) delegates keyboard focus straight down to whichever child was added with `focus=true` — the raw `TextArea`. `tview.Application` then tracks focus at that leaf: `app.GetFocus()` returns the `TextArea`, never the `Editor` wrapper, so comparing it against `a.composerEditor` (a switch case or `==`) never matches. `Editor.HasFocus()` is overridden (`return e.area.HasFocus()`) specifically so callers ask the right question instead; every place in `internal/ui` that needs "is the composer focused" (the router, `hintForFocus`, `toggleComposerFocus`) calls that method, never an identity comparison.
  - **Pitfall (M3a review round 1):** `routeComposerKey` originally fed the *raw* `*tcell.EventKey` back into `Editor.Handle` once per key in its own already-normalized `normalized` slice. Success/failure is read from `Store.MutationError()` — the mutation queue's own standing error — never `Store.LastError()`, which also surfaces other, lower-priority standing errors (the current pull request's files, or a list section) whenever nothing higher-priority masks them, and would otherwise report a perfectly successful send as failed: success toasts `"comment posted"`/`"comment updated"`; failure re-saves the draft (`Drafts.Save(target.draftKey, ps.text)`) and toasts `"not sent; draft kept (<reason>)"` with `MutationError()`'s message.
  - **Failed-send re-save vs. a reopened composer** (review round 2, item 15): if the user has already reopened a composer for the exact same target by the time a send fails (`*a.composerTarget == ps.target`) and possibly started typing something new into it, `onMutationChanged` merges `ps.text` into the *live* editor (`Vim.SetTextFromOutside(ps.text + "\n\n" + current)`, or just `ps.text` if the reopened composer is still empty) instead of writing straight to the draft file — writing to the file underneath a live editor would only have the next write-through save silently clobber it right back with the failed text on top of whatever the user has since typed. Either branch (the merge's own write-through, or the direct re-save) is followed by `App.refreshDraftGutterIfNeeded(ps.target)` (M3b review round 1, item 10): `finishSend` already closed the composer and deleted its draft the instant the mutation was enqueued (see `sendComposer`'s own doc comment), so the gutter marker had already disappeared by the time the failure is known — without this call it would stay hidden even after the draft is resurrected on disk, until some unrelated later refresh happened to catch up.
  - **Draft-gutter refresh coalescing** (M3b review round 1, item 7): `onComposerChange` originally called `refreshDraftGutterIfNeeded` — which lists every draft for the whole pull request from disk and rebuilds the diff's entire row set — on every single keystroke while composing a line/range/file comment, since `Drafts.Save`'s own empty-text-deletes rule makes "has a draft" recomputable from `text != ""` alone on every call. `App.composerDraftGutterMarked` now tracks that boolean for the currently open composer's own target (initialised from `openComposer`'s own `Drafts.Load` result), and `onComposerChange` only calls `refreshDraftGutterIfNeeded` when it actually flips — once when the first character is typed (or the last one is deleted), not once per keystroke either side of that.
  - A `Drafts.Load` failure (a draft exists but could not be read — not simply "none exists", which is `ok == false` with no error) and a `Drafts.Delete` failure after a send both toast (`showErrorToast`, which also logs at Error) rather than only logging at Warn (review round 2, item 21) — a `Delete` failure in particular could otherwise leave a stale draft to resurrect text that was already posted successfully, with no visible sign it happened.
- **Mention candidates** (`App.mentionCandidates`, M3a; repository users + fuzzy matching added M4): the open pull request's author, requested (user) reviewers, and every comment/review author already in its timeline, followed by `Store.MentionableUsers()` (the repository's own mentionable users, M4 data slice — nil until that repository's first fetch resolves, handled like any other empty slice), deduplicated by login: participants are added first, and a later `add()` call for an already-seen login backfills its `Name` if the earlier one was empty (a bare `pr.ReviewRequests` entry — `model.Reviewer` has no `Name` field at all — is filled in once the same login turns up in `MentionableUsers()`, which always carries one) rather than being dropped outright. A non-empty query fuzzy-matches (`github.com/sahilm/fuzzy`, `fuzzy.FindFrom`) against each candidate's `"login name"` (`candidateSource`, `login` alone when `Name` is empty) — a scattered subsequence matches, not just a strict prefix, results are ranked by the library's own score (an exact prefix match ranks above a scattered one), and case is folded by the library itself, so no separate lower-casing is needed. An empty query after `@` returns every candidate as-is, in that same participant-priority order.

Merge dialog (opened by `:merge`), edit-PR form, create-PR form, reviewer picker, and label picker remain planned (M5).
  - **Submit review** (M4, `internal/ui/submitreview.go`, `S`/`pr.submit`, bound in `ContextPR`/`ContextFiles`/`ContextDiff` like `pr.pending`): `App.openSubmitReviewDialog` shows a choice menu ("Approve"/"Request changes"/"Comment"); its `onChoose` callback re-checks `Store.CurrentRef()` against the ref captured when the menu was shown — mirroring `performReviewSend`'s own re-check (composer.go) — since it fires well after the menu was shown and `closeComposerIfWrongPR` cannot reach a menu with no composer open yet behind it. ## Vim editor (`internal/ui/editor`) — implemented (M3a)

- `Vim` (pure, no tview/tcell dependency beyond `internal/ui/keys.Key`): a modal state machine over `Text interface { Text() string; Cursor() int; SetCursor(int); Replace(start, end int, s string); Select(start, end int) }`. `NewVim(t Text) *Vim` — named `NewVim`, not `New`, so it does not collide with `Editor`'s own `New` in the same package. Tests (`vim_test.go`) use a string-backed `fakeText` that fails the test immediately on an offset not aligned to a grapheme-cluster boundary; production (`editor.go`'s `textAreaAdapter`) wraps `*tview.TextArea` (`Cursor()` = the start of `GetSelection()`, which `TextArea` itself documents as the cursor position whenever nothing is selected). Modes: `ModeNormal`/`ModeInsert`/`ModeVisual`/`ModeVisualLine`/`ModeCommand`; state: `count`/`pendingOpCount` (a count typed before an operator and one typed between it and its motion multiply together, matching vim's compound counts — `effectiveCount()`), `pendingOp`, unnamed register (`register`/`registerLinewise`), visual `visualAnchor`/`visualCursor` (see the pitfall below), an insert-session snapshot, and an undo/redo stack. `Handle(k keys.Key) Action{Kind, Command, Query}` where `Kind` is one of `Consumed`/`Forward`/`Command`/`MentionQuery`/`ModeChanged`/`SendRequested`/`CloseRequested`/`DiscardRequested`/`ExternalEditRequested`.
- **Undo/redo live in the layer, not in `TextArea`** — `TextArea` groups insert-mode keystrokes per word and does not export its own undo. Every command maps to one `Replace(start, end, new)` via the internal `replace` helper, which records `{start, old, new}` (`pushUndo`, a no-op for a zero-length diff); `undo` = `Replace(start, start+len(new), old)`, `redo` (Ctrl-r) is the inverse, and a fresh edit clears the redo stack. Commands that enter insert mode (`i a I A o O cc cw c$ C s`) call `enterInsertSession` first, which snapshots `Text()` and sets `insertActive = true`; every mutation performed while `insertActive` bypasses `replace`'s own recording (applied to `Text` directly), so `leaveInsertSession` (on `Esc`) can push the *whole session* — snapshot vs. final text, reduced to their common-prefix/suffix `diffSpan` (itself snapped to grapheme boundaries on both sides, since the two strings can differ in length) — as one entry, matching vim's "one insert session, one undo". `SetTextFromOutside` (`:e`'s return, or a restored draft) pushes one entry the same way. `Ctrl-z`/`y`/`l`/`d`/`k`/`q`/`x`/`v` are never forwarded to `TextArea` (only Ctrl-w/Ctrl-u are, from the insert whitelist below; Ctrl-r is handled directly by `Vim`).
- Motions (`motion.go`) compute byte offsets from `Text()` (called once per keystroke) using `uniseg` grapheme clusters (`cluster.go`; `Select` rounds to a cluster boundary, so implementing `h` as "-1 byte" would not move on CJK text — verified by table tests moving over `"日本語"`); word classes (`wordClassOf`) treat a double-width cluster as its own single-cluster "word" (never merging two consecutive CJK characters the way two ASCII letters would), matching vim's own multibyte handling; `j`/`k` keep a sticky "desired column" in display cells, resynced from the cursor's *actual* column only when the immediately preceding keystroke was not itself `j`/`k` (`lastWasVertical`), rather than every motion updating it — equivalent in effect, since every motion but `j`/`k` changes the actual column anyway. `h`/`l`/`w`/`0`/`^` are exclusive as operator motions, `e`/`$` inclusive (extended to the target cluster's own end via `clusterEnd`), `gg`/`G`/`j`/`k` linewise — vim's own classification; `cw` behaves like `ce` (the target motion is swapped from `w` to `e`) unless the cursor starts on whitespace, matching vim's own documented exception. `dd`/`cc`/`yy` and their `j`/`k`/`gg`/`G` linewise-target forms share `captureLinewise`/`lineContentSpan`/`applyLinewiseChange`: a deleted last line steals the *preceding* newline instead of leaving a dangling blank line, while `cc` never touches the surrounding newlines at all (only the line's own content). After `Replace` the cursor sits at the end of the replacement, so every command sets it explicitly (`clampToLineIfAtEnd` steps back to a line's last cluster rather than resting one past it, matching vim, except on an empty line). Leaving insert moves the cursor left one grapheme cluster within the line, matching vim.
- **Pitfall — visual mode's active end is *not* `Text.Cursor()`:** once `Select(a, b)` has set a real (non-empty) range, `Text.Cursor()`/`GetSelection()` only ever report the range's *start*, never whichever end the user was actually moving (vim's anchor vs. active-cursor distinction) — moving *forward* from the anchor and then reading `Cursor()` back would silently return the anchor, not the new position. `Vim` therefore tracks the active end itself, in `visualCursor` (separate from `visualAnchor`), and every visual-mode function (`moveCursorVisual`, `verticalMoveVisual`, `gg`/`G`, `applyVisualOp`) reads/writes that field directly rather than ever calling `Text.Cursor()` while a selection is active; `updateVisualSelection` computes `Select`'s two arguments from `visualAnchor`/`visualCursor` alone. Visual mode's own motions are inclusive of whatever cluster the cursor lands on (`updateVisualSelection`'s `clusterEnd`), unlike the *same* motion used with an operator in normal mode — a well-known vim asymmetry (`vwd` from the start of "one two three" deletes "one t", not "one ", the way `dw` would) reproduced deliberately, not a bug. For the same reason, `Ctrl-r` (redo) in visual mode calls `exitVisual` *before* `redo` (review round 1, item 18): redo can shrink or restructure the buffer arbitrarily, and `visualCursor` (left exactly as it was, since visual mode never resyncs it from anything else) would then be a stale, possibly out-of-range offset into the new text that the next visual motion's own `lineBounds` call would index with directly — a real panic, not just a wrong result. vim itself has no visual-mode redo binding at all; exiting first, like `Esc`, and letting redo run in its usual normal-mode context (whose own cursor placement is already clamped to the new text) is the closest equivalent.
- `:` command mode (`command.go`): `:w`/`:wq` → `SendRequested`, `:q` → `CloseRequested`, `:q!` → `DiscardRequested`, `:e` → `ExternalEditRequested`, anything else → `Consumed` plus a message from `LastCommandError()`; Backspace on an empty line cancels back to normal, matching vim. `Ctrl-s` → `SendRequested` is checked first in `Handle`, ahead of every mode, so it always works regardless of mode.
- Mentions (`mention.go`): `OnTextChanged() Action` — **not** a `Kind` `Handle` itself ever returns — inspects the *current* `Text()`/`Cursor()` for `@[\w-]*` immediately before the cursor at a word boundary, returning `MentionQuery{Query}` (only in `ModeInsert`) or `Consumed`. It is a separate method because most insert-mode keys are reported as `Forward` (see below): `Handle` returns *before* the host has actually applied a Forwarded key to `TextArea`, so it cannot evaluate "the text after this keystroke" within that same call — the production `Editor` instead calls `OnTextChanged` from `TextArea`'s own `SetChangedFunc` callback, which fires after every edit, forwarded or not, actually lands; pure tests call it directly against a `fakeText` positioned as if a keystroke had just landed. `AcceptMention(login)` replaces the detected `@prefix` with `@login ` via one `replace` call — but only once it has independently re-verified `Cursor() >= mentionStart` and that `text[mentionStart:cursor]` (`isMentionSpan`) is still exactly `@[\w-]*` (review round 2, item 20): a bare cursor move (Left/Right/Home/End, forwarded straight to `TextArea`) neither goes through `Vim.Handle` nor triggers `TextArea`'s own "changed" callback, so `OnTextChanged` never gets a chance to notice the cursor has left the span before some other key (Tab/Enter) would otherwise accept a now-stale one — `Editor.dispatch`'s `Forward` case additionally closes the popup outright on exactly those same keys, as a first line of defense, but `AcceptMention`'s own check does not depend on that alone.
- Insert mode (`insert.go`) forwards a whitelist to `TextArea`, via `Action{Kind: Forward}`: any non-Ctrl rune, Enter, Tab, Backspace, Delete, arrows, Home/End, Ctrl-w, Ctrl-u; `Esc` ends the insert session (see above); everything else is dropped. Forwarding is a single path: the host (`Editor.dispatch`) calls `textArea.InputHandler()(ev, ...)` for a `Forward` action and nothing else ever mutates `TextArea` directly on a Forwarded keystroke.
- `Editor` primitive (`editor.go`, a `*tview.Flex` embedding `TextArea` + a one-line mode/hint `TextView`, plus a hidden-until-open `*tview.List` for the mention popup): `New(Options{Candidates, Suspend, ExternalEditor, OnChange, OnAction}) *Editor` (named `New`, since it — not the pure `Vim` — is the primitive other packages construct); `Handle(ev *tcell.EventKey) bool` normalizes `ev` and calls `HandleKey` once per resulting key; `HandleKey(k keys.Key, ev *tcell.EventKey) bool` processes exactly one already-normalized key — lets an open popup's own keys (Ctrl-n/Ctrl-p/Up/Down move, Tab/Enter accept, Esc closes *only* the popup) take priority, and otherwise dispatches `Vim.Handle`'s result — and is what a caller that has *already* normalized its own event (gprt's router, routing a composer's own `Ctrl-w` chord one key at a time) must call directly, once per key, rather than `Handle` (see the router's own pitfall note for the bug calling `Handle` per key there caused). `Draw` caches `screen` (`lastScreen`) for the blur callback below, then runs `Flex.Draw`, then (only while the `TextArea` itself has focus — see the pitfall below) sets the terminal cursor's style (`screen.SetCursorStyle`: steady block in normal/visual, steady bar in insert), then the popup (if open), anchored just below the cursor's screen position (`TextArea.GetCursor`/`GetOffset`/`GetInnerRect`) and opening upward instead when it would not fit. `TextArea.SetBlurFunc` resets the cursor style to `CursorStyleDefault` (via `lastScreen`) the moment focus leaves the `TextArea` (`tview.Application.SetFocus` calls the previously focused primitive's own `Blur()` before assigning a new one) — without it, the terminal keeps showing whatever shape was last drawn (typically a steady bar, from insert mode) even after the composer closes, since nothing else ever draws over it; not observable through `tcell.NewSimulationScreen`, whose own `SetCursor` is an unconditional no-op, so this is covered by inspection/manual testing only, not a unit test.
- **Pitfall — `Editor.HasFocus()` is overridden, not inherited:** `tview.Flex.Focus` (which `Editor` would otherwise inherit) delegates keyboard focus straight down to whichever child was added with `focus=true` in `AddItem` — the raw `TextArea` — so `tview.Application.GetFocus()` returns the `TextArea`, never the `Editor` wrapper itself (the same behaviour `tview.Form` has, for the same reason). `Editor.HasFocus()` is overridden (`return e.area.HasFocus()`) so any caller that needs "is this Editor focused" — `Draw`'s own cursor-style logic, and `internal/ui`'s router/`hintForFocus`/`toggleComposerFocus` — asks the right question instead of comparing `app.GetFocus()` against an `*Editor` value, which would silently never match.
- Mention candidates arrive via the injected `Options.Candidates func(prefix string) []Candidate{Login, Name}` (`App.mentionCandidates`: a per-PR-derived source since M3a, with the repository's real `mentionableUsers` appended and the filter itself switched to `sahilm/fuzzy` since M4 — see the Mention candidates bullet above).
- The composer pane is removed from its `Flex` (`RemoveItem`) when hidden, never resized to 0 — a `TextArea` drawn at width 0 stops extending its lines.
- External editor: `:e` → `Editor.runExternalEditor`, which resolves the command (`Options.ExternalEditor` > `$EDITOR` > `"vim"`, split with shell-like quoting via `google/shlex`), calls `Options.Suspend(func(){ write a temp file; exec the command with the file path appended; read it back }) bool` (wired in production to `app.Suspend(f)`, itself returning `false` when it could not actually suspend — already suspended, or no screen yet — in which case `app.Sync()` is skipped too), then feeds the (CRLF-normalized) result to `Vim.SetTextFromOutside` (one more undo entry).
  - **Failure handling** (review round 2, items 16–17): `Suspend` returning `false`, `Suspend` being `nil`, or the command/temp-file round trip itself failing all abort with the buffer left completely untouched — the external editor's own (in that case unreliable) output is never applied. `Editor.reportExternalEditorError` records the message (shown by `renderStatus`, ahead of `LastCommandError`, until the next `:e` attempt) and calls `Options.OnError` (wired to `App.onComposerError` → a toast) so the failure is visible even if the user is not looking at the composer's own status line at that moment.
  - **CRLF normalization** (review round 2, item 19): `normalizeCRLF` (`strings.ReplaceAll(s, "\r\n", "\n")`) is applied to `:e`'s own read-back and to `Editor.SetText`'s argument (the prefill/draft-restore path) — `uniseg` treats a `"\r\n"` pair as one grapheme cluster, but every line-oriented computation in `internal/ui/editor` (`lineBounds` and everything built on it) splits purely on `"\n"`; an un-normalized `"\r"` would end up stranded as a trailing character of the previous line the moment that line is edited, corrupting undo entries and confusing line-based motions.

```yaml
  global.toggle_list: "<C-w>o"
  diff.comment: "c"
  pr.submit: "S"
```

- `ConfigDir()`, `CacheDir()`, `StateDir()` follow gh's own precedence rather than `os.UserConfigDir`/`adrg/xdg`, which resolve to `~/Library/…` on macOS and would diverge from `~/.config/gh`, which gprt piggybacks on for authentication:
  - Config: `GPRT_CONFIG_DIR` > `$XDG_CONFIG_HOME/gprt` > `~/.config/gprt`
  - Cache: `$XDG_CACHE_HOME/gprt` > `~/.cache/gprt`
  - State: `$XDG_STATE_HOME/gprt` > `~/.local/state/gprt`
  - A non-absolute `$XDG_CONFIG_HOME`/`$XDG_CACHE_HOME`/`$XDG_STATE_HOME` is invalid per the XDG Base Directory specification and is silently treated as unset. `$GPRT_CONFIG_DIR` is gprt's own variable, not an XDG one: if it is set but not absolute, `ConfigDir()` (and therefore `DefaultPath()`) returns an error naming the variable and its value instead of silently falling back to `$XDG_CONFIG_HOME`.
- `Load(path)` returns `Default()` unchanged if the file does not exist; a path that exists as a symlink whose target does not (a broken symlink) is instead reported as an error, since treating it as "no config" would silently hide the misconfiguration. An empty document (zero bytes, blank lines, comments only, or just a `---` marker) also returns `Default()` unchanged: goccy/go-yaml's `Decoder.Decode` overwrites its destination with a zero value before reporting `io.EOF` for an empty document, so `Load` uses `yaml.NewDecoder(...).Decode` specifically to detect that `io.EOF` and discards the now-zeroed struct in favour of a fresh `Default()`, rather than the naive `yaml.UnmarshalWithOptions` (which would silently return the zeroed config with no error at all). A file with more than one YAML document (separated by `---`) is rejected as `*config.ParseError`: without this check the decoder would silently parse only the first document and ignore the rest. A lone trailing `---` with nothing meaningful after it is not a second document (decoding it also reports `io.EOF`, same as an empty file) and is accepted. Otherwise `Load` unmarshals starting from `Default()` (so omitted keys keep their default) with `yaml.Strict()` (unknown keys are a config error), then calls `Validate()`. A parse/strict-decode failure, or a rejected extra document, is returned as `*config.ParseError{Path, Err, Formatted}`: `Error()` returns `yaml.FormatError`'s human-readable text (what a user sees) or the plain "multiple YAML documents" message, `Unwrap()` returns the underlying yaml error (so callers can still `errors.Is`/`errors.As` against the cause).
- `Validate()` collects every problem via `errors.Join` instead of stopping at the first one: `icons` ∈ {unicode, nerd}; `list.state` ∈ {open, closed, merged, all}; `refresh_interval` ≥ 30s; `tab_width` ∈ [1, 16]; `highlight_style` ∈ {""} ∪ chroma's own `styles.Names()`; each `list.sections[i]` needs a non-empty `name` and `query`; each `keys[action]` needs a non-empty sequence. A non-integral `tab_width` (`2.5`) is silently truncated by the YAML decoder before `Validate` ever sees it (`tab_width: 2.5` becomes `2`, no error) — a YAML-decoder quirk, not a validation gap. `highlight_style` is checked here, at startup, rather than left to `theme.SetHighlightStyle`/chroma's own `styles.Get` to silently fall back to a default for an unknown name (M2 review): gprt has no startup-toast mechanism that runs before the TUI takes over the screen, so a runtime-only warning would never reach the user. An empty `highlight_style` is accepted (not checked against `styles.Names()` at all): `theme.SetHighlightStyle` already treats it as "use the default" rather than an error (M2 review round 3, item 27), so rejecting it here would only be stricter than the value's own documented meaning. An unknown non-empty name's error message names a few example style names (`"github-dark"`, `"monokai"`, `"dracula"`), since chroma's own `styles.Names()` has no other discoverable listing surfaced anywhere in gprt itself.

## Concurrency rules

Binding for every implementer; violating one of these is a defect regardless of test coverage.

1. `store` fields are UI-goroutine only; no mutex. Goroutines get ctx + snapshot values, never the store itself.
2. `dispatch` is called only from goroutines the store started; never from key handlers or dispatch callbacks. Synchronous results return by value. Tests drive `Dispatch` through a channel-based fake event loop (a fake that calls `f()` synchronously is forbidden because it would hide deadlocks).
3. Every async result carries a generation token; `apply` drops results whose token != current (ctx cancel alone is not enough).
4. Timer callbacks (`AfterFunc` debounce, refresh ticker) only `dispatch(func(){ store.X() })`.
5. In-flight dedup map is registered/unregistered on the UI goroutine.
6. `cache.Store` (mutex) and `gh.Client` (stateless) are goroutine-safe; rate-limit info travels with results.
7. Mutations run through a single-flight FIFO queue; no re-send while in flight (implemented, M3a: `internal/store/mutations.go`). Unlike rule 8's highlight pool, this queue is not a bounded-channel worker pool fed from the UI goroutine — it starts at most one directly-spawned goroutine at a time from a plain UI-goroutine-owned slice — so the deadlock rule 8 describes does not apply to it; a future mutation kind that needed real concurrency (rather than single-flight) would have to follow rule 8's shape instead.
8. Highlight pool (2 workers) is ctx-cancelled on PR switch (implemented, M2: `internal/store`'s `startHighlightPool`/`resetFiles`). Verified (M2) that a resolved `*chroma.RegexLexer` is safe for concurrent `Tokenise` calls once compiled, so one shared lexer per file extension — not one per worker — is used; see `internal/highlight`'s doc comments for the underlying chroma/regexp2 guarantee this relies on. **The UI goroutine must never send directly on a bounded channel a worker pool reads from** (found in M2 review): a worker blocked in `Dispatch` — which blocks until the UI goroutine runs the queued function (rule 2) — while the UI goroutine is itself blocked trying to enqueue more work on a full channel deadlocks the whole application, since neither side can make progress. `internal/store`'s highlight pool avoids this with an unbounded, mutex-protected `highlightQueue` the UI goroutine only ever pushes to (never blocking) plus a non-blocking, coalescing wake signal; a dedicated feeder goroutine (not the UI goroutine) drains it and forwards jobs onto the workers' bounded channel, blocking *itself* when that channel is full. Any future UI-goroutine-fed worker pool (for example a mutation queue) must follow the same shape.
9. Every goroutine has `defer recover` → log + toast. Never wait for goroutines after `app.Stop()` (tview #1163); `main` returns as soon as `Run()` returns.
10. `app.Suspend`/`app.Sync` may be called from key handlers; never `app.Draw()` from the event loop; use `QueueUpdateDraw` everywhere. SimulationScreen tests run `Run()` in a goroutine and synchronise assertions through `app.QueueUpdate`.
