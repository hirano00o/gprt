# Keybindings

Reference for gprt's default keybindings. This is the source for the in-app `?` help screen.

## Status

`internal/ui/keys` (normalisation, vim-notation parsing, the full default keymap below, `Merge` validation, and the `Sequencer` multi-key/count state machine) and the router (`internal/ui`) are implemented (M1a). The **Status** column below marks each binding `Done (M1a)` once the *action itself* has an effect — reaching it through the Sequencer and dispatch table is not enough on its own if the pane or feature it controls does not exist yet. Every binding is present in the keymap and listed by `?`/`:help` regardless of its status, since remapping validation (`keys:` in config) does not depend on whether an action is implemented yet.

Since M3a, `App.currentContexts` resolves the PR tab (`prView`) through `ContextPR` first (falling back to `ContextDetail`/`ContextGlobal`) — `c`/`e`/`d` (bound identically in `ContextPR` and `ContextComment`, so `ContextComment` needs no separate resolution of its own yet) reach the composer's own open/edit/delete actions from there. Since M3b, the diff (`diffView`) resolves through `ContextDiff` first, then `ContextThread`/`ContextComment`, then `ContextGlobal` — `ContextDiff` always wins the `c` binding (`diff.comment`), whose own dispatch case then decides "new comment" vs. "reply" from the cursor's actual row (a thread header row vs. a line row), matching the fixed single action ID documented in footnote 2 below; `ContextThread`'s `r`/`x` and `ContextComment`'s `e`/`d` are otherwise unreached by `ContextDiff` (which binds none of them), so they resolve regardless of cursor position — each of `App.replyToCurrentThread`/`toggleCurrentThreadResolved`/`editCurrentThreadComment`/`deleteCurrentThreadComment` itself toasts when the cursor is not actually on a thread, rather than the router silently dropping the key. `p` (`pr.pending`) is bound in `ContextPR`/`ContextFiles`/`ContextDiff` ("PR open", not just the PR tab). The composer, once open, bypasses the Sequencer/keymap entirely except for its own `Ctrl-w` chords, and even those only outside insert mode (see `App.routeComposerKey`): in insert mode, `Ctrl-w` is vim's own "delete the word before the cursor" instead, forwarded to the TextArea, which implements it natively. Every other key — including ones that are global bindings elsewhere, like `q`, `R`, `?`, or `:` — goes straight to the vim editor as one of *its* keys instead (see "Vim editor keys" below). Since M4, `pr.submit` (`S`) is bound in `ContextPR`/`ContextFiles`/`ContextDiff` ("PR open", matching `pr.pending`'s own contexts) and `comment.react` (`a`) is reachable from `ContextPR`/`ContextComment` exactly like `e`/`d`, so it resolves both on the PR tab and on the diff (through `ContextComment`, always included there regardless of cursor position — see the diff `ContextDiff` paragraph above); Since M5, `list.new_pr` (`n`) opens the create-PR form (`internal/ui/createform.go`), reachable only from `ContextList`, and `pr.edit` (`E`) is bound in `ContextPR`/`ContextFiles`/`ContextDiff`, matching `pr.pending`/`pr.submit`'s own contexts, and opens the edit-PR form (`internal/ui/editform.go`) regardless of which of those three panes currently has focus. On the PR tab specifically, `e`/`d` on the description block (the pull request's own body) resolve differently from an issue-comment block: `e` opens a composer editing the pull request's body (`comment.edit`, `internal/ui/prbody.go`) and `d` is a no-op toast (`comment.delete`) — a pull request's own body has no delete operation, only edit.

Two overlay dialogs beyond `?`/`:messages`/the confirm modal exist since M3b, both routed by the same single-overlay `App.overlay` mechanism as those (`App.handleKey`'s `switch a.overlay` in router.go): a **choice menu** (`App.showChoiceMenu`, a small `*tview.List`) for the send-mode picker ("Add single comment" / "Add to review"), the submit-review event picker ("Approve" / "Request changes" / "Comment"), and for picking among several of a thread's own comments to edit/delete/react to — `j`/`k` move, `Enter` chooses, `q`/`Esc` cancel (returning to the composer with its text intact, when one is open behind it); and the **pending list** (`App.openPendingList`, `p`) — `j`/`k` move, `Enter` opens the entry under the cursor, `d` deletes it (after a confirm via `App.showConfirm`, stacked on top like any other overlay it is called over — a Ctrl-C-while-mutating "Quit anyway?" confirm can even stack on top of that one in turn, see `App.confirms`), `D` discards the whole pending review (same stacked confirm), `q`/`Esc` close it. A read-only overlay of the same shape, the **review-threads list** (`internal/ui/threadlist.go`'s `App.openThreadList`, `t`, `overlay == "threads"`), lists every review thread on the current pull request sorted by path then line — `j`/`k` move, `Enter` jumps to the entry's thread in the Files tab (opening its file, syncing the tree, and focusing the diff so `r`/`x`/`c` work immediately) and closes the dialog, `q`/`Esc` close without acting; it re-renders on `EventPRChanged`/`EventMutationChanged` while open, exactly like the pending list. Every confirm dialog (this one and `App.showConfirm`'s own `"confirm"` overlay — delete/discard, `:merge`/`:close`/`:reopen`, Ctrl-C-while-mutating) defaults focus to "Cancel", never the destructive/executing button: `Tab`/`Backtab` moves to it, then `Enter` confirms — a bare `Enter` right after the dialog opens does nothing. Since M4, another overlay, the **reaction picker** (`App.openReactionPicker`, `a`), lists GitHub's eight known reactions for one subject (the pull request's own body, an issue comment, a review, or a review comment), each row showing its current count and a `YOU` marker once `ViewerHasReacted` — `j`/`k` move, `Enter`/`Space` toggles it via `Store.ToggleReaction` and leaves the picker open (so several reactions can be toggled in a row), disabled with a toast while `Store.Mutating()`; `q`/`Esc` close it. The picker re-renders on `EventPRChanged` (so a toggle's own optimistic apply, or an unrelated background refresh, updates counts/markers live) and closes itself if its own subject can no longer be found at all. Opening it is refused with a toast when `PullRequest.ViewerCanReact` is false.

Since M5, five more overlays exist, each forwarding most keys straight to a `tview` built-in rather than a router-owned scheme of its own: the **merge dialog** (`App.cmdMerge`, `:merge`) is a `*tview.TextView` "loading repository settings…" placeholder (`q`/`Esc` close it) until `RepositoryInfo` resolves, then a real `*tview.Form` (method `DropDown`, commit headline `InputField`, commit body `TextArea`, a read-only summary `TextView`, "Merge"/"Cancel" buttons) — every key is forwarded to the Form's own `InputHandler` except `Esc`, which cancels; the **edit-PR form** (`App.openEditPRForm`, `E`) is a `*tview.Form` (Title/Base branch `InputField`s — the base field autocompletes from `Store.SearchBranches`, debounced 300 ms — a Draft `Checkbox`, "Labels (N selected)"/"Reviewers (N selected)" buttons, and an "Edit body" button opening the vim composer inside the form's own body pane below it, with the same keys as the create-PR form's body composer below) forwarding every key to the Form except `Esc` (asks "Discard changes?" first, only if the computed diff against the pull request is non-empty) and `Ctrl-s` (saves); `Up`/`Down` are rewritten first (`internal/ui/formnav.go`'s `rewriteFormNavKey`, applied by the same router) to move between items exactly like `Tab`/`Backtab` already do, *unless* the Base field's own autocomplete drop-down is currently shown, in which case the rewriting runs the other way — `Tab`/`Backtab` navigate its candidates instead (`Enter` still selects one, unchanged) — and a bare `Esc` only closes that drop-down rather than reaching the cancel path above; the **edit-labels overlay** (stacked over the edit-PR form) is a plain multi-select `*tview.List` over the repository's label catalog — `j`/`k` move, `Space` toggles, `Enter` confirms (writing the selection back to the form and its own button text), `q`/`Esc` cancel (discarding whatever was toggled within this overlay only); the **reviewers overlay** (`internal/ui/editreviewers.go`, stacked over either the edit-PR form or the create-PR form below — `App.reviewersOwner` names which one) combines a search `InputField` (typing debounces a `Store.SearchTeams` call by 300 ms, against the owning form's own chosen repository) and a multi-select `*tview.List` of currently-requested reviewers (removable), repository users matching the typed text (addable; a `"(loading users…)"` row stands in until that repository's mentionable users resolve), and searched teams (addable) — `Tab` toggles focus between the two, `j`/`k`/`Space` act on the list, `Enter` confirms (writing the result back to whichever form opened it and that form's own "Reviewers (N selected)" button), `Esc`/`q` cancel; the **create-PR form** (`App.openCreatePRForm`, `n`, `ContextList` only) is a bordered dialog (`createFormLayout`) with a `*tview.Form` (`createForm`) on the left — Repository `InputField` — fuzzy-autocompleted, `github.com/sahilm/fuzzy`, over `Store.ViewerRepositories()`'s own `nameWithOwner`, an exact `"owner/name"` not in that list also accepted; Head/Base branch `InputField`s, each autocompleting from `Store.SearchBranches` like the edit-PR form's own base field; a Title `InputField`; a Draft `Checkbox`; "Edit body" and "Reviewers (N selected)" buttons, both refused with a toast until a repository is chosen — below the buttons, a read-only body preview (`createFormBodySlot`), swapped for the vim composer while "Edit body" is open; on the right, a live diff preview between the chosen Head and Base branches (`createFormPreview`) forwarding every key to the Form except `Esc` (asks "Discard this pull request?" first, only once anything has been entered), `Ctrl-s` (validates locally, then calls `Store.CreatePullRequest`), and `Ctrl-w l` (moves focus to the diff preview — see below); `Up`/`Down`/`Tab`/`Backtab`/`Esc` are rewritten by the same `rewriteFormNavKey` the edit-PR form uses, for each of the three autocompleted fields (Repository/Head/Base) independently — including the Repository field's own drop-down, already shown the moment the form opens (its `SetAutocompleteFunc` callback runs once, eagerly, right when it is registered), so the very first `Esc` there only closes it. Choosing a repository (typing or picking a suggestion) loads its metadata/mentionable users, preselects Base with the repository's default branch, and — only if the body is still empty — prefills it from the repository's first pull request template; the same three fields also debounce (300 ms) a refresh of the diff preview (`Store.CompareBranches`) once all three are set, showing a `"(choose repository, head and base to preview)"` hint until then, `"(loading…)"` while a comparison is in flight, and the error message on failure. `Ctrl-w l` from the form focuses the diff preview, where `j`/`k`/`g`/`G`/`h`/`l`/`PgUp`/`PgDn`/the arrow keys scroll it natively (its own `TextView`); `Ctrl-w h` or a literal `Esc` from there returns focus to the form instead of scrolling or (`Esc`'s usual meaning here) cancelling it. "Edit body" opens the vim composer (a new kind, `composerKindNewPRBody`, `internal/ui/createform.go`/`composer.go`) directly inside `createFormBodySlot`, in place of the read-only body preview, over the create form's own body text instead of calling the store on send — the form's other fields and its diff preview stay visible, and live, the whole time: `Ctrl-s`/`:w` and `:q` (which otherwise only keeps a draft) both hand the typed text back to the form and return to it; only `:q!` discards it. `Ctrl-w h`/`l`/`j`/`k` are all no-ops from within it (the global pane-focus functions they would otherwise call have no notion of this overlay at all, and would strand the composer, unfocused and unreachable, behind the main list/detail layout); `submitCreateForm`/`cancelCreateForm` refuse with a toast ("finish editing the body first") while it is open, as a second, independent guard against the same. Its own draft is scoped to the chosen repository, not to any pull request — it never shows up in the "p" pending list, is restored by reopening `n` for the same repository, and is deleted once the pull request is created, the form itself is discarded, or the form's Repository field is switched to another repository. Unlike every other overlay in this milestone, neither the create-PR form nor its own body composer is bound to `Store.CurrentRef()` at all: opening it does not require a pull request to be open, and switching the currently open pull request while it is open never closes either one.

The `?` help and `:messages` overlays are scrollable `TextView`s: `q` or `Esc` closes either one (pressing `?` again also closes the help overlay specifically), and every other key — including `j`/`k`/`gg`/`G`/`PgUp`/`PgDn` — is left to the `TextView`'s own native scrolling rather than being swallowed by the router. Inside the help overlay specifically, `/` opens its own search row (a hidden `InputField` below the text, the same show/hide trick the list filter uses) — `Enter` runs it (Go `regexp`, vim smartcase), marks the current match in reverse video, and scrolls it into view; `n`/`N` cycle through every match (wrapping around), each one marked and scrolled to in turn; feedback (match count, "no match", an invalid pattern) is shown in the overlay's own title, since it covers the status bar. `:messages` has no search of its own. `list.down`/`up`/`top`/`bottom`/`half_down`/`half_up`/`page_down`/`page_up` are bound in the `files`/`detail`/`diff` contexts too and move whichever movable pane currently has focus — the PR list, the PR tab, the Files tab's tree, or its diff. For the tree specifically, these actions are routed through a `treeMovablePane` adapter that synthesises `tview.TreeView`'s own native `j`/`k`/PgUp/PgDn keys (repeating `k`/`j` for top/bottom, since `tview.TreeView`'s native `g`/`G` only scroll the viewport and never move the selection itself) rather than reimplementing tree traversal by hand, so the visible movement is unchanged from the tree's native behaviour. `K`/`J` (parent/child navigation) remain `tview.TreeView`'s own, unmapped by gprt's keymap. `h` is added on top of the tree's native handling via its own `SetInputCapture` (collapse-or-parent); `l` is the remappable `list.open` action (`Enter`'s row below), routed to `treeOpen` when the tree has focus rather than the list's own `Select`. A key genuinely bound in no context still falls through unchanged.

## Remapping

`keys:` in `config.yaml` remaps a binding by **Action ID**, using vim notation for the key sequence (`<C-w>o`, `gt`, `]c`, `<Esc>`, `<Enter>`). Any action not listed in `keys:` keeps its default sequence. Example:

```yaml
keys:
  global.toggle_list: "<C-w>o"
  diff.comment: "c"
  pr.submit: "S"
```

Two remapping errors are rejected at startup: an unknown action ID, and a key sequence that duplicates or is a prefix of another sequence already bound in the same context.

The vim editor's own keys (listed at the bottom of this document) are **fixed** and cannot be remapped through `keys:`.

³ `Ctrl-c` shares `global.quit`'s intent (quit the application) but is handled separately by the router because of its in-flight-mutation confirmation; see `docs/DESIGN.md`, concurrency rule 9.

## `:` commands

Entered via `global.command` (`:`), these exist only as typed commands, never as single-key bindings, specifically to avoid an accidental keypress next to `n` triggering something destructive:

| Command | Effect | Status |
|---------|--------|--------|
| `:merge` | Open the merge dialog (method picker restricted to the repository's own allowed methods, with a single allowed one preselected; commit headline/body; a `Mergeable`/`MergeStateStatus`/review-decision summary line), then a confirmation dialog ("Merge #N with `<method>`?", followed by the repository, title and author) | Done (M5) |
| `:close` | Close the current PR, after a confirmation dialog ("Close #N?", followed by the repository, title and author) — refused with a toast when `ViewerCanClose` is false or the pull request is not `OPEN` | Done (M5) |
| `:reopen` | Reopen the current PR, after a confirmation dialog ("Reopen #N?", followed by the repository, title and author) — refused with a toast when `ViewerCanReopen` is false or the pull request is not `CLOSED` | Done (M5) |
| `:messages` | Show the ring buffer of recent log messages (see `internal/logging`) | Done (M1a) |
| `:help` | Show the help screen (same as `?`) | Done (M1a) |
| `:q` | Quit, asking for confirmation first while a mutation is in flight (same `quitWithConfirmIfMutating` as `q`/`Ctrl-c`) | Done (M1a) |
| `:quit` | Quit (alias of `:q`) | Done (M1a) |
| `:reload` | Discard cached data and re-fetch every section (same as `R`) | Done (M1a) |

An unrecognized command shows an error toast instead of doing nothing silently.

## Vim editor keys (composer, fixed — not remappable)

Done (M3a): `internal/ui/editor`'s `Vim` modal layer and `Editor` primitive (`*tview.TextArea` + a one-line mode/hint status row), wired into the composer pane. The "Add single comment" / "Add to review" choice menu is done (M3b) — `Ctrl-s`/`:w` sends directly for a general comment (`AddComment`) or an edit (`EditComment`/`EditReviewComment`), and shows the menu first for a line/range/file comment or a reply whenever `Store.CanSendSingle()` is true (see the choice-menu note above the default bindings table). Since M4, `Ctrl-s`/`:w` on the submit-review composer (opened by `S`, not a vim key of its own) sends via `Store.SubmitReview` instead — see the `S` row above.

| Key(s) | Effect |
|--------|--------|
| `Esc` | Leave insert/visual mode (also closes the mention popup by itself, without leaving insert mode — see below) |
| `i a I A o O` | Enter insert mode (insert before/after cursor, start/end of line, open line below/above) |
| `Ctrl-w` (insert mode) | Delete the word before the cursor (forwarded to `TextArea`'s own native implementation — outside insert mode, `Ctrl-w` instead starts the `Ctrl-w j/k/h/l` focus chord described above) |
| `h j k l w b e 0 ^ $ gg G` (with optional counts) | Motions |
| `x X dd dw de d$ D cc cw c$ C yy yw p P` | Operators and shortcuts (delete, change, yank, paste); `cw` behaves like `ce` (does not eat trailing whitespace) when the cursor starts on a non-blank, matching vim |
| `J` | Join lines |
| `u` | Undo (one insert session — `i`/`a`/`I`/`A`/`o`/`O`/`cc`/`cw`/`c$`/`C`/`s` through the next `Esc` — is a single undo unit) |
| `Ctrl-r` | Redo |
| `v V` + `d y c` | Visual / visual-line selection combined with an operator |
| `:w`, `Ctrl-s` | Send: `AddComment` for a new general comment, `EditComment` for an edit; refused with a toast while another mutation is already in flight |
| `:q` | Close the composer, keeping the draft |
| `:q!` | Close the composer, discarding the draft |
| `:e` | Suspend the TUI, edit the buffer in the configured `editor` (falling back to `$EDITOR`, then `vim`), and restore it (CRLF normalized to LF) as one more undo entry. Any failure — the TUI could not be suspended, the command itself failed, or a temp-file operation failed — shows `editor failed: …` in the status line, toasts the same message, and leaves the buffer untouched (never blanks it) |
| `@` (insert mode) | Opens a completion popup listing the open PR's author, requested reviewers, and every comment/review author so far, followed (since M4) by the repository's own `mentionableUsers` (deduped by login against the PR-derived participants above), fuzzy-matched (`sahilm/fuzzy`, case-folded, ranked by match quality) against what follows `@` |
| `Ctrl-n`, `Ctrl-p`, `Up`, `Down` (mention popup) | Move the selection in the `@`-mention popup |
| `Tab`, `Enter` (mention popup) | Accept the selected mention (`@login `, one `Replace`) |
| `Esc` (mention popup) | Close the popup only, without leaving insert mode |
| `Left`, `Right`, `Home`, `End` (mention popup) | Close the popup — these move the cursor without editing the buffer, so nothing would otherwise re-evaluate whether it is still over a mention span; `Tab`/`Enter` also verify the span itself before accepting, as a second line of defense |
