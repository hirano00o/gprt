# Requirements

Status values: `Done`, `In progress`, `Planned`. Milestones refer to the branches in the [Milestones](#milestones) section of `docs/DESIGN.md` (`M1a`, `M1b`, `M2`, `M3a`, `M3b`, `M4`, `M5`). This table is updated in the same commit as any change to implementation status.

Review comments are also done end to end (M3b): `e`/`d` with the diff's cursor on a thread row collect the comments the viewer may edit/delete — none toasts, one acts directly, several show a choice menu ("@author: first line") — and call `Store.EditReviewComment`/`DeleteReviewComment`. PR metadata editing's data side is done (M5 data slice): `Store.UpdatePullRequestMeta` (`gh.Client.UpdatePullRequest` — title/body/base/labels, a field left unset sent as an explicit GraphQL null meaning "leave unchanged"), `Store.SetReviewers` (`gh.Client.RequestReviewers`, `union: false`, replacing the requested-reviewer set outright), and `Store.SetDraft` (`gh.Client.MarkReadyForReview`/`ConvertToDraft`) — each applies the server's own returned fields optimistically, then invalidates/refetches the pull request and refreshes the list (`mutation.refreshList`). The pull request's own body is edited the same way as a comment (M5 UI slice): `e` on the PR tab's description block opens a composer (`composerKindPRBody`, `internal/ui/prbody.go`), prefilled with the live body, sending `Store.UpdatePullRequestMeta` with only `Body` set; `d` there is a no-op toast (a pull request's own body cannot be deleted). The edit-PR form itself is done (M5 UI slice, `internal/ui/editform.go`): `E` (`ContextPR`/`ContextFiles`/`ContextDiff`, refused with a toast when `ViewerCanUpdate` is false) opens a `tview.Form` with Title/Base branch (autocompleted via `Store.SearchBranches`, debounced 300ms) `InputField`s, a Draft `Checkbox`, and "Labels (N selected)"/"Reviewers (N selected)" buttons opening stacked multi-select overlays (`editlabels.go`/`editreviewers.go`, `Space` toggles, `Enter` confirms, `Esc`/`q` cancel within that overlay only); `Ctrl-s` computes the diff against the pull request and enqueues only what changed, in order — `UpdatePullRequestMeta` (title/base/labels), `SetReviewers`, `SetDraft` — toasting "nothing to save" when nothing did and each enqueued step's own success/failure, keeping the form open (values intact) until every step finishes and closing only if none failed; `Esc` asks to discard first only when that same diff is non-empty. The reviewers overlay's candidates merge three sources by ID: every currently-requested reviewer (removable), the repository's own `Store.MentionableUsers()` filtered locally by the typed query (addable — a brand-new individual user; `model.User.ID`, selected by `mentionable_users.graphql`'s own `id` field, is what makes this possible), and `Store.SearchTeams` results (addable teams); `SetReviewers` always sends the complete, current set for both `userIds`/`teamIds` (never a partial delta), since `union: false` replaces each list outright. | Done | M3a, M3b, M5 |
| F9 | Extra actions | Open PR/comment/check in browser (`o`) — done, including surfacing failures: an `Open` error toasts and reaches `:messages`, and a launched browser process exiting non-zero later (`browser.Opener.OnExit`, a background goroutine) is reported the same way via `App.ShowError`. Merge (method choice) / Close / Reopen via `:merge` / `:close` / `:reopen` commands (no single-key binding) each followed by a confirmation dialog. Data side is done (M5 data slice): `gh.Client.MergePullRequest`/`ClosePullRequest`/`ReopenPullRequest` and `Store.Merge`/`Close`/`Reopen` — `Merge`'s `prepare` hook captures the pull request's own `HeadOID` as `expectedHeadOid` at run-start time and refuses locally, with nothing sent to GitHub, when the pull request is no longer `OPEN` by then (a stale `Mergeable`/`MergeStateStatus` is left for the server to accept or reject on its own terms); each applies the server's returned state and refreshes the list on success. The `:merge`/`:close`/`:reopen` commands and their confirmation dialogs are done (M5 UI slice): `:close`/`:reopen` (`internal/ui/prcommands.go`) each require an open, loaded pull request, refuse locally with a toast when `ViewerCanClose`/`ViewerCanReopen` is false or the state does not fit (closing an already-merged pull request, reopening an already-open one), then confirm ("Close #N?"/"Reopen #N?") before calling `Store.Close`/`Store.Reopen`; `:merge` (`internal/ui/mergedialog.go`) calls `Store.EnsureRepositoryMetadata`, showing a "loading repository settings…" placeholder until it resolves (or immediately, if already fresh), then a method chooser restricted to the repository's allowed methods (a single allowed one preselected), a commit headline (defaulted to `"<title> (#N)"`, disabled for Rebase, which GitHub ignores it for) and body (a plain `tview.TextArea`), and a `Mergeable`/`MergeStateStatus`/review-decision summary line; its own Submit refuses locally when the pull request is no longer `OPEN`, otherwise confirms ("Merge #N with `<method>`?") before calling `Store.Merge`. Every one of the three tracks its own outcome (`Store.MutationError()`, never `LastError()`) for a "closed"/"reopened"/"merged" success toast or a failure one (`pendingSimpleMutation`, `internal/ui/prcommands.go` — `onMutationChanged`'s own non-composer counterpart). Local checkout is out of scope. | Done | M1a, M5 |
| F10 | CI | Show check-runs/statuses, refreshed with the PR; open a check in the browser. No rerun, no log viewing. The list's rollup icon (from the search query's `statusCheckRollup`) and the PR tab's checks list (a "Checks · X passed · Y failed · Z pending · W skipped" summary, each zero-count category omitted, plus one row per check, each opening its own details URL with `o`) are both done, refreshed every 5 minutes alongside the PR. | Done | M1a, M1b |
| F11 | Key remapping | Every navigation/action binding is remappable in config (`keys:`); the vim editor's own keys are fixed. `internal/ui/keys` (normalisation, vim-notation parsing, the full default keymap, `Merge` validation, the multi-key/count `Sequencer`) and the router are done. | Done | M1a |

## Non-functional requirements

| Requirement | Decision | Status | Milestone |
|-------------|----------|--------|-----------|
| Lazy loading | List page 1 → detail → files pages → highlight, loaded on demand rather than up front. The list's page 1 loads eagerly on start; reaching the last loaded row of a section with more pages triggers `Store.LoadMore`. `Store.OpenPR` fetches a pull request's detail only when opened (cache-first, then network). `Store.LoadFiles` fetches a pull request's changed files one REST page at a time (cache-first, then `If-None-Match`), parsing each page's patches and enqueueing a 2-worker highlight pool per page as it lands. The Files tab now triggers it itself — becoming visible, or the open pull request changing while it is visible, calls `Store.LoadFiles(false)` — so it is reachable end-to-end from the UI. | Done | M1a, M1b, M2 |
| Cache | Disk cache with ETag revalidation for REST and stale-while-revalidate for GraphQL. The on-disk `Entry{Body, ETag, FetchedAt}` store (`internal/cache`) with atomic writes and PR-scoped invalidation exists; `internal/store` caches search results per section, the current pull request's detail, and its changed files (`Get`/`Put` under `cache.PRKey(..., "files/page-<n>")` per page, `Entry.ETag` round-tripped as `If-None-Match`/a fresh `ETag` response header) — all three stale-while-revalidate: a cached result is shown immediately, marked stale, while a network refetch runs. Search and detail caching are wired end-to-end into the TUI (stale list rows render dimmed; the PR tab's header shows a "(cached)" marker while `DetailState().Stale`); files caching is data-complete and the status bar now shows one of `files N` (every page arrived), `files N/M` (more pages remain, total known), or `files N pages…` (more pages remain, total unknown), plus `highlighting N`, while the Files tab is active, though `FilesState().Stale` itself has no dedicated visual marker yet. | In progress | M1a, M1b, M2, M3b |
| Refresh | 5-minute auto refresh (configurable via `refresh_interval`) for the list and the current PR. `internal/store.StartAutoRefresh`'s ticker calls both `Store.Refresh()` and `Store.RefreshPR()` (a no-op while no pull request is open); `R` (`global.reload`) forces an immediate cache-skipping reload of both via `Store.Reload()`, which also calls `Store.ReloadPR()`. Opening a pull request from the list (`Store.OpenPR`) is done. | Done | M1a, M1b |
| Drafts | Drafts persisted on every change and restored across PR switches/reloads/restarts. `internal/drafts.Store` (atomic JSON files keyed by pull request/kind/anchor, save-on-every-change semantics, corrupt-file tolerance, a non-decoding `Count` cheap enough to call on every status-bar render) is done and wired into the composer: write-through save on every real edit (never on the initial prefill/restore itself — opening a composer and closing it again without typing anything creates no draft), restore on open (or the comment's live body, for a first-time edit composer), delete on send/`:q!` (a `Load`/`Delete` failure toasts, not just a debug-log Warn), kept (and merged into a reopened composer for the same target, or re-saved to disk otherwise) on `:q`/a mutation failure, a "✎ N" count in the status bar for the open pull request, and one composer per pull request — switching pull requests closes and saves it under its own original target automatically. Switching composer targets on the same pull request saves the outgoing one automatically, without asking. The `p` pending-review/drafts list and the diff gutter's own `✎` marker (`DiffFile.DraftLines`/`DraftMarker`, recomputed on file open and on a line/range/file draft's own save/delete, never per `Draw`) are both done (M3b). | Done | M3a, M3b |
| Auth | Reused from `gh` (`GH_TOKEN`/`GITHUB_TOKEN` override; GHES via gh host config). Implemented by `gh.New` via go-gh's `auth.DefaultHost`/`auth.TokenForHost`. | Done | M1a |
| Language | All docs, comments, commits, and UI strings in English. | Done | (ongoing convention) |
| Stack | Go 1.26, tview + tcell only (no BubbleTea), no mouse support. `go.mod` pins `github.com/rivo/tview v0.42.0` and `github.com/gdamore/tcell/v2 v2.13.10` as direct dependencies; the TUI never calls any mouse-related tcell/tview API. | Done | M1a |

## Known limitations (v1)

- Multi-line range comments are single-side only (all deletion lines or all addition/context lines, not a mix).
- No mouse support.
- No local checkout of a pull request's branch.
- No CI rerun and no check-run log viewing; checks can only be viewed and opened in the browser.
- The vim editor's own keys are fixed and cannot be remapped through config.
- The `/` diff search only matches diff line text (`diff.Line.Text`), not review thread comment bodies.
- `?`/`:help` lists every default-keymap binding, whether or not the action behind it has a pane yet. Since M3a, `diff.comment`/`comment.edit`/`comment.delete` are reachable from the PR tab (`ContextPR`). Since M3b, they are also reachable from the diff (`ContextDiff`, falling back to `ContextThread`/`ContextComment`), alongside `diff.comment_file`/`thread.reply`/`thread.toggle_resolved`; `pr.pending` is reachable from the PR tab, the tree, and the diff. Since M4, `comment.react`/`pr.submit` are also implemented, the former reachable the same way as `comment.edit`/`comment.delete`. Since M5, `pr.edit` (`E`) is implemented, reachable from `ContextPR`/`ContextFiles`/`ContextDiff` like `pr.pending`/`pr.submit`, and `list.new_pr` (`n`) is implemented, reachable only from `ContextList`.
